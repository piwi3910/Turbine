## Problem

After Phase 6, Turbine runs its two BF16 models — `meta-llama/Llama-3.2-3B-Instruct` (dense, GQA, Phase 1) and `allenai/OLMoE-1B-7B-0125-Instruct` (MoE, Phase 2) — on AMD R9700 cards (HIP backend, _libturbine_hip.so_) and NVIDIA GB10 (CUDA backend, _libturbine_cuda.so_), with tensor and data parallelism inside one vendor's collective domain, worker discovery across nodes, a TCP transport and a cluster KV directory. Every request still runs prefill and decode on the same device group, every device group holds every layer and every expert, all cross-node KV movement goes through the kernel TCP stack, and — by decision — no request ever touches devices of two vendors. Four things are missing. First, the strategies that let a model outgrow one device group: pipeline parallelism (PP) and expert parallelism (EP). The Phase 1/2 models fit one device, so Phase 7 builds PP and EP as correctness vehicles on those models, where every result can be checked against a single-device run, so the Phase 8 model families (Mixtral, Qwen3 MoE) can later use them for capacity. Second, latency interference: long prefills stall co-scheduled decodes, and chunked prefill (Phase 2) only softens it; TS §10 prefill/decode disaggregation (PD) removes it by running the two phases in separate pools. Third, transfer cost: disaggregation and cluster KV reuse pay off only if KV moves at link speed, and the two Sparks are joined by a 200 Gb/s ConnectX-7 RoCE link the Phase 6 TCP transport cannot saturate. Fourth, the lab is heterogeneous (two NVIDIA GB10 nodes, one node with two AMD RDNA4 cards), and TS §10 requires placement to understand mixed pools; Phase 7 is where mixed-vendor serving begins, as a second PD milestone that runs prefill on AMD and decode on NVIDIA over 10 GbE.

## Users

- **Operators running Turbine across several nodes:** need to declare, in configuration, which workers prefill, which decode, how a model is split into pipeline stages and expert shards, and to see from `/turbine/v1/*` and `/metrics` where every request, stage, expert shard and KV transfer is — and why each placement decision was made (TS §14).
- **Clients of the OpenAI API:** need equivalent responses (token-identical under greedy decoding where the arithmetic is unchanged, within the phase-1 golden tolerance otherwise) whether the deployment is colocated, pipelined, expert-parallel or disaggregated, and must never see duplicated or lost tokens when a transfer or a node fails (TS §12).
- **Turbine developers (humans and AI agents):** need PP, EP, PD and transfer logic testable as deterministic simulations on the macOS workstation without GPUs or RDMA NICs (TS §17 items 2, 3, 7), and a lab procedure that exercises the real RoCE link and the AMD→NVIDIA path without disturbing other workloads on the hosts.
- **Benchmark runners:** need `turbine-bench` profiles that show whether disaggregation actually improves decode ITL under prefill-heavy load, and what fraction of the RoCE link a KV transfer achieves (TS §18 "multi-node scaling efficiency").

## In scope

- [S-1] **Pipeline parallelism (PP):** a model split into contiguous layer ranges ("stages"), each stage on one device group (a Phase 5 TP group or a single device), stages chained across devices or nodes. The partitioner balances stages by estimated per-layer cost (weight bytes + per-token FLOPs; MoE layers costed by active experts) and places the embedding on the first stage and the LM head on the last (tied embeddings, as in Llama-3.2-3B, are loaded on both). Activations (hidden state, BF16, `hidden_size` × tokens) cross stage boundaries through the Phase 6 transport. Each stage owns the paged KV of its layers. The scheduler runs up to _distributed.pipeline.micro_batches_ micro-batches in flight so decode steps of different batches overlap across stages. PP stages are same-vendor in the validated configurations; a cross-vendor PP boundary is allowed by the placement validator (S-6) but not validated in this phase.
- [S-2] **Expert parallelism (EP), built on OLMoE-1B-7B:** MoE expert weights sharded across _distributed.expert.parallel_size_ ranks with a static placement map (expert id → rank) computed at load time, contiguous by default; attention, router and embeddings replicated on every EP rank (OLMoE has no shared expert; a shared expert, when a later family has one, is replicated too). Per MoE layer: route locally, dispatch tokens to owning ranks with an all-to-all through the Phase 5 collective abstraction (one runtime-loaded NCCL-API binding serving RCCL and NCCL), run experts, combine with the router weights in a fixed, rank-count-independent order. Per-rank and per-expert token counts are recorded (TS §10 "utilization metrics"). The lab vehicle is EP 2 across the two R9700 cards on `novanas` (RCCL, the Phase 5 collective domain).
- [S-3] **Prefill/decode disaggregation (PD):** workers take a role — `prefill`, `decode` or `both` (_distributed.role_). The ingress worker that accepted the HTTP request chooses a prefill worker and a decode worker (S-7 scoring), the prefill worker runs the whole prompt and samples the first token, the decode worker pulls the request's KV (S-4, S-5), and generation continues on the decode worker. The token stream is relayed to the client by the ingress worker (Phase 6 symmetric ingress), so the client connection never moves. Delivered in two milestones: **M1** — prefill on `dgx-spark`, decode on `dgx-spark2`, same vendor, over the 200 Gb/s RoCE link with the RDMA transport; **M2** — heterogeneous: prefill on `novanas` (AMD R9700, HIP backend), decode on a Spark (NVIDIA GB10, CUDA backend), over 10 GbE with the TCP transport. M2 starts only after M1's acceptance criteria pass.
- [S-4] **KV transfer format "TKV1":** a versioned, self-describing, checksummed wire format for one request's attention KV blocks (header layout under Interfaces). It carries a model fingerprint, the KV dtype, the token range, the first sampled token and the sampler state, so the receiver can reject a mismatch before touching its pools. KV is sent in the **sender's native dtype** in a canonical, vendor-neutral layout; the receiver accepts it as-is when dtypes match, applies an **exact upcast** when one exists (e.g. FP8 → BF16), and refuses every lossy conversion unless _distributed.kv_conversion.allow_lossy_ is set. It is the only format used for PD, cluster KV retrieval (Phase 6 directory hits) and heterogeneous transfers. Segment kinds for linear-attention recurrent and convolution state are reserved in version 1 so the Phase 8 model-families track can add hybrid models without a new wire version; Phase 7 senders never emit them.
- [S-5] **RDMA transport:** a `rdma` transport in `turbine-transport` for RoCE v2 over reliable-connected (RC) queue pairs written in Turbine, on top of rdma-core _libibverbs.so.1_ loaded at runtime with `libloading` (never linked at build time; no UCX, NIXL or other middleware). The decode side performs one-sided RDMA READs of registered source buffers; the control exchange runs over the Phase 6 authenticated control channel. On GB10 the KV pool lives in unified memory and is registered directly; where registration of the pool fails the transport stages through a registered bounce buffer of _distributed.transport.rdma.bounce_bytes_. The Phase 6 TCP transport remains the fallback, selected per peer pair by the topology graph, and is the only transport for `novanas` (no RDMA NIC).
- [S-6] **Heterogeneous pools and mixed-vendor serving:** a capability model in `turbine-distributed` that records, per device, vendor, architecture, supported dtypes and KV dtypes, execution backend (HIP / CUDA), collective backend (RCCL / NCCL) and link types, and a placement validator that allows or refuses each strategy per device set: TP and EP only within one collective domain (same vendor and backend); PP across vendors only when the boundary tensor dtype is supported on both sides; PD across vendors only when both sides use the same model fingerprint and _kv.block_tokens_ and the S-4 conversion table has a lossless path. This lifts the Phase 1–6 rule "no mixed-vendor serving" for PD and PP only. Refusals are startup errors naming the devices, the strategy and the missing capability.
- [S-7] **Cluster KV directory and routing extensions:** directory entries gain per-location KV dtype, in-flight transfer state (source, destination, bytes, deadline) and a transfer-cost estimate per transport; the router scores candidate prefill/decode workers with TS §11 `compute availability + KV locality + transfer cost + device pressure + SLA/priority`, logging every term of the chosen and the runner-up candidate. Transfer cost uses the measured per-peer-pair bandwidth (RDMA ≈ 25 GB/s line rate, 10 GbE ≈ 1.25 GB/s), so a 10 GbE hop is chosen only when its prefill savings exceed its transfer time.
- [S-8] **Pressure and admission integration:** a disaggregated request is admitted only when both pools admit it (Phase 3 admission with worst-case KV reservation, evaluated on each side with its own budget); the decode worker reserves KV blocks before the prefill worker starts; in-flight transfers are bounded per worker (_distributed.pd.max_inflight_transfers_) and count as reserved memory on both sides until committed or released.
- [S-9] **Failure handling (TS §12):** transfer timeout, checksum failure, transport loss, prefill-worker loss and decode-worker loss each have a defined outcome (Failure modes) with no duplicated or lost tokens; PD falls back per _distributed.pd.fallback_. Node death follows the Phase 6 rule: rerun elsewhere only if no token has streamed, otherwise the defined recovery or `worker_lost`.
- [S-10] **Observability:** the metrics listed under Interfaces, the `pipeline`, `expert` and `pd` sections of `GET /turbine/v1/scheduler` and the `transfers` section of `GET /turbine/v1/kv`, and a structured log event with reason codes for every placement, routing, fallback and transfer decision.
- [S-11] **Deterministic simulation and chaos tests:** a GPU-free simulator for PP scheduling, EP dispatch/combine and PD request flow with injectable transport latency, loss and corruption, run by `cargo test` on macOS (TS §17 items 2, 3, 7).
- [S-12] **Lab validation and benchmarks:** lab configuration files and a runbook for PP and PD M1 across `dgx-spark` / `dgx-spark2` over RoCE, EP on `novanas`, and PD M2 from `novanas` to `dgx-spark`; `turbine-bench` profiles `prefill-heavy` and `decode-heavy` and a `compare` report that sets PD against two colocated DP replicas on the same two nodes; a `turbine-bench kv-transfer` subcommand measuring TKV1 transfer bandwidth against the link's `ib_write_bw` baseline.

## Out of scope

- Hot-expert replication and dynamic expert re-placement at runtime (TS §10 "future"); Phase 7 placement is static per load, with metrics that would justify it later.
- Combining strategies inside one request path beyond: PD with each pool being a single device or a Phase 5 TP group; PP alone; EP alone. Arbitrary PP×TP×EP×PD compositions keep composable interfaces but are not validated.
- EP across nodes (EP over NCCL on the RoCE link) and PP across vendors: allowed by the validator, not validated in this phase.
- Serving a model that does not fit one device group; PP and EP are proven on the Phase 1/2 models, and larger models arrive with the Phase 8 model-families track.
- Transparent continuation of a generation after its decode worker dies with state that existed only on that worker (TS §12): recovery re-derives state from the emitted token history (Failure modes), it does not migrate live GPU state.
- Encryption of RDMA payloads (RoCE has none); RDMA is restricted to configured peers (Constraints). The control channel keeps the Phase 6 pre-shared-key HMAC authentication without encryption.
- NVLink/NVSwitch, InfiniBand fabrics, multi-rail striping, GPUDirect RDMA into discrete VRAM and GPUDirect Storage — none exist or are needed in the lab (`novanas` has no RDMA NIC).
- Linear-attention (Gated DeltaNet) recurrent-state transfer: reserved in TKV1 (S-4), implemented by the Phase 8 model-families track together with the hybrid models.
- Lossy KV conversion across devices (e.g. BF16 → FP8) unless enabled explicitly; it is off by default and its quality validation (TS §8) belongs to the Phase 8 quantization track. Phase 7 KV is BF16 on every device (Phase 2 decision).
- Intel devices, quantized weights, speculative decoding and multimodal input (Phase 8 or out).
- Autoscaling of pools, cross-cluster federation, per-tenant placement policy.

## Constraints

- Rust only in the serving path; no Python (TS §21 rule 4). RDMA verbs (_libibverbs.so.1_) and collective libraries (RCCL/NCCL) are loaded at runtime with `libloading`, exactly as Phase 0 loads NVML and amd-smi and Phase 1 loads the kernel libraries, so the workspace still builds and every non-ignored test passes on macOS arm64 with no GPU and no RDMA libraries.
- `unsafe` and FFI added by this phase live only in the `rdma` module of `turbine-transport` (verbs) and in the existing collective FFI module from Phase 5; the phase-1 `unsafe_isolation` test's allowlist gains exactly that module; every `unsafe` block carries a `// SAFETY:` comment stating the lifetime rule for registered memory regions: a region is deregistered only after every posted work request referencing it has completed or the queue pair is in the error state (TS §21 rule 10).
- The Phase 6 control-plane protocol's maximum version rises to 2 (`PROTOCOL_MAX`, contract-chosen); the Phase 6 test `proto::tests::message_roundtrip_and_versioning` then uses protocol 3 as the unsupported version.
- Every queue and buffer is bounded (TS §21 rule 8): in-flight micro-batches per pipeline (_distributed.pipeline.micro_batches_), in-flight transfers per worker (_distributed.pd.max_inflight_transfers_), EP dispatch buffers (sized at load from _distributed.expert.max_tokens_per_rank_), RDMA send/receive queue depth (_distributed.transport.rdma.queue_depth_).
- Correctness before optimization (TS §21 rule 1): PP must be token-identical to the colocated single-device run under greedy decoding with the same batch composition (it changes no arithmetic); PD in simulation must be token-identical, and on hardware within the phase-1 golden tolerance (≥ 14 of 16 prompts with the first 32 greedy tokens identical, top-5 |Δlogprob| ≤ 0.15 nats; prefill and decode run in different batch compositions, and in M2 on different vendors' kernels); EP must match within the same tolerance with the combine order fixed by S-2.
- Memory registered for RDMA is exposed only with `REMOTE_READ` access, only to peers listed in the Phase 6 worker registry, only for the lifetime of one transfer, and is deregistered (or its rkey invalidated) on commit, release or timeout (TS §16).
- Models: `meta-llama/Llama-3.2-3B-Instruct` for PP and PD (28 layers, hidden size 3072, 24 query heads, 8 KV heads × head_dim 128, tied embeddings, ~6.4 GB in BF16; attention KV = 28 × 2 × 8 × 128 × 2 B = 114,688 B/token in BF16) and `allenai/OLMoE-1B-7B-0125-Instruct` for EP (16 layers, hidden size 2048, 16 query and 16 KV heads × head_dim 128, 64 routed experts with top-8 routing, no shared expert, 4,096-token context, ~13.8 GB in BF16). Figures come from the published _config.json_ files and are re-checked against the downloaded copies before the lab runs. Weights live in `/home/piwi/turbine-models/<slug>` on each host, downloaded by Claude with the user's HF token at that time (never stored in the repo); tests read `TURBINE_TEST_MODEL_DIR` and never download.
- Lab: `dgx-spark` (192.168.10.246) and `dgx-spark2` (192.168.10.245), 1× GB10 each, ~121 GB unified memory each, ConnectX-7 RoCE at 200 Gb/s on 192.168.47.0/24 (_rocep1s0f0_) and 192.168.48.0/24 (_roceP2p1s0f0_), rdma-core user tools (`ibv_devinfo`, `ib_write_bw`) installed, `nvidia_peermem` not loaded; Turbine runs there in `docker run` containers. `novanas` (192.168.10.203): 2× Radeon AI PRO R9700 (`gfx1201`, 32 GB each), ROCm 7.14.1 at `/opt/rocm/rocm`, 10 GbE only, no RDMA, no Docker — Turbine runs as k3s Jobs requesting `amd.com/gpu` with host networking. Every lab run uses a memory budget (`reliability.memory.device_budget_bytes`; there is no memory-budget key under `server` — CONFLICT C-12) within the host's free memory measured at the start of that run and a port that is not 8000/8890/8891.
- **Host workloads:** any lab run that needs production workloads (e.g. production vLLM on the Sparks, anything using the R9700 cards) moved or memory freed on any host is started only after the implementer has asked the user and the user has moved the workloads; the implementer never stops, moves or reconfigures production workloads itself. ### Wire format TKV1

All integers little-endian. One transfer = one header segment followed by payload segments; every segment is independently checksummed so a receiver can verify segments as their RDMA READs complete.

```
Header (fixed part, 128 bytes)
  magic            [4]  "TKV1"
  version          u16  = 1
  flags            u16  bit0 = has_recurrent_state (reserved, 0 in Phase 7), bit1 = has_sampler_state
  request_id       [16] UUID of the request
  model_fp         [32] SHA-256 of the vendor-neutral KV identity: model config hash + weights index hash
                        (the Phase 4 identity inputs) + KV dtype + block_tokens + layer/head/head_dim description;
                        excludes device-specific pool layout
  kv_format        u16  0 = bf16, 1 = fp16, 2 = fp8_e4m3_per_tensor_scale, 3 = fp8_e4m3_per_block_scale
  state_format     u16  0 = none, 1 = fp32, 2 = bf16 (0 in Phase 7)
  block_tokens     u32
  token_start      u64
  token_count      u64
  first_token      u32  sampled token id (valid when token_count covers the full prompt)
  attn_layers      u16  number of attention layers carried
  state_layers     u16  number of linear-attention layers carried (0 in Phase 7)
  segment_count    u32
  header_crc32c    u32  over the fixed part with this field zeroed
  reserved         [..] zero to 128 bytes
Segment table (segment_count × 32 bytes)
  kind             u16  1 = attn_kv_block, 2 = recurrent_state (reserved), 3 = conv_state (reserved), 4 = sampler_state
  layer            u16  model layer index
  block_index      u32  logical block within the request (kind 1), else 0
  offset           u64  byte offset of the segment in the source registered region
  length           u64
  crc32c           u32
  reserved         u32
```

- Attention KV segments hold one block of one layer in the canonical layout `[K | V]`, each `[block_tokens, kv_heads, head_dim]` row-major in `kv_format`, plus trailing scales for the FP8 formats; a partial final block carries `token_count mod block_tokens` valid rows and zero padding. The pool layout is identical on the HIP and CUDA backends (the Phase 2 layout kept by Phase 2b, CONFLICT C-23); pack/unpack is still implemented generically, so a future provider whose pool layout differs packs on send and unpacks on receive with a lossless permutation copy; the dtype is never changed by packing.
- The sampler-state segment holds the request's sampling parameters, PRNG state and the penalties' token-count table, so sampling after transfer continues the same random stream.
- A Phase 7 receiver rejects segment kinds 2 and 3 and a non-zero `state_layers` with `format_mismatch`.
- Conversion table (S-4, S-6), applied by the receiver only: identical formats → copy; `fp8_*` → `bf16` → exact upcast, allowed; `bf16` → `fp8_*` and `fp16` ↔ `bf16` → lossy, refused unless _distributed.kv_conversion.allow_lossy_. The sender never converts.

### RDMA transfer protocol (PD, decode pulls)

1. Ingress picks (prefill P, decode D) and asks D to **reserve** blocks for the projected prompt + max output; D answers `reserved{held_blocks}` (blocks it already holds from its prefix cache) or `refused{reason}`.
2. P runs prefill into its own pool, samples the first token, registers the request's regions `REMOTE_READ`, and sends D a **ready** message over the control channel: TKV1 header + segment table + `{rkey, remote base address}` per region.
3. D validates the header (magic, version, model_fp, formats, sizes against its reservation), posts RDMA READs straight into its reserved blocks (or into its bounce buffer, then copies), verifies each segment's crc32c, then sends **committed** to P and starts decoding.
4. P deregisters the regions and releases the blocks on **committed**, on **aborted**, or at _distributed.pd.transfer_timeout_; D releases its reservation on the same triggers.

Over TCP (M2 and every peer pair without RDMA) the same messages are used and the payload is streamed on the data connection in segment-table order. QP connection setup (GID, QPN, PSN exchange) runs once per peer pair over the control channel, not per request.

### Metrics

- `turbine_kv_network_transfer_bytes_total{transport,direction}` counter (phase-4 keeps `turbine_kv_transfer_bytes_total{path}` for tier copies, CONFLICT C-9) — `transport` ∈ {`rdma`, `tcp`, `local`}, `direction` ∈ {`send`, `receive`}.
- `turbine_kv_transfer_duration_seconds{transport}` histogram — ready → committed.
- `turbine_kv_transfers_inflight` gauge.
- `turbine_kv_transfer_failures_total{reason}` counter — `reason` ∈ {`timeout`, `checksum`, `transport_error`, `peer_lost`, `format_mismatch`, `reservation_refused`}.
- `turbine_kv_conversions_total{kind}` counter — `kind` ∈ {`copy`, `exact_upcast`, `lossy`}.
- `turbine_pd_requests_total{path}` counter — `path` ∈ {`disaggregated`, `short_prompt_local`, `fallback_colocate`, `fallback_recompute`, `rejected`}.
- `turbine_pipeline_stage_duration_seconds{stage}` histogram — `stage` is the stage index (bounded by config).
- `turbine_pipeline_bubble_ratio` gauge — fraction of stage-time idle over the last 10 s.
- `turbine_expert_rank_tokens_total{rank}` counter — tokens dispatched to each EP rank.
- `turbine_expert_imbalance_ratio` gauge — max / mean tokens per rank over the last 10 s.
- `turbine_ep_all_to_all_duration_seconds{phase}` histogram — `phase` ∈ {`dispatch`, `combine`}.

Per-expert counts are exposed only through `/turbine/v1/scheduler` (16 layers × 64 experts would already be 1,024 series, and later families have more).

### `turbine-bench` additions

```
turbine-bench --url <ingress> --profile prefill-heavy|decode-heavy [...Phase 0 flags]
turbine-bench compare --baseline <report.json> --candidate <report.json>
turbine-bench kv-transfer --peer <host:port> --transport rdma|tcp --bytes <size> --iterations <n>
```

- `prefill-heavy`: prompt 8,192 words, max tokens 128, concurrency 8. `decode-heavy`: prompt 256 words, max tokens 1,024, concurrency 32. Both are seeded like Phase 0 prompts. Both are run on Llama-3.2-3B (OLMoE's 4,096-token context is too short for `prefill-heavy`).
- `compare` prints per-metric deltas (ttft, itl, e2e p50/p95/p99, throughputs) and exits 0.

## Data

- **Transient only.** Transfers are in memory; nothing is persisted by this phase. Registered regions, reservations and in-flight transfer records live in process memory and are released on commit, abort or timeout.
- **Pipeline plan** (computed at load, logged once, exposed in `/turbine/v1/scheduler`): `[{stage, device_group, first_layer, last_layer, weight_bytes, est_cost}]`; owned by `turbine-distributed`.
- **Expert placement map** (computed or read at load): `layer → [rank; num_experts]`, owned by `turbine-distributed`; read-only after load.
- **KV directory entries** (owned by the Phase 6 directory in `turbine-kv`) gain `kv_format` and an optional `transfer {source, destination, bytes, deadline}`.
- **Capability records** (owned by `turbine-device`, consumed by `turbine-distributed`): per device `{vendor, arch, dtypes, kv_formats, execution_backend, collective_backend, rdma_devices}`, derived from the Phase 0 inventory plus runtime probes (kernel library loaded, collective library loaded, verbs devices).
- **Size guide** (from Constraints): an 8,192-token Llama-3.2-3B prompt moves 8,192 × 114,688 B = 896 MiB of BF16 KV — ~38 ms of wire time at the RoCE line rate (M1) and ~0.75 s over 10 GbE (M2), which is why S-7 costs the link.

## Edge cases

- Prompt shorter than one block, or exactly a multiple of _kv.block_tokens_ (no partial last block).
- Prompt below _distributed.pd.min_prompt_tokens_: served locally, no transfer.
- Request with `max_tokens: 1`: the prefill worker's first token is the whole answer; no transfer is started and the decode reservation is released.
- First token is EOS or hits a stop sequence on the prefill worker.
- Client cancels during prefill, during transfer (after **ready**, before **committed**), or during decode: every reservation, registration and block is released on both sides within one scheduler iteration plus the transfer abort round-trip (TS §21 rule 9).
- Prefix-cache hit on the decode worker for part of the prompt: only the missing blocks are transferred (the reservation names which blocks D already holds).
- Decode worker has the same prompt's KV in a different dtype: the directory treats it as a miss unless an exact upcast exists.
- Model fingerprint mismatch between P and D (different revision, KV dtype, or block size): transfer refused before any READ, reason `format_mismatch`. P and D with different _kv.block_tokens_ are refused already at PD pairing by the placement validator.
- Heterogeneous pair (M2): P's HIP pool and D's CUDA pool share the same layout (CONFLICT C-23); the transfer still goes through the canonical TKV1 layout, and packing and unpacking must be lossless (bit-identical round trip).
- Layer split with a stage of zero layers; `stages` greater than available device groups; a 7-stage split of 28 layers (4 layers each) versus an uneven explicit split.
- Expert count not divisible by _distributed.expert.parallel_size_ (64 experts, parallel size 3); a placement file missing an expert or naming a non-existent rank; all top-8 experts of a batch landing on one rank (imbalance saturates that rank's dispatch buffer).
- A batch where some EP rank receives zero tokens (it must still enter the collective).
- RDMA: device present but link down; GID index auto-detect finds no RoCE v2 IPv4 GID; memory registration fails for the pool (bounce path); READ returns a work-completion error; queue pair enters the error state mid-transfer; peer restarts and reuses an old QPN; a peer with no RDMA device (`novanas`) — TCP is chosen without error.
- Heterogeneous: an EP or TP group that would include both NVIDIA and AMD devices; PP boundary between vendors where one side lacks BF16; a worker whose kernel library failed to load (placed nowhere, logged).
- Clock skew between nodes (all deadlines are measured on the node that owns them, never compared across nodes).

## Failure modes

- **Verbs library missing or RDMA device absent with _distributed.transport.rdma.enabled_:** exit 1 at startup naming the library path or device. With rdma disabled, the TCP transport is used and a startup INFO names the reason.
- **RDMA connection to one peer fails at runtime:** that peer pair is marked `rdma_degraded` in the topology graph, transfers use TCP, `turbine_kv_transfer_failures_total{reason="transport_error"}` increments, reconnection is retried with exponential backoff capped at 30 s, never indefinitely without logging.
- **Transfer timeout or checksum failure:** D aborts, releases its reservation, P releases its blocks; the request takes the fallback path: D re-runs prefill locally on prompt + already-emitted first token (`fallback_recompute`, the TS §8 recompute tier); if D cannot admit that, P continues decoding (`fallback_colocate`) when _distributed.pd.fallback_ is `colocate`, else the request fails with 503 `kv_transfer_failed`. The client sees each token exactly once.
- **Lossy conversion needed but not allowed:** refused before any READ with `format_mismatch`; the pair is not used for that request and the router picks another decode worker or applies the fallback.
- **Decode reservation refused (pressure):** the router tries the next-best decode worker once; then applies _distributed.pd.fallback_. The refusal reason is logged with D's pressure state.
- **Prefill worker lost before ready:** ingress re-submits the request to another prefill worker if no token has been emitted; otherwise treats it as a transfer failure above.
- **Decode worker lost mid-generation:** ingress re-routes to another decode-capable worker, which recomputes KV from prompt + every emitted token and continues; the stream carries no duplicate tokens. If none is available the stream ends with `finish_reason: "error"` and an error event naming `worker_lost` (no transparent continuation claim, TS §12).
- **Pipeline stage lost:** every request with a micro-batch in the pipeline fails with 503 `pipeline_stage_lost`; the pipeline stops admitting (the worker's `/ready` turns false) until the stage returns, then warm-restarts; unaffected pools keep serving.
- **EP rank lost:** the EP group is unusable (every MoE layer needs every rank); treated like a stage loss for that group.
- **All-to-all or activation send exceeds 10× its p99 over the last minute:** logged as latency drift; feeds the Phase 3 circuit breaker for that group.
- **Placement impossible (model does not fit the declared stages/ranks, or a heterogeneous refusal):** exit 2 before binding, naming the devices, the strategy and the shortfall in bytes or the missing capability.
- **Lab host lacks the memory for a run:** `scripts/lab-pd.sh` exits 1 before starting anything; the implementer asks the user to free the host (Constraints).
