Amendments to earlier specs made by this phase:

- Amends Phase 4 S-1 ("Only full blocks are keyed and shareable") and S-3 ("matched full blocks are attached"): full blocks stay the only keyed, tiered and shared-by-reference unit; in addition a request may reuse a token-granular prefix of one more L0 block (a cached partial tail or a partially matching full block) through a private copy (copy-on-write, S-4, S-5). The Phase 4 edge case "prompt shorter than one block (no sharing)" no longer holds for L0: such a prompt can reuse a partial tail.
- Amends Phase 4 S-3's report: `usage.prompt_tokens_details.cached_tokens` and `ResourceEstimate.cached_prefix_tokens` are token-granular, no longer a multiple of _kv.block_tokens_.
- Amends Phase 2m S-9 (`AdmissionInfo`): the admission information a scheduling policy sees gains the prompt length, the attached cached-prefix length and the policy window (S-7).
- Amends Phase 2 §Scheduling rules rule 2 ("one token each"): a decoding sequence whose grammar forces tokens may append more than one token in an iteration (S-9, S-10).

## Problem

After the pre-Phase-5 performance track and Phase 5, Turbine serves Llama-3.2-3B at about 855 output tok/s and OLMoE-1B-7B at about 613 on one R9700 (novanas GPU 0, the `lab-bench.sh` workload; main close-out 2026-09-28: Llama 855.2, ITL p50 15.4 ms, TTFT p50 208 ms; OLMoE 613.9, 24.3 ms, 118 ms), and the Phase 4 multi-turn profile reaches a cached-token ratio of 0.907 with a later-turn TTFT p50 of 76 ms. Comparing vLLM and SGLang showed four SGLang ideas Turbine lacks. (1) Prefixes are shared only in whole 128-token blocks: a request whose cached prefix ends inside a block recomputes up to 127 tokens that another request already computed, and the Phase 4 planner's two-token minimum (`MIN_RECOMPUTE_TOKENS`) makes a prompt one token past a block boundary recompute the whole 129-token tail. In the multi-turn profile every later turn loses on average about half a block of the previous turn's tail. (2) The admission order of waiting requests ignores the cache: under saturation a request whose prompt is almost entirely cached waits behind uncached ones while its cached blocks may be reclaimed. (3) Structured output decodes one token per forward even where llguidance already knows the next bytes (`{"name":"`, `","age":` …), so JSON-schema requests spend a full decode step on every forced token. (4) The engine's host work between two forwards is known at c16 (≈ 0.29 ms of a 17.5 ms Llama decode step, 1.5 %; the GPU idles ≈ 0.38 ms per step, `.procoder/perf-profile-2026-09-27.md`), but not at c1, where steps are shorter and an SGLang-style overlap scheduler would matter most; Turbine already has overlap scheduling (Phase 2c S-16), off by default because it moved OLMoE's TTFT from 403 to 635 ms. The decision orders the work: measure the host share first, then token-granular prefix reuse, then a cache-aware scheduling policy, then jump-forward structured output, each landed alone and measured.

## Users

- **API clients running multi-turn chat, agents and shared system prompts:** need later turns to reuse every token of the cached prefix, not only whole blocks, with outputs identical to a cold run, and lower TTFT under load.
- **API clients requesting JSON-schema or tool-call output:** need lower latency per structured response with the same output as token-by-token decoding.
- **Operators:** need a registered, selectable cache-aware scheduling policy with a stated starvation bound, metrics that show partial-block reuse, jump-forward acceptance and the host share of a step, and a switch per optimisation to bisect a regression.
- **Turbine developers:** need each item behind host tests and a deterministic simulator test, the lab measurement procedure extended to c1, the host share and the multi-turn profile, and a record of the before/after numbers per landing step ("one change, then measure").
- **Phase 6–8:** need the partial-block path to stay L0-only so KV formats and hybrid recurrent state (Phase 7 caches it only at block boundaries) are not affected, and the multi-token append of S-9 to be reusable by speculative decoding (Phase 8).

## In scope

- [S-1] Host-share measurement tooling: a `turbine-bench stage-share --before <metrics.txt> --after <metrics.txt> [--output text|json]` subcommand reads two Prometheus scrapes of `turbine_engine_iteration_seconds{stage}` and reports, over the iterations between them, the seconds per stage, the iteration count and `host_share` = Σ seconds of every stage except `device_wait` ÷ Σ seconds of all eight stages (the `launch` stage counts as host time: it includes the blocking graph launch, during which the GPU idles). `scripts/lab-bench.sh` gains `--concurrency <n>` (the throughput bench's concurrency, default 16, unchanged workload otherwise), computes `host_share` with the subcommand from its existing before/after scrapes and prints it on the `BENCH` line (`host_share=<0.0000>`), and gains `--multi-turn` (after the throughput bench, the Phase 4 profile `--profile multi-turn --sessions 16 --turns 8 --shared-prefix-words 2000 --concurrency 8 --session-hints`) and `--multi-turn-sessions <n>` (the same profile with `--sessions <n> --concurrency <n>`, the saturated variant), each adding `mt_cached=<ratio> mt_ttft_first_p50=<ms> mt_ttft_first_p99=<ms> mt_ttft_later_p50=<ms> mt_tok_s=<tok/s>` to the line, and `--dry-run` (prints every command it would run on the host and the workstation, contacts nothing, exits 0), so the flag plumbing is tested without a GPU.
- [S-2] The measurement landing (the decision's item 4, first): on novanas GPU 0 with the main tip after Phase 5, `lab-bench.sh` at `--concurrency 1 --quick` and at the default c16 for Llama and OLMoE (four `host_share` values), plus the multi-turn baselines for items 2 and 3 (standard and saturated, Llama). The numbers go into `.procoder/perf-log.md` and a decisions entry. Rule from the decision: overlap scheduling work (S-3) is built only if the host share at c1 exceeds 0.05 for either model; otherwise S-3 is closed with the measurement as evidence and no code change.
- [S-3] Conditional: overlap scheduling without the TTFT penalty (perf-profile candidate #6). Built only under the S-2 rule. The engine launches iteration N+1 ahead (Phase 2c S-16) only while no admitted request is waiting for its first prefill chunk; when one is, the turn runs serially so the new request joins the next plan at once; when the A/B on `lab-bench.sh` (both models, c1 and c16) shows higher throughput and TTFT p50 ≤ 1.10 × the serial run, _execution.overlap_scheduling_ defaults to `true`, else it stays `false` with the numbers recorded.
- [S-4] Token-granular prefix match (the decision's item 1, part 1) in `turbine-kv`. The directory keeps, next to the keyed full blocks, **partial entries**: an L0 block holding fewer than _kv.block_tokens_ tokens whose KV is written, stored under the key `block_key(ns, parent, tail tokens)` with its token ids, its parent the last full block of the sequence (or `ROOT_PARENT` for a sequence shorter than one block). `KvDirectory::lookup` still walks full blocks with `chunks_exact`; where the walk stops (first missing key, or the end of the prompt's full blocks), it compares the remaining prompt tokens token by token with the stored tokens of the L0-resident children of the last matched key — full blocks and partial entries — and returns the longest common prefix (`PrefixMatch.partial: Option<PartialMatch { key, block, tokens }>`). At most `PARTIAL_SCAN_LIMIT` = 64 children are compared per lookup (most recently used first) and at most `PARTIAL_PER_PARENT` = 8 partial entries are kept per parent (least recently used dropped). Token ids are compared, so a hash collision can never return another sequence's KV.
- [S-5] Copy-on-write attach and publication (item 1, part 2). `KvHierarchy::attach_prefix` attaches the reused full blocks by reference as in Phase 4 and, when the planner reuses every matched full block up to the partial match's parent and the match has at least one token, allocates one private L0 block and asks for a copy of the matched block into it (`PrefixAttach.tail_copy: Option<TailCopy { src, dst, tokens }>`; the request holds a reference to `src` until the copy's iteration has completed). The planner's cap becomes token-granular: reuse covers at most `prompt − MIN_RECOMPUTE_TOKENS` tokens (still 2, decision "Pre-Phase-5 #1 follow-up (A)"), so a prompt one token past a block boundary recomputes 2 tokens instead of 129; `cached_tokens` = full blocks × _kv.block_tokens_ + partial tokens. The scheduler plans the copy in the request's first iteration (`IterationPlan.tail_copies`), executed with the fork copies before the forward through `ModelExecutor::copy_blocks`; the request's block table is the shared full blocks followed by the private copy, and its prefill starts at `cached_tokens`, mid-block. The private block is covered by the request's reservation like any block it writes (the reservation excludes only the full blocks attached by reference). When a request finishes (stop, EOS, length; not a cancellation or failure), choice 0's last block, if partial, is published as a partial entry holding the tokens whose KV is written (prompt plus generated tokens minus the newest, never-fed token). Partial entries are L0-only (the decision's constraint: L1/L2 hold full blocks): they are never demoted, prefetched or promoted, `has_reuse_evidence` is false for them, and a reclaim drops them (reason `partial_l0_only`); a full block that exists only in L1/L2 is never used for a partial match. _kv.partial_prefix_reuse_ switches S-4 and S-5 off (A/B), restoring Phase 4 exactly.
- [S-6] Multi-GPU (Phase 5) under S-5: block ids are logical and every rank's pool has the same block count, so a tail copy is one `(src, dst)` pair executed on every rank: through `TpExecutor::copy_blocks` (local mode: rank 0 plus every `WorkerRank` via a copies-only `StepPlan`) and in static mode through the `StepPlan.copies` the workers apply before their forward — the same path the n > 1 fork copies take; EP groups use the same `TpExecutor`; each DP replica has its own directory and partial entries; pipeline stages (refused by the server in Phase 5) would copy on every stage's pool. The partial entry and its token ids live only in the leader's directory. The TP golden gate and `kv_gpu` prefix reuse at tp 2 stay bit-exact with the Phase 5 Task 29 invariant rows.
- [S-7] Cache-aware scheduling policy (the decision's item 2) `cache_aware`, one file `crates/turbine-scheduler/src/policy/cache_aware.rs` registered in the `scheduling_policy` registry after `default`, selected by `scheduler.policy: cache_aware`. `AdmissionInfo` gains `prompt_tokens`, `cached_prefix_tokens` (the prefix attached before the admission gate, Phase 4 decision "prefix attach before the admission gate", so the attached blocks cannot be reclaimed while the request waits) and `window` (from _scheduler.cache_aware_window_); `AdmissionKey` gains `affinity: u64` between `arrival` and `order` (the default policy sets 0, so its order is unchanged). Key (user decision 2026-09-28): preempted requests exactly as `default`; others `tier 1, priority, arrival = the start of the request's arrival window (⌊arrival / window⌋ × window), affinity = u32::MAX − cached_prefix_tokens, order = submit_no` — within one window and one priority the longest cached prefix goes first, windows and priorities keep their order. Starvation bound: a waiting request is never admitted after an equal-priority, never-preempted request that arrived at least one `window` later. The policy is stateless and clock-free like every scheduling policy; the victim choice and chunk cap are `default`'s. `default` stays the default policy in this phase (user decision 2026-09-28); the lab A/B of S-13 is recorded for the user's decision.
- [S-8] Policy tests and docs: the Phase 2m conformance suite (`decode_never_starved`, `chunk_budget`, `preemption_by_recompute`) runs over `cache_aware` through `registry_conformance`; a deterministic simulator test drives a saturated workload with a continuous flood of fully cached requests and interleaved uncached ones through the real scheduler, gate and `KvHierarchy` (`KvSimDriver`) and checks the starvation bound for every pair, that every request completes, and that a test-only unbounded variant (window ∞) does starve the uncached requests (the test catches a missing bound); `docs/extending/scheduling-policy.md` gains `cache_aware` as the registered example, the new `AdmissionInfo` fields and the pitfall "the key is computed once at push".
- [S-9] Multi-token append for a running sequence (enabler of S-10): `Scheduler::extend(seq, tokens)` asks the next plan to feed `1 + tokens` tokens of a decoding sequence in one item (`BatchKind::Prefill { start, len }` over its own positions, taken from the iteration's token budget after the decodes and before prefill chunks, at most _structured_output.jump_forward_max_tokens_ + 1, falling back to a plain decode when the budget or the pool cannot cover it); `IterationOutcome` gains `rolled_back: Vec<(SeqId, u32)>` so `complete` shortens a sequence's table by the rejected tokens and frees blocks left empty; the engine's KV commits (`kv_commits`) publish only blocks completed by kept tokens. `SeqSlice` gains `logits_rows: u32` (default 1: the last position, as today): the executor returns full logits rows for the last `logits_rows` positions of that sequence (never device-reduced), in position order; under TP the leader's executor returns them.
- [S-10] Jump-forward structured output (the decision's item 3). After a constrained choice samples and commits a token, the engine asks its matcher for llguidance's forced tokens (`TokenMatcher::forced_tokens`, over `Matcher::compute_ff_tokens`, which re-tokenizes the last committed token together with the forced bytes and chops trailing tokens that could merge with what follows, so an emitted token is never rewritten), capped by _structured_output.jump_forward_max_tokens_, `max_tokens` and `model.max_seq_len`. With k ≥ 1 forced tokens the next iteration feeds the sampled token plus the k forced tokens in one chunked-prefill item with `logits_rows = k + 1`. Verification (user decision 2026-09-28): the forced tokens are a draft checked against the model — row j's logits go through the choice's normal step (mask, logits processors, sampler with its own uniform, logprobs) exactly as a token-by-token step would; while the sampled token equals forced token j+1 it is accepted and committed; at the first disagreement the model's own token is taken, the remaining forced tokens are rolled back (S-9) and the matcher and detokenizer never saw them; when all k are accepted, row k yields the next token. Greedy and seeded outputs are therefore the token-by-token outputs up to the rounding difference between a prefill-shaped and a decode-shaped step (the same bound the golden gate already applies to batch composition). Stop strings, EOS, `max_tokens` and tool-call parsing see accepted tokens one at a time in order. Requests without a grammar, and choices with `n` > 1 beyond choice 0's first token, are unaffected; overlap scheduling already finishes a constrained step serially (Phase 2c S-16), so a jump-forward step is never launched ahead. _structured_output.jump_forward_ switches it off.
- [S-11] Configuration additions (under Interfaces), validated at startup and settable with `--set`: _kv.partial_prefix_reuse_, _scheduler.cache_aware_window_, _structured_output.jump_forward_, _structured_output.jump_forward_max_tokens_; _execution.overlap_scheduling_'s default changes only under S-3.
- [S-12] Metrics, log events and diagnostics under Interfaces: partial-block reuse counters, jump-forward token counters, the KV document's `partial_entries`, `/turbine/v1/status` `modules.scheduling_policy` naming `cache_aware` when chosen.
- [S-13] Lab acceptance and performance targets per landing step under the test tiers of AGENTS.md, with the rule "one change, then measure" (Interfaces, "Performance targets").

## Out of scope

- Moving partial blocks to L1/L2, prefetching them, or keying tiers below L0 by token; partial reuse of blocks that are only in L1/L2 (they are full blocks; the decision allows "L0-only or copied whole", this phase takes L0-only).
- A radix tree replacing the Phase 4 directory: the directory keeps its full-block hash chain; only the last block is matched token by token.
- Hybrid recurrent-state caching (Phase 7 caches it at block boundaries only) and quantized KV (Phase 6); partial reuse must not block either, nothing more.
- Speculative decoding (Phase 8): S-9's multi-token append and S-10's verification are its building blocks, not a proposer.
- Jump-forward for `n` > 1 choices after the first token, for requests with `logit_bias`-only constraints, and across a tool-call grammar's free-text section (only the grammar's forced bytes are jumped).
- A new overlap scheduler design beyond S-3's rule (S-3 is conditional; no overlap work when the c1 host share is ≤ 0.05).
- Making `cache_aware` the default policy, and changing the DP router (`prefix_affinity`) — the router already sends a session to the replica holding its prefix.
- New kernels: the tail copy uses the existing `copy_blocks` op, the extended item the existing chunked-prefill path; no kernel ABI change.
- NVIDIA, multi-node and pipeline-parallel serving (held or refused, decision 2026-09-26 and Phase 5).

## Constraints

- Order and landing (decision "Phase 5p"): S-1/S-2 (measure) first, then S-3 only under its rule, then S-4–S-6, then S-7–S-8, then S-9–S-10. Each item lands alone and is measured before the next: `scripts/lab-bench.sh` with golden c1 and the throughput bench per landing step; for S-4–S-8 also the multi-turn profile before and after (`--multi-turn`, and `--multi-turn-sessions 64` for S-7); for S-10 the JSON-schema golden of Interfaces.
- Test tiers (AGENTS.md "Test tiers", decision 2026-09-27): per landing step `scripts/gate.sh`, plus `scripts/lab-test.sh novanas --tier quick` when the change touches GPU-facing code (`turbine-model` for S-9, the `kv_gpu` lab tests for S-5/S-6), plus `scripts/lab-bench.sh --quick` for an iteration read and the full 200-request `scripts/lab-bench.sh` for the landing number; phase exit: `scripts/gate.sh --full`, `scripts/lab-test.sh novanas --tier full`, `scripts/lab-bench.sh --golden16` for both models and the 10-minute `scripts/overload-soak.sh novanas --duration 10m`.
- Prefix-exact prefill invariance (decisions "Pre-Phase-5 #1 follow-up" and "(A)"): a warm request that reuses a token-granular prefix produces bit-identical tokens and logprobs to the cold run of the same prompt when the reused KV was written by a prefill (the Phase 4 `kv_gpu` rule); Llama's prefill steps keep the invariant GEMM rows, the planner keeps `MIN_RECOMPUTE_TOKENS` = 2, and a warm prefill that starts mid-block must stay prefill-shaped. KV written by decode steps (a previous turn's generated tokens) is reused as in Phase 4: identical within the golden tolerance, not bitwise, because decode steps use the speed-tuned rows.
- KV tiers (decision constraint): L1 and L2 hold full blocks only; a partial entry never leaves L0; the Phase 4 reuse-evidence gates, `DEMOTION_INFLIGHT` and capacity demotion are unchanged for full blocks.
- Correctness bar unchanged: the golden tolerances of `tests/golden/<slug>/tolerance.json` (strict at concurrency 1, batched bounds at 16), the OLMoE calibration, the `kv_gpu` bit-exact prefix checks, the Phase 3 reservations (a tail copy's block is reserved; a shared block is never written) and cancellation releasing every reference within one iteration.
- Scheduling policies are stateless, clock-free and deterministic (Phase 2m); every scheduler change is covered by the deterministic simulator (TS §17) with no GPU.
- Bounded everything (TS §21 rule 8): children compared per lookup (64), partial entries per parent (8), partial entries in total (they are L0 blocks, reclaimed like cached blocks), forced tokens per step (_structured_output.jump_forward_max_tokens_ ≤ 256), logits rows per step (≤ max_batch_tokens).
- Every automatic decision exposes a reason code and a metric (TS §21 rule 7): partial reuse outcomes, jump-forward accept/reject, policy selection (`module_selected`).
- Phase 5 (merged before this phase starts): every item works at tp 1, TP (local and static rank modes), EP and DP as S-6 states; lab checks at tp 2 run through `scripts/lab-cluster.sh tp2-novanas` (both R9700s, under `scripts/bench-lock.sh`) at phase exit, not per landing step.
- Unsafe Rust and FFI stay in `crates/turbine-kernels/src`; `turbine-kv` and `turbine-scheduler` gain no GPU or model dependency; no new external dependency (llguidance 1.8.0 already provides `compute_ff_tokens`); no vendor GPU crate.
- Lab: novanas only, GPU 0 for every throughput, golden and multi-turn number (GPU 1 is not comparable), native runs under `scripts/bench-lock.sh`; the standing novanas approvals (2026-09-25/26) cover `lab-test.sh`, `lab-serve.sh` and the golden/bench runs; if `amd.com/gpu` is held by another workload, stop and ask the user; soaks are asked for first.
- Every run is recorded: `lab-bench.sh` uploads to labbook (set `phase-5p`), and each landing step adds a row to `.procoder/perf-log.md`.

### Performance targets (measured on novanas GPU 0, `lab-bench.sh`, median of 3 runs where stated)

## Edge cases

- Prompt equal to a cached sequence plus one token: reuse `prompt − 2` tokens (partial tail copy), prefill 2 tokens; prompt exactly a cached partial entry: reuse `prompt − 2`.
- Prompt shorter than one block that matches a short cached sequence (a partial entry under `ROOT_PARENT`): tail copy of that block, prefill from the match.
- Divergence inside a full block (the previous turn's text re-tokenized differently near the end): the full child is compared token by token and its matching prefix is copied; the rest of the copied block is overwritten by the prefill (attention reads `kv_len` tokens only).
- The best candidate lives only in L1/L2, or is being promoted: no partial reuse (`not_resident`); the full-block plan proceeds as in Phase 4.
- The planner cuts the full-block prefix earlier (recompute cheaper, L0 pressure): no partial reuse (`planner_cutoff`).
- The source block is reclaimed or its entry replaced after attach: impossible before the copy — the request holds a reference to `src` until the copy's iteration completes; a request cancelled, timed out, circuit-rejected or SURVIVAL-requeued before its first iteration drops both `src` and `dst` (and clears its prefix, as in Phase 4).
- Two requests copying the same source in one iteration: two pairs, one source, two private blocks.
- Two requests with the same new short prompt arriving together: the second finds no partial entry (the first publishes at its finish) and computes its own; pending-wait applies only to full blocks.
- Fork (`n` > 1) after a partial reuse: the fork copies choice 0's private tail as today.
- A request finishing with its last block exactly full: that block is already published as a full block; nothing partial is published. A cancelled or failed request publishes nothing partial.
- More than 8 partial entries under one parent (many sessions branching from one system prompt): least recently used dropped; lookups compare at most 64 children.
- Phase 5 static rank mode: a worker receives the copy in the step's `StepPlan.copies` before its forward; a worker lost mid-copy fails the step as in Phase 5 (`RankStopped`).
- Cache-aware: all waiting requests uncached (policy orders like `default` within a window: affinity equal, then submit order); a preempted request (tier 0, as `default`); a request whose prefix is still promoting is held before the gate as in Phase 4 and keyed when it is submitted; a window of 10 ms (almost `default`) and 60 s.
- Jump-forward: forced span ending the JSON (EOS allowed after it); forced tokens crossing `max_tokens` (capped); a stop string completed inside the forced span (the tokens after it are dropped as with token-by-token stop handling); forced tokens when the choice asks for `top_logprobs` (every accepted row reports its own logprobs from its row); a forced span whose canonical tokenization differs from the model's greedy choice (rejected at that token, the model's token taken); the budget cannot fit the span (plain decode, forced tokens recomputed next step); preemption of a sequence with a pending extension (the extension is dropped; recompute re-prefills prompt + generated).
- Host share: a scrape pair with no iteration between them (`stage-share` exit 2); c1 with 64 requests (`--quick`, the minimum that gives a stable c1 share).

## Failure modes

- **Tail copy fails on the device:** the iteration fails as a Phase 2 failed iteration (its requests end with `internal_error`; three in a row stop the engine); under TP the collective/rank failure path of Phase 5 applies.
- **Directory inconsistency (a partial entry points at a reclaimed block):** the entry is removed, the lookup is `no_candidate`, an error is logged with the key; debug builds assert (Phase 4 rule).
- **llguidance returns forced tokens the mask then rejects, or `compute_ff_tokens` errors:** jump-forward is skipped for that step (no forced tokens), logged at DEBUG; the request continues token by token.
- **A rejected forced token leaves the matcher inconsistent:** impossible by construction — the matcher is only told accepted tokens; a matcher error after an accepted token fails that choice with the existing "constrained decoding failed" path.
- **Logits rows exceed the executor's workspace:** `logits_rows` is bounded by `q_len` and the step's rows by `max_batch_tokens`, which the Phase 2 workspace already covers; a startup check refuses a configuration where _structured_output.jump_forward_max_tokens_ + 1 > _scheduler.max_batch_tokens_ (exit 2).
- **An unknown `scheduler.policy`:** exit 2 before bind naming the registered policies (Phase 2m).
- **Regression at a landing step:** the landing is reverted or the item's switch set to false in the lab config; the numbers stay in the perf log.
