# phase-2m-modularity

Status: complete

Source: user decisions 2026-09-26 ("before we continue with Phase 3, make our existing code follow our modularity rules"), the AGENTS.md pluggability rule, GitHub issues piwi3910/Turbine #1 (model families), #2 (prompt and tool-call formats), #3 (backends, card families, kernel providers), #4 (quantization formats — BF16 module only) and #6 (logits processors and scheduling policies). Decisions and options: `.procoder/ask/decisions.md` ("Modularity refactor before Phase 3", "Phase 2m modularity: design choices"). Builds on `phase-2-serving-runtime` and `phase-2c-performance` as merged to main (9ce3ba4); merges the Phase 8 run-ahead registry work from `runahead/p8-umbrella`.

## Problem

Turbine's architecture promise is that models, formats, backends, cards and kernels are swappable modules, but the code on main does not keep it. The survey of 2026-09-26 found per-op kernel traits and a few other traits at the bottom, but every place that picks an implementation is a hand-written `match` or `if`: a closed `Architecture { Llama, Olmoe }` enum branched on in config parsing, the loader, three executor dispatch functions and the server; two executors (crates/turbine-model/src/executor/llama.rs and olmoe.rs) that are 55–60% copy-paste; the Llama-3 tool format wired through a closed config enum, the server backend and a heuristic inside the engine; the choice between hipBLASLt, Composable Kernel and Turbine HIP kernels made inside the C++ library where Rust sees only an implementation string; gfx1201-only thresholds and a gfx1201-only CMake build; a sampler whose processing order and device fast path are hand-coded twice; a scheduler whose policy (admission order, victim choice, chunk sizing) is fused with its mechanism; and BF16 implied in about 70 places. Every next step — Phase 3 onward, new families (Phase 8), new cards, quantization — would add another branch to each of these places. The user wants the existing code brought in line now, before Phase 3, so that each later addition is a new file plus a registry entry.

## Users

- **Turbine developers (humans and AI agents):** adding a model family, a tool-call format, a weight format, a kernel implementation, a card family, a logits processor or a scheduling policy means adding one file (or directory) and one registry entry, following a how-to, with a conformance test suite that tells them whether the new module is correct.
- **Operators:** unchanged behaviour and configuration for the models served today; clearer startup refusal (with a reason code) when a model × format × device combination is unsupported; the selected module for every extension point visible in logs, `/turbine/v1/status` and metrics.
- **Reviewers:** every slice of the refactor proves no behaviour change (host tests, lab golden c1 and c16, GPU suites) and no throughput regression (lab-bench within 3%).

## In scope

- [S-1] Registry pattern: one shared convention for every extension point — a trait, one file (or directory) per implementation, and a static registry (a `&'static [&'static dyn Trait]` or equivalent list built at compile time) with lookup by name, enumeration for diagnostics and a startup log line naming the module picked and why. No runtime plugin loading except the kernel libraries.
- [S-2] Model families (issue #1): `turbine-model/src/families/` with one file per family (llama.rs, olmoe.rs, and from the Phase 8 run-ahead qwen3.rs, qwen3_moe.rs, mistral.rs, mixtral.rs). A `ModelFamily` trait owns: the Hugging Face architecture names it accepts, `config.json` parsing and validation into its family config, weight slots, requirements and workspace sizing, the default prompt/tool format and chat-template quirks, and construction of its executor. The closed `Architecture` enum and every `match` on it outside the registry go away; the server resolves the family through the registry.
- [S-3] Shared decoder skeleton: one executor skeleton in `turbine-model/src/executor/` (buffers, embedding, per-layer attention with RoPE and paged KV, residual + norm, final norm, lm_head including tied weights, logits reduction, profiling, tracing, decode graphs, launch/collect) with per-family hooks for the attention variant (e.g. OLMoE Q/K RMSNorm, Qwen3 per-head Q/K norm) and the FFN variant (dense SwiGLU, MoE with its routing and workspace). executors in crates/turbine-model/src/executor/llama.rs and olmoe.rs are replaced by the skeleton plus their hooks; tracing (`set_trace`) works for every family.
- [S-4] Prompt and tool-call formats (issue #2): `turbine-model/src/formats/` with one file per format (llama3_json.rs, and from the Phase 8 run-ahead hermes.rs, mistral.rs). A `ToolFormat` trait owns: tool rendering when the chat template does not, the constrained grammar for `tool_choice` required / named / auto, the streaming parser into `tool_calls`, the special tokens it needs from the tokenizer, and the auto-mode "output opens like a call" test (moved out of `engine/requests.rs`). _model.tool_call_parser_ becomes an open name validated against the format registry (values accepted today keep working); a family declares its default format.
- [S-5] Kernel implementations selected in Rust (issue #3): kernel ABI minor version adds per-op implementation enumeration and explicit selection. The library reports, for each op, the implementations it contains (name, provider family such as `hipblaslt` / `ck` / `turbine_hip`, and a supports query per op config); the Rust `KernelRegistry` chooses one implementation per op config with reason codes and passes the choice on each call (or binds it once per shape). The C++ library no longer chooses between implementations internally; implementations stay in one library per backend. The CPU reference provider is split into one file per op family.
- [S-6] Card profiles (issue #3): `turbine-kernels/src/cards/` with one declarative Rust profile per card family (gfx1201.rs first): capabilities (matrix instructions, BF16 support, wave size, LDS size), tuned thresholds (e.g. MoE small-m / grouped cut-offs, paged-attention page multiple), preferred implementation order per op and autotune seed. The profile is chosen from the discovered device, passed to the library at context creation, and used by the registry's selection. `kernels/rocm/CMakeLists.txt` builds the architectures the profiles list instead of refusing everything but gfx1201.
- [S-7] Backends (issue #3): an `ExecutionBackend` trait with one file per backend (`cpu`, `hip`) covering library loading, device matching and the provider(s) it contributes; _execution.backend_ names a registered backend. The `match` arms in `turbine-server/src/model.rs` (`load_provider`, `amd_device`, `paged_attention_fallback`) and vendor error strings outside the kernels/device crates (`STICKY_DEVICE_ERRORS`) move behind the backend. Device discovery backends are registered the same way.
- [S-8] Logits processors (issue #6): a `LogitsProcessor` trait with one file per processor (logit bias, repetition penalty, presence/frequency penalty, `min_tokens` EOS ban, grammar mask) applied as an ordered chain; each processor declares whether it can run on the device and whether it needs the full vocabulary row, and the device fast-path eligibility is derived from the chain instead of a hand-written conjunction. Sampling steps (temperature, top-k, top-p, greedy) keep their current order. Logprob "originals" are tracked through a shared touched-ids record.
- [S-9] Scheduling policy (issue #6): a `SchedulingPolicy` trait in `turbine-scheduler` owning admission order (today `(priority, arrival)` plus preempted-first), preemption victim choice (today lowest priority, most recent), and chunk sizing (today `chunk_cap`); the stage order of `plan()` (drop cancelled → decode → forks → continuing prefills → admit) and the block accounting stay mechanism. The current behaviour is the `default` policy; _scheduler.policy_ selects a registered policy. The simulator runs any registered policy.
- [S-10] Weight format module (issue #4, BF16 only): a `WeightFormat` trait with bf16.rs as its only implementation, owning dtype detection from the checkpoint (`torch_dtype`, refusal of `quantization_config`), weight byte sizing and the dtype handed to loader, executor op configs and the KV layout. The hard-coded `DType::BF16` sites in config, loader and executors read the format instead. No new dtype or quantized kernel.
- [S-11] Phase 8 run-ahead merge: bring in from `runahead/p8-umbrella` the architecture registry and the Qwen3, Qwen3-MoE, Mistral and Mixtral families (CPU execution), the Hermes and Mistral tool formats and the family chat-template fixtures from that branch, the support matrix (`(vendor, arch, architecture, weight_format, kv_format, speculative_method) → supported | experimental | unsupported{reason}`) with most-specific-row resolution, `--support-matrix` / `--check-config` reporting, startup refusal of unsupported rows with a reason code, and the guard test against vendor-specific types in core public signatures — each reshaped onto S-1…S-10. The Phase 8 families stay refused on GPU backends (support-matrix rows) until their Phase 8 track closes.
- [S-12] How-tos: `docs/extending/` with one page per extension point (model family, tool format, weight format, kernel implementation, card family, backend, logits processor, scheduling policy) listing exactly which files to add, which registry entry to add, and which conformance tests must pass.
- [S-13] Conformance suites: one shared test suite per extension point that every registered implementation must pass — families (tiny-checkpoint CPU vs naive reference, batching/chunking/paged equivalence, fused vs unfused), tool formats (render, grammar, parse, round trip through the constrained sampler), kernel implementations (each implementation vs the CPU reference on the lab), logits processors (host vs device path equivalence where both exist), scheduling policies (simulator invariants: decode never starved, chunk budget respected, preemption by recompute).
- [S-14] Proof of no change: every slice lands with the host workspace tests, the relevant GPU lab suites, the served golden gate for both Llama and OLMoE (c1 strict, c16 batched) and `scripts/lab-bench.sh` on GPU 0 for both models, each within 3% of the previous step's throughput and TTFT p50 within 10%; results logged in `.procoder/perf-log.md`.

## Out of scope

- New model families, tool formats or kernels beyond what main and `runahead/p8-umbrella` already contain; running the Phase 8 families on a GPU (their support-matrix rows stay unsupported on GPU vendors).
- New dtypes, quantized formats or quantized kernels (issue #4 beyond the BF16 module), and speculative decoding or a speculative seam (issue #5).
- KV eviction policies (no eviction exists yet; Phase 4 adds `EvictionPolicy` following S-1), collectives and transports (Phases 5–7 already specify traits).
- The Phase 8 eval gate (`turbine-golden eval`, the GSM8K-200 set), the Phase 8 track start gate script, and the `quality.max_accuracy_drop` / `speculative.method` config keys from `runahead/p8-umbrella` beyond what the support matrix needs — they stay for Phase 8.
- Splitting the HIP library into one shared library per provider (rejected option), data-file card profiles (rejected option), CUDA / NVIDIA work (on hold).
- Porting the parked run-ahead branches for Phases 3–7; each is ported onto the new layout when its phase starts.
- Any change to the OpenAI API, the served outputs, or the defaults of existing configuration keys.

## Constraints

- No behaviour change for the models served today: greedy outputs, logprobs and tool/JSON outputs identical on the host test suites; served golden c1 strict and c16 batched pass for Llama and OLMoE; seeded sampling streams bit-identical (`crates/turbine-model/src/sampler.rs` seeded-stream tests, `tiny_server` seeded requests).
- No performance regression: `scripts/lab-bench.sh` on novanas GPU 0 per slice, Llama ≥ 747 tok/s and OLMoE ≥ 601 tok/s (97% of 770.4 / 619.8), TTFT p50 within 10% of 195 / 134 ms. Registry lookups happen at startup or once per shape, never per token.
- Engineering rules (AGENTS.md) stay binding: unsafe/FFI isolated in turbine-kernels (and turbine-device for discovery), no vendor GPU crate in the dependency tree, scheduler testable without GPUs, bounded queues, no micro-crates without an ownership boundary — modules live inside the existing crates (decision 2026-09-26).
- Kernel ABI: additive only, as a new optional minor group; a library without it still loads and the Rust side falls back to asking the library's default implementation (today's behaviour); `tests/abi_header_neutral.rs` keeps the header vendor-neutral.
- Configuration compatibility: every configuration file that loads on main today loads unchanged with the same meaning (`examples/turbine.yaml`, `scripts/lab/*.yaml`, test configs).
- Builds and tests run on novanas (`scripts/remote-cargo.sh`, `scripts/lab-test.sh`), never on the workstation; lab runs under the standing Phase 2 / 2c approval.
- Landing: one slice at a time on a branch, measured before the next lands (user feedback: land one change, then measure); parallel agents only for independent slices in separate worktrees.

- `turbine_model::formats::{ToolFormat, FormatRegistry, registry()}` — `ToolFormat::{name, special_tokens, render_tools, grammar(tool_choice, tools), parser() -> Box<dyn ToolCallParser>, opens_like_call(&str, token)}`.
- `turbine_model::weights::{WeightFormat, registry()}` with `bf16`.
- `turbine_model::sampling::{LogitsProcessor, ProcessorChain}` — `LogitsProcessor::{name, applies(&SamplingParams), device_capable, needs_full_row, apply(&mut [f32], &mut Touched, &State)}`.
- `turbine_scheduler::policy::{SchedulingPolicy, registry()}` with `default` — `admission_key`, `pick_victim`, `chunk_cap`.
- `turbine_kernels::cards::{CardProfile, registry(), profile_for(&DeviceInfo)}`; `turbine_kernels::backends::{ExecutionBackend, registry()}` with `cpu`, `hip`; `KernelRegistry` selection reports `(op, implementation, provider, reason)`.
- `turbine_core::support::{SupportMatrix, SupportRow, Support}` (from the Phase 8 run-ahead).

Kernel C ABI (new optional minor group, e.g. v2.4 "implementations"): `turbine_impl_count(op)`, `turbine_impl_info(op, index, *info)` (name, provider, flags), `turbine_impl_supports(op, index, cfg)`, and an implementation index argument on each op call (or `turbine_impl_bind(op, cfg, index)`), plus `turbine_context_set_profile(ctx, *profile)` carrying the card profile's thresholds. Exact names settle in the plan and `.procoder/contract/interfaces.md` §9.

Configuration: _model.tool_call_parser_ (open name, validated against the format registry; `llama3_json`, `none` unchanged; `hermes`, `mistral` added), _execution.backend_ (registered backend name; `cpu`, `hip` unchanged), _scheduler.policy_ (new, default `default`), _execution.card_profile_ (new, default `auto`: chosen from the device). `turbine-server --support-matrix` prints the matrix.

Diagnostics: startup log `module_selected` events (extension point, name, reason); `/turbine/v1/status` gains `modules` (family, tool format, weight format, backend, card profile, scheduling policy) and the support row; kernel selection per op already in status stays and gains the provider.

## Data

No new persistent data. Registries are static tables compiled into the binaries. Card profiles are Rust constants. The support matrix is a Rust table in `turbine-core`. Golden references, fixtures and tolerance files are unchanged; the Phase 8 run-ahead adds tiny-checkpoint fixtures and chat templates for its families under `crates/turbine-model/tests/fixtures/`.

## Edge cases

- A checkpoint whose `architectures[0]` is known to two families, or unknown: refused at startup with the list of registered families; nested `text_config` architectures (from the Phase 8 registry) resolve the same way.
- _model.tool_call_parser_ naming a format the family's tokenizer cannot support (missing special token): refused at startup, as today for `llama3_json` without `<|python_tag|>`.
- Tied vs untied `lm_head` and families with Q/K norm but no bias: handled by skeleton options, not new branches in the skeleton.
- A kernel library without the implementation-enumeration ABI group: the registry uses the library's own default per op (today's behaviour) and logs that selection is library-internal.
- An op config no implementation supports on the chosen card: refused at startup with the op, config and each implementation's refusal reason (today: registry error).
- A device whose architecture has no card profile: refused on the HIP backend with a reason naming the discovered architecture and the profiles available; _execution.card_profile_ can force one for experiments.
- Seeded sampling: processors that consume random numbers must keep the exact draw order so seeded streams stay bit-identical.
- Decode graphs: the skeleton's graph keys must not change, or graph capture/replay counts in the tests change.
- The support matrix and the family registry disagree (a family without a matrix row): the most-specific-row rule decides; a registered family with no row on the current vendor is refused.

## Failure modes

- Registry misconfiguration (two modules with the same name): a unit test over every registry fails the build; at runtime the first registration wins and a warning is logged.
- Kernel library missing an implementation the card profile prefers: the registry falls to the next implementation in the profile's order, logging the reason; if none supports the config, startup fails (exit 1).
- A refactor slice changes numerics: caught by host tests (bitwise CPU paths), GPU suites (`hip_ops`, `tiny_model`, in-process golden) and the served golden; the slice is reverted, not landed.
- A slice regresses throughput > 3% or TTFT > 10%: the chain stops; the slice is fixed or reverted before the next one.
- OLMoE golden c16 flaps on p10/p14 with batch composition (pre-existing, 2026-09-26): one retry per step as in the Phase 2c chain; a persistent failure blocks the slice.
