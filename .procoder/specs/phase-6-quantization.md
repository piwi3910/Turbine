## Problem

After Phase 5 Turbine serves `Llama-3.2-3B-Instruct` and `OLMoE-1B-7B-0125-Instruct` in BF16 only, with BF16 KV only, on one or both R9700 cards (`gfx1201`, 32 GB each) of `novanas`. The checkpoints people run at useful sizes ship quantized — FP8 per-channel and block-scaled, MXFP4, INT4 AWQ and GPTQ — and today any `quantization_config` is refused at config load (`weights::tests::bf16_refusals_match_main`). RDNA4 has FP8 WMMA but no FP4 matrix path: hipBLASLt on the installed ROCm 7.14.1 offers FP8 × FP8 → BF16 with scalar and per-row/column scales but no mixed BF16 × FP8 and no block-scaled or microscaled GEMM, so FP4 and INT4 run weight-only and every format needs a kernel decision under the reuse-first rule. KV is the other half of memory: an FP8 e4m3 cache halves the L0 page and doubles the pool; the Phase 4 lower tiers (pinned host L1 over a ≈ 12 GB/s link, NVMe L2) hold L0-format bytes, so a sub-8-bit format (TurboQuant: random rotation, per-coordinate optimal scalar quantizer, 1-bit QJL residual; ≈ 3.5 bits reported quality-neutral) could hold several times more reusable prefix in the same bytes and move it faster, if lossy blocks never silently replace exact ones. The families of Phase 7 (Qwen3 at 32K → 128K, gpt-oss at 4K → 128K) extend context with static YaRN RoPE scaling, which the config parser refuses today. Finally, when every tier fills, Turbine can only drop cached prefixes; a pressure-driven ladder that first compresses the oldest, least-reusable blocks would keep more reuse under load, provided output never depends on pressure history without that being visible and testable.

## Users

- **Operators:** load a quantized checkpoint by pointing `model.path` at it, see its resolved format in the support-matrix row and `/turbine/v1/status`, get a startup refusal with a reason for anything not proven, choose FP8 KV, per-tier KV formats and the compression ladder explicitly, and read per-tier × format metrics.
- **API clients:** get the same OpenAI API from quantized models, can refuse lossy KV reuse per request, and see how many prompt tokens came from lossy cached KV.
- **Turbine developers:** add a weight format, a checkpoint packaging or a KV codec as one file plus a registry entry, with CPU reference implementations and conformance suites that run on the macOS workstation, and the kernel evaluations recorded before any own kernel.
- **Phase 7:** needs FP8 dense layers under TP 2 (Mixtral), the MXFP4 OpenAI-native loader (gpt-oss) and YaRN for every family.

## In scope

The sub-steps land in this order (provisional, Q1): foundations (S-1, S-2) → weights (S-3 … S-12) → FP8 KV in L0 (S-13, S-14) → YaRN (S-15, S-16) → per-tier formats with FP8 as the first lower-tier codec (S-17 … S-19) → TurboQuant (S-20) → compression ladder (S-21); S-22 … S-25 (gates, configuration, observability, lab) accompany every step.

### Weights

- [S-3] `WeightFormat` becomes a quantized-linear description. The trait (`turbine_model::weights`) keeps `check_config` / `check_tensor` and replaces the three dtypes with: `column()` (the support-matrix value), `scheme(&self, layer: &LinearSlot) -> QuantScheme` (per linear layer; layers the checkpoint leaves unquantized, e.g. `lm_head`, embeddings, norms, report `QuantScheme::Bf16`), `slots(&self, base: &WeightSlot) -> Vec<WeightSlot>` (the tensors one quantized linear layer needs: packed data, scales, zero points, E8M0 exponents, activation scales) and `activation(&self) -> ActivationQuant` (`None` | `Fp8PerTensorStatic` | `Fp8PerTokenDynamic` | `Fp8PerGroupDynamic { group }` | `Mxfp4Emulated`). One registry entry per checkpoint packaging, one file each under `crates/turbine-model/src/weights/`: `bf16`, `ct_fp8` (compressed-tensors FP8 tensor/channel/block), `hf_fp8` (`quant_method: fp8`, with or without `weight_block_size`), `awq` (AutoAWQ GEMM), `gptq` (AutoGPTQ), `ct_pack_int4` (compressed-tensors `pack-quantized` W4A16), `ct_mxfp4` (`mxfp4-pack-quantized`), `quark_mxfp4` (Quark `fp4` group 32, E8M0 scales, weight-only or W4A4) and `openai_mxfp4` (`quant_method: mxfp4`, `*_blocks` / `*_scales` tensors); `detect` keeps `bf16` first. Container → column mapping (provisional, Q5): `fp8` ← compressed-tensors `float-quantized` 8-bit with weight strategy `tensor` or `channel`, and `quant_method: fp8` without `weight_block_size`; `fp8_block` ← compressed-tensors weight strategy `block` [128, 128] and `quant_method: fp8` with `weight_block_size` [128, 128]; `awq_int4` ← `quant_method: awq`, `version: gemm`, 4 bits, zero points; `gptq_int4` ← `quant_method: gptq`, 4 bits, `desc_act: false`, and compressed-tensors `pack-quantized` 4-bit int, group strategy, no non-trivial `g_idx`; `mxfp4` ← compressed-tensors `mxfp4-pack-quantized` without input activations, Quark `fp4` weight-only, OpenAI `mxfp4`; `mxfp4_a4` ← Quark `fp4` weights with `fp4` dynamic input tensors. Refused with a reason: act-order GPTQ (`desc_act: true` or a non-identity `g_idx`, reason `gptq_act_order`), any bit width, group size, block shape or scale dtype outside these (reason `quant_scheme_unsupported` naming the field), `kv_cache_scheme` other than null or static FP8 per-tensor, and every container mapping to a reserved column (`modelopt_nvfp4`, `modelopt_fp8`, `modelopt_mixed`, `ct_nvfp4`; deferred `phase-2b-nvidia`).
- [S-4] Loading. `WeightLoader` loads through the detected format (no hard-wired `Bf16`); each quantized linear layer becomes a `QuantLinear { scheme, data: DeviceTensor, scales: Option<DeviceTensor>, zeros: Option<DeviceTensor>, act_scale: Option<f32> }` whose layout is the one the kernel provider needs (S-6): the loader repacks at load time where a packaging's layout differs (AWQ's interleaved nibble order, GPTQ's row-packed `qweight`, OpenAI's `*_blocks`), on the host, through the existing 256 MiB staging buffer and pinned bounce buffer. The fused Q/K/V and gate/up stacks of Phase 1 stay: stacking concatenates packed rows and their scales; a stack whose parts have different per-tensor scales is rescaled to a per-channel scale vector at load (exact). Memory accounting (`ModelShape.weight_bytes`) counts the packed bytes and the scale tensors.
- [S-5] CPU reference. `turbine-kernels` `cpu` provider gains `dequantize(scheme, data, scales, zeros) -> Vec<f32>` for every scheme and a quantized GEMM that dequantizes the weight to F32 and, for `ActivationQuant` other than `None`, quantize-dequantizes the activations first (FP8 e4m3 round-to-nearest-even with saturation; MXFP4 E2M1 with E8M0 shared exponent per 32, OCP rules). It is the reference every GPU implementation is tested against. Every family's `write_tiny` gains a quantized variant per packaging (`testing::tiny::write_tiny_quantized(dir, family, packaging, seed)`, written in Rust, no Python), so the macOS test suite covers detection, loading, repacking and CPU execution of every packaging.
- [S-6] Kernel ABI. An optional minor group v2.9 (`TURBINE_ABI_MINOR` 9; `TURBINE_ABI_VERSION` stays 2, per the umbrella constraint) adds: `turbine_qgemm_desc` (A, B, C pointers and strides as `turbine_gemm_desc`, plus `int32_t scheme`, `b_scales`, `b_zeros`, `a_scales`, `group_size`, `block_n`, `block_k`, `act_quant`) with the trio `turbine_qgemm` / `turbine_qgemm_supported` / `turbine_qgemm_impl` and op code `TURBINE_OP_QGEMM` = 17; `turbine_quantize_act_desc` with the trio `turbine_quantize_act*` (op 18: per-tensor static, per-token dynamic and per-group-of-128 dynamic FP8 e4m3, and MXFP4 quantize-dequantize) ; scheme codes `TURBINE_QSCHEME_FP8_TENSOR` 1, `_FP8_CHANNEL` 2, `_FP8_BLOCK` 3, `_INT4_GROUP_ZP` 4, `_INT4_GROUP_SYM` 5, `_MXFP4` 6; dtype codes `TURBINE_DTYPE_F8E4M3` 16 and `TURBINE_DTYPE_U8` 17. A library with minor < 9 simply has no quantized GEMM, and a quantized checkpoint on it is refused at startup (exit 1, `event="kernel_capability"`, reason `qgemm_unavailable`). Rust: `OpKind::QGemm`, `OpKind::QuantizeAct`, `QGemmConfig { n, k, scheme, act_quant, c_dtype, group_size }`, `trait QGemmKernel { supports, implementation, execute }`, `KernelProvider::qgemm()` / `quantize_act()` defaulting to `None`, and `KernelRegistry::qgemm(&cfg)`.
- [S-7] `fp8` on HIP (provisional, Q2): W8A8 following the checkpoint's activation scheme — per-token dynamic or per-tensor static activation quantization (`turbine_quantize_act`), then hipBLASLt FP8 × FP8 → BF16 with the weight's scale as scalar or per-column vector (`HIPBLASLT_MATMUL_DESC_*_SCALE_POINTER` / the vector-scale mode the gfx1201 `SABV` kernels implement) and the activation scale per row; a checkpoint with no activation scheme runs W8A16 through the dequantize path of S-8. The quantize step is fused into the preceding RMSNorm where the evaluation shows a provider for it, else it is its own op. Registered implementation `hipblaslt_fp8` in `impl_table.cpp`; the `gemm_table` tuning covers FP8 shapes.
- [S-8] `fp8_block` on HIP: first CK `ck_tile` `ABQuantGrouped` (FP8 A per-token-group-of-128 scales × FP8 B per-128 × 128-block scales) instantiated for `gfx1201` from the pinned CK; if it does not build or does not match the CPU reference, W8A16 through a dequantize-to-BF16 path (provisional, Q3), with the evaluation recorded before any own kernel.
- [S-9] `awq_int4` / `gptq_int4` on HIP, weight-only (W4A16, BF16 activations): decode (M ≤ 16) through a dequantize-GEMV and prefill through dequantize-to-BF16 tiles feeding a BF16 WMMA GEMM or CK `BQuantGrouped` with packed INT4 B; candidates evaluated in order: CK `ck_tile` `gemm_quant` `BQuantGrouped` (pk_int4 B), llama.cpp's HIP `mul_mat_vec_q` / `mmq` for 4-bit groups (as a registered implementation built from pinned sources), vLLM/aiter ROCm AWQ/GPTQ kernels (their `gfx12` support), then own. Zero points (AWQ) and symmetric groups (GPTQ, 8 as implicit zero) share one kernel family with a scheme flag.
- [S-10] `mxfp4` and `mxfp4_a4` on HIP, weight-only on RDNA4: FP4 E2M1 values times 2^(E8M0 − 127) per 32 elements dequantized to BF16 in the kernel (exact in BF16), candidates in order: CK `ck_tile` microscale pipeline (`gemm_microscale_*`), llama.cpp's HIP MXFP4 (`GGML_TYPE_MXFP4`) mat-vec and mmq kernels, then own. `mxfp4_a4` (Quark W4A4) runs the same kernel after `turbine_quantize_act` quantize-dequantizes each 32-element activation group to MXFP4 (the checkpoint's `round_method: half_even`, `scale_calculation_mode: even`); its row is `supported` only if it passes the S-3 gate against the checkpoint's reference, else `experimental` (decision "Phase 6 MXFP4"). The OpenAI native packaging (`openai_mxfp4`) is loaded and repacked into the same layout and tested on a tiny fixture; its row stays `unsupported` (reason naming `phase-7-model-families`) until Phase 7 closes gpt-oss-20b.

### FP8 KV in L0

- [S-13] `kv.dtype` (umbrella-reserved key) with values `bf16` (default) and `fp8_e4m3`. With `fp8_e4m3`, `KvLayout.dtype` is `F8E4M3`, pages halve and the pool holds twice the blocks; the paged-append step quantizes new K and V rows with per-layer K and V scales (provisional, Q10: from the checkpoint's `kv_cache_scheme` / `k_scale` / `v_scale` tensors when present, else 1.0; the scales enter the namespace key); attention reads FP8 pages through the provider the evaluation picks — the pinned CK FMHA pagedkv / split-KV FP8 instances for `gfx1201` first, then an FP8-reading variant of the Turbine paged kernel (dequantize on load), then llama.cpp's HIP flash attention if its quantized-KV path can be adapted to e4m3 pages. The CPU provider stores and reads F8E4M3 through the S-5 rounding rules. Nothing lossy is on by default (umbrella constraint): `fp8_e4m3` is always an explicit setting. FP8 KV works under Phase 5 TP, EP and DP (per-rank pools, same scales on every rank). Support rows `amd/gfx1201/{Llama,Olmoe}ForCausalLM/bf16/fp8_e4m3/none` turn `supported` after the S-22 gate; FP8 KV combined with a quantized weight format is `supported` only for combinations that passed their own gate.
- [S-14] KV tier accounting under FP8: the lower tiers store the L0 page bytes as they are (the `l0` format), the Phase 4 `kv_gpu` round trips stay bit-exact at `fp8_e4m3`, and `/turbine/v1/kv` and `turbine_kv_bytes` report the real bytes.

### YaRN

- [S-15] `rope_scaling` type `yarn` parsed for every registered family (`factor`, `original_max_position_embeddings`, `beta_fast` (default 32), `beta_slow` (default 1), `mscale` / `mscale_all_dim` / `attention_factor` as transformers resolves them, `truncate` (default true)); `inv_freq` computes transformers' `_compute_yarn_parameters` blend in FP64 on the host; the attention factor folds into the attention softmax scale (`scale × attention_factor²`, provisional, Q19), so the RoPE ABI is unchanged. `dynamic`, `linear`, `longrope` and a YaRN entry with a `dynamic` flag stay refused (dynamic scaling would change cached keys mid-sequence). `model.max_seq_len` may extend to `factor × original_max_position_embeddings` when `max_position_embeddings` is smaller. A configuration key `model.rope_scaling` (a mapping with HF's field names) overrides `config.json`'s entry (provisional, Q19).
- [S-16] RoPE configuration in identity: the resolved RoPE parameters (type, theta, every scaling field) enter the namespace key, so blocks cached under one RoPE configuration are never reused under another. Proof (provisional, Q19): Llama-3.2-3B-Instruct with `model.rope_scaling: {rope_type: yarn, factor: 16.0, original_max_position_embeddings: 8192, beta_fast: 32, beta_slow: 1}` against transformers' native YaRN on a copy of the checkpoint carrying that `config.json` (fixture time), over the 16 golden prompts plus one ≈ 12,000-token prompt, committed as `tests/golden/llama-3.2-3b-instruct-yarn16/`; the row stays the BF16 Llama row (YaRN is not a support-matrix column), gated by that golden at c1 and c16.

### Per-tier KV formats

- [S-17] KV codecs. A `KvCodec` trait (`turbine_kv::codec`, one file per codec, registry `kv_format`): `name()`, `lossy()`, `bytes_per_block(layout)`, `encode_cpu` / `decode_cpu` (the reference, `turbine-kv` stays GPU-free) and a `KernelOp` binding for the GPU transcode. Registered: `l0` (identity, lossless), `fp8_e4m3` (lossless only when L0 is FP8 with the same scales; from BF16 L0 it is lossy), `tq4`, `tq2` (S-19). GPU transcoding: an optional ABI group v2.10 adds `turbine_kv_transcode_desc` (source pages, source format and scales, destination buffer, destination format, codec parameters) with the trio `turbine_kv_transcode*` (op 19), one call per demotion batch, writing into a device staging buffer whose bytes then cross the host link through the existing pinned paths (L1 slots are pinned; L2 goes through the pinned bounce buffer — no pageable async copy is added); promotion copies the small bytes up and decodes into the L0 page (provisional, Q11: attention never reads a lower-tier format).
- [S-18] Per-tier configuration: `kv.cpu.format` and `kv.nvme.format` ∈ {`l0`, `fp8_e4m3`, `tq4`, `tq2`} (default `l0`); a tier may not be more precise than the tier above it (exit 2 naming both keys); `kv.lossless_tail_blocks` (default 1): the last N full blocks of a sequence at demotion time are demoted at the L0 format whatever the tier's format; a partial last block never leaves L0 (Phase 4/5p) (provisional, Q13). Lower-tier formats are resolved against a `TIER_FORMAT_REFUSALS` table in `turbine_core::support` (`tq4`/`tq2` are `experimental` until the S-22 gate passes, then `supported`); the support-matrix row keeps naming the L0 format.
- [S-19] Lossy lineage and reuse (provisional, Q14–Q16). Every directory location carries its format; a block keeps its key while an exact copy exists; a lossy copy is filed under `lossy_key(key, format, seed)`; a block computed over a lossy prefix is chained from the lossy parent key, so exact and lossy lineages never alias. A lookup follows the exact chain first and continues on lossy keys unless the request sends `x-turbine-kv-lossy: deny` (or `kv.lossy_reuse: deny` is configured); an opted-out request recomputes from the first lossy block. The planner multiplies a lossy block's retrieval cost by `1 + kv.lossy_penalty.<format>` (defaults `fp8_e4m3` 0.1, `tq4` 0.5, `tq2` 1.0). Responses report `usage.prompt_tokens_details.lossy_cached_tokens` (0 when none). Blocks in lossless formats keep the Phase 4 bit-exact guarantee.
- [S-20] TurboQuant (provisional, Q12): codecs `tq4` and `tq2` per token-head vector (`head_dim` 128): a randomized Hadamard rotation (random ±1 signs from a seed derived from the namespace key, then the fast Walsh–Hadamard transform), the vector's L2 norm stored in BF16, each rotated coordinate quantized with a fixed Lloyd–Max codebook for the post-rotation coordinate distribution (Beta, approximately Gaussian at d = 128; codebooks computed in Rust at build time of the test, committed as constants), and for K the 1-bit QJL sign of a second randomized projection of the residual with its BF16 norm (the paper's inner-product variant); `tq4`: K 3 + 1 bits, V 4 bits; `tq2`: K 1 + 1 bits, V 2 bits; the same widths for every layer. Encode/decode kernels: evaluation first (llama.cpp and vLLM/SGLang for existing TurboQuant or QJL HIP kernels, CK elementwise/transform building blocks), then own; the CPU codec is the reference and the GPU codec must match it bit-exactly on decode (encode may differ only by documented tie-breaking, tested).
- [S-21] Pressure-driven compression ladder (provisional, Q17, Q18), the last step. Every block location carries a format tag (S-19). `EvictionPolicy` gains `fn action(&self, b: &BlockScoreInputs, ctx: &LadderContext) -> EvictAction` (default: `Demote` or `Drop` exactly as Phase 4 decides) with `EvictAction::Compress { to }`; `cost_aware` implements the ladder: when a block would be dropped from the lowest enabled tier, or that tier is above 0.95 used, and the pressure controller is not GREEN, the oldest, least-reusable blocks of that tier move one rung down (`l0` → `fp8_e4m3` → `tq4` → `tq2` → evict), then the next tier up once the lowest tier sits on one rung; new demotions into a tier take its current rung; at most 32 rewrites per reclaim tick with ticks ≥ 50 ms apart; a tier's rung for new demotions steps back up only after it has stayed below 0.85 used for `reliability.pressure.deescalate_dwell`; compressed blocks never go back up. L1 and L2 only (L0 joins after mixed-format attention, not in this phase). The lossless rung is the L0 format's bytes unchanged. Switch: `kv.ladder.enabled` (default `false`); `kv.ladder.max_format` bounds the lossiest rung (default `tq2`). Every rung change emits a reason code and metrics; tests pin the pressure state.

## Edge cases

- A checkpoint whose `config.json` says `torch_dtype: float16` with quantized linears (AWQ, GPTQ): activations run in BF16 (`model.dtype`), F16 scales are converted at load; embeddings and norms stored in F16 are converted to BF16 at load (logged once).
- `lm_head` or embeddings unquantized (`ignore: ["lm_head"]`) or tied: `QuantScheme::Bf16` for those, the BF16 GEMM path.
- A fused stack (qkv, gate_up) whose parts carry different per-tensor FP8 scales: rescaled to a per-channel vector at load (exact); parts with different schemes (one quantized, one not): refused `quant_scheme_unsupported`.
- `n` or `k` not a multiple of the group or block size: refused `quant_scheme_unsupported` naming the layer (the proof checkpoints are aligned).
- A kernel library without v2.9 and a quantized checkpoint: exit 1 before bind with `qgemm_unavailable`; `kv.dtype: fp8_e4m3` without FP8 paged attention: exit 1 `kv_fp8_unavailable`; a tier format without v2.10: exit 1 `kv_transcode_unavailable`.
- CPU backend: every format runs through the S-5 reference (slow, `experimental` like every CPU row).
- FP8 KV with a checkpoint that stores `k_scale`/`v_scale` and a TP split: every rank uses the same per-layer scale.
- YaRN with `original_max_position_embeddings` ≥ `max_position_embeddings` (nothing to extend): accepted, `max_seq_len` capped by `max_position_embeddings`; YaRN on a model whose config already has `llama3` scaling: the override replaces it wholesale.
- Two requests with different RoPE overrides cannot exist (one model per process); a server restarted with a different override never sees the old blocks (L2 wiped; namespace differs).
- Lossy lineage: a request that opted out arrives while only a lossy copy of its prefix exists: it recomputes from the first lossy block and publishes an exact chain alongside the lossy one; a later exact lookup takes the exact chain.
- Promotion of a lossy block into L0 for a request that allows lossy reuse: the L0 copy keeps the lossy key; blocks that request prefills on top are chained from it (lossy lineage) and are never matched by an opted-out request.
- `kv.lossless_tail_blocks` larger than a sequence's full blocks: every block of it is demoted at the L0 format.
- Ladder: a tier already at `kv.ladder.max_format` and still above high water: the oldest least-reusable blocks are evicted (`ladder_floor`); pressure returns to GREEN mid-rewrite: in-flight rewrites complete, no new ones start; a block referenced by a running request is never rewritten; a block being promoted is never rewritten.
- Transcode failure on the device: the demotion is abandoned (the source copy stays), the tier is marked degraded as for a copy error (Phase 4 S-12), the request never fails.
- NVMe slab written by an older `TKVSLAB1` version: impossible (wiped at startup).

## Failure modes

- **Unsupported quantized checkpoint:** config load refuses it (exit 1 before weights are read, `quant_refused` with reason); an `unsupported` support row exits 2 under `--check-config` and 1 at startup (umbrella).
- **Kernel library lacks a group:** exit 1 before bind with `qgemm_unavailable`, `kv_fp8_unavailable` or `kv_transcode_unavailable`.
- **A quantized kernel produces NaN/Inf at warm-up:** the Phase 1 warm-up check fails startup (exit 1) naming the op and implementation.
- **Golden or accuracy gate fails for a format:** its row stays `experimental` (degraded) or `unsupported` (wrong), the finding is recorded, and the phase continues with the next format; the phase closes only with the user's decision on each non-passing format.
- **TurboQuant decode mismatch between GPU and CPU:** the lab test fails; the codec's row stays `experimental`.
- **Lossy block served to an opted-out request:** a correctness bug; prevented by lineage keys, covered by a simulator test that asserts it can never happen.
- **Ladder oscillation:** bounded by hysteresis and the per-tick rewrite cap; a simulator test with a pinned pressure trace asserts the rung sequence.
- **A download fails or disk falls below 60 GB free:** the download stops and the coordinator is asked; nothing else is deleted.
