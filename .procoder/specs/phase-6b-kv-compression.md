## Problem

After `phase-6a-quantization`, L0 holds BF16 or FP8 KV, and the Phase 4 lower tiers (pinned host L1 over a ≈ 12 GB/s link, NVMe L2) hold the L0 page bytes unchanged. A sub-8-bit format — TurboQuant: random rotation, per-coordinate optimal scalar quantizer, 1-bit QJL residual; ≈ 3.5 bits reported quality-neutral — could hold several times more reusable prefix in the same bytes, move it faster over the host link, and, read directly by attention, multiply the L0 pool; but only if lossy blocks never silently replace exact ones, requests can refuse them, and the planner knows a lossy retrieve is worth less than an exact one. When every tier fills, Turbine can only drop cached prefixes; a pressure-driven ladder that first compresses the oldest, least-reusable blocks would keep more reuse under load, provided output never depends on pressure history without that being visible and testable.

## Users

- **Operators:** choose per-tier KV formats, TurboQuant in L0 and the compression ladder explicitly, and read per-tier × format metrics and ladder reason codes.
- **API clients:** get the same OpenAI API from quantized models, can refuse lossy KV reuse per request, and see how many prompt tokens came from lossy cached KV.
- **Turbine developers:** add a KV codec as one file plus a registry entry, with a CPU reference and a conformance suite that run on the macOS workstation, and the kernel evaluations recorded before any own kernel.

## In scope

The sub-steps land in this order (user decision 2026-09-28, Q1, Q11): per-tier formats with FP8 as the first lower-tier codec (S-1 … S-3) → TurboQuant as a lower-tier codec (S-4), then in L0 with a mixed-format paged attention (S-5) → compression ladder in L1/L2 (S-6), then in L0 as the final sub-step (S-7); S-8 … S-11 (gates, configuration, observability, lab) accompany every step.

### Per-tier KV formats

- [S-1] KV codecs. A `KvCodec` trait (`turbine_kv::codec`, one file per codec, registry `kv_format`): `name()`, `lossy()`, `bytes_per_block(layout)`, `encode_cpu` / `decode_cpu` (the reference, `turbine-kv` stays GPU-free) and a `KernelOp` binding for the GPU transcode. Registered: `l0` (identity, lossless), `fp8_e4m3` (lossless only when L0 is FP8 with the same scales; from BF16 L0 it is lossy), `tq4`, `tq2` (S-3). GPU transcoding: an optional ABI group v2.11 adds `turbine_kv_transcode_desc` (source pages, source format and scales, destination buffer, destination format, codec parameters) with the trio `turbine_kv_transcode*` (op 19), one call per demotion batch, writing into a device staging buffer whose bytes then cross the host link through the existing pinned paths (L1 slots are pinned; L2 goes through the pinned bounce buffer — no pageable async copy is added); promotion copies the small bytes up and decodes into an L0 page of the L0 base format, except that a TurboQuant block promoted into an L0 that holds TurboQuant pages (S-5, S-7) is copied as is.
- [S-2] Per-tier configuration: `kv.cpu.format` and `kv.nvme.format` ∈ {`l0`, `fp8_e4m3`, `tq4`, `tq2`} (default `l0`); a tier may not be more precise than the tier above it (exit 2 naming both keys); `kv.lossless_tail_blocks` (default 1): the last N full blocks of the latest finished sequence at demotion time are demoted at the L0 format whatever the tier's format — a growing sequence's newest demoted block keeps the guarantee, and the tags expire when a later sequence finishes, so an earlier finished sequence's tail demotes like any other block (user decision 2026-10-03, "6b: stale lossless-tail tags and the tq4 lab bound", 1); a partial last block never leaves L0 (Phase 4/5p) (user decision 2026-09-28, Q13). Lower-tier formats are resolved against a `TIER_FORMAT_REFUSALS` table in `turbine_core::support` (`tq4`/`tq2` are `experimental` until the S-8 gate passes, then `supported`); the support-matrix row keeps naming the L0 format.
- [S-3] Lossy lineage and reuse (user decision 2026-09-28, Q14–Q16). Every directory location carries its format; a block keeps its key while an exact copy exists, and a lossy copy of it is one more location (with its format) on that exact entry; only an L0 copy promoted from a lossy copy is filed as its own entry under `lossy_key(key, format, seed)`, and a block computed over a lossy prefix is chained from that lossy parent key, so exact and lossy lineages never alias (user decision 2026-09-30, 6b Task 4). A lookup follows the exact chain first and continues on lossy keys unless the request sends `x-turbine-kv-lossy: deny` (or `kv.lossy_reuse: deny` is configured); an opted-out request recomputes from the first lossy block. The planner multiplies a lossy block's retrieval cost by `1 + kv.lossy_penalty.<format>` (defaults `fp8_e4m3` 0.1, `tq4` 0.5, `tq2` 1.0). Responses report `usage.prompt_tokens_details.lossy_cached_tokens` (0 when none); over TurboQuant L0 pages (S-5) every cached token is served from a lossy block and counted there (user decision 2026-10-02, "6b Task 13: TurboQuant in L0 — gate results, prefill profile", 4 A). Blocks in lossless formats keep the Phase 4 bit-exact guarantee.

### TurboQuant

- [S-4] TurboQuant (user decision 2026-09-28, Q12): codecs `tq4` and `tq2` per token-head vector (`head_dim` 128): a randomized Hadamard rotation (random ±1 signs from a seed derived from the namespace key, then the fast Walsh–Hadamard transform), the vector's L2 norm stored in BF16, each rotated coordinate quantized with a fixed Lloyd–Max codebook for the post-rotation coordinate distribution (Beta, approximately Gaussian at d = 128; codebooks computed in Rust at build time of the test, committed as constants); K and V take the same path, the paper's TurboQuant_mse, each with its own rotation signs (amended, user decision 2026-10-01 "6b Task 9: TurboQuant K quantizer", A: on real Llama-3.2-3B K the specified inner-product K — b − 1 MSE bits plus a 1-bit QJL residual of a Gaussian projection — had 5× the K reconstruction error and about twice the attention-output error of K with all its bits in the MSE stage, `tq_loss_on_real_kv`); `tq4`: K and V 4 bits (144-byte records); `tq2`: K and V 2 bits (80-byte records); the same widths for every layer. Encode/decode kernels: evaluation first (llama.cpp and vLLM/SGLang for existing TurboQuant HIP kernels, CK elementwise/transform building blocks), then own; the CPU codec is the reference and the GPU codec must match it bit-exactly on decode (encode may differ only by documented tie-breaking, tested).
- [S-5] Mixed-format paged attention and TurboQuant in L0. `kv.dtype` accepts `tq4` and `tq2` as the L0 base format besides `bf16` and `fp8_e4m3`. Every L0 block carries a format tag in its block-table entry; L0 pages are allocated from one page class per format carved from the one KV budget (the base class sized by `kv.dtype`, other classes grown on demand in slabs of pages and returned when empty), so a block's bytes always match its tag. The paged-append step encodes new K/V rows into the block's format (TurboQuant on the GPU through the S-4 codec). The attention reads each block by its tag: BF16 and FP8 blocks as in `phase-6a-quantization` S-13 (FP8 elements read as `bf16(e4m3 × scale)`, the reference included); in decode, `tq4` / `tq2` blocks without materialising K or V — per step and head, q is rotated once with the randomized Hadamard transform (the signs depend only on the namespace seed, layer and head, so one rotation serves every TurboQuant block of the sequence), the score of a key is its BF16 norm times the dot product of the rotated q with the key's codebook values (the rotated-domain MSE reconstruction; no residual term since K is TurboQuant_mse, S-4), and V is accumulated as norm-weighted codebook values in the rotated domain and rotated back once per output row. Prefill (amended, user decision 2026-10-01 "6b Task 10: TurboQuant prefill attention", A) reuses CK: the batch's TurboQuant and FP8 blocks are decoded into a bounded BF16 staging pool by the S-4 / S-1 transcode, a staged block table points at them, and the unchanged CK BF16 prefill instance attends — K and V are materialised for prefill only, and the prefill is judged against the reference over the BF16-rounded decoded values. Prefill chunks read their own new rows from the pages as well (appended first, then staged), so prefill and decode see the same KV. Reuse first: before any own kernel, existing quantized-KV attention is evaluated on `gfx1201` — llama.cpp's HIP flash attention with q4_0 / q8_0 KV, CK FMHA with FP8 KV, vLLM / aiter ROCm paged attention with quantized KV — and recorded; the evaluation decides whether an existing kernel is adapted (e.g. its dequant-on-load loop fed with TurboQuant decode) or an own mixed-format kernel is written. Gates: the GPU attention against a CPU reference TurboQuant attention (`cpu::tq_attention`: decode, then exact attention in F32) within a documented tolerance; golden and `turbine-golden eval-compare` (within `quality.max_accuracy_drop` of BF16 KV) with `kv.dtype: tq4` and `tq2` for Llama and OLMoE; and the decode ITL impact at c1 and c16 against BF16 KV measured and reported (no fixed bound, Q20). The ABI carries this in v2.11: `turbine_attention_paged_desc` gains `block_formats` (one byte per block-table entry, null = every block in `dtype`) and `tq_params` (seed, codebooks), read only at minor ≥ 11. Support rows `amd/gfx1201/{Llama,Olmoe}ForCausalLM/bf16/tq4/none` turn `supported` after the gates, else stay `experimental`. `kv.dtype: tq2` is refused on every backend (amended, user decision 2026-10-02, "6b Task 13: TurboQuant in L0 — gate results, prefill profile", 2 B: shared-prefix GSM8K collapses to 0.15–0.20 on both models): the support matrix's `tq2` KV column is `unsupported` with the reason code `kv_tq2_l0_refused`, so startup exits 2 naming `kv.dtype` before any port is bound; `tq2` stays a lower-tier format (S-2, S-4) and a ladder rung (S-6, S-7). The recent window (user decision 2026-10-02, "6b Task 13: TurboQuant in L0 — gate results, prefill profile", 1 C): when the L0 base format is lossy, the newest `kv.recent_window_blocks` full blocks of each live sequence hold BF16 pages instead — a sequence's new blocks are created in the BF16 page class (grown on demand like any non-base class), and a block that leaves the window because the sequence grew past it is recompressed in place into the L0 base format (the S-1 transcode on the device, the host codec on the CPU backend), its page, format tag and lineage following S-3 and this section. The window is a quality decision, not a pressure reaction: it runs whatever the pressure controller does, with or without the ladder, and the ladder's L0 step (S-7) never rewrites a block inside a live sequence's window or its lossless tail. `kv.recent_window_blocks` defaults to 1 (one block, the server's `kv.block_tokens` tokens: it matches `kv.lossless_tail_blocks`, and the newest tokens carry most of an attention row's mass; larger values trade L0 capacity for exactness; 0 turns the window off). The executor resolves every block id through its page class (per-class block addressing through the ABI v2.11 descriptors, user decision "6b Task 17: the BF16 recent window needs per-class block addressing", A — a BF16 window page is larger than a TurboQuant base page, so the flat base-class addressing could not read it; `p6b-window`), so the window serves: the append writes each new row in its block's class at the class's slab offset and attention and the fork's block copy read the same way, the flat base-page addressing staying byte-identical for pools without classes.

### Compression ladder

- [S-6] Pressure-driven compression ladder (user decision 2026-09-28, Q17, Q18), the last step. Every block location carries a format tag (S-3). `EvictionPolicy` gains `fn action(&self, b: &BlockScoreInputs, ctx: &LadderContext) -> EvictAction` (default: `Demote` or `Drop` exactly as Phase 4 decides) with `EvictAction::Compress { to }`; `cost_aware` implements the ladder: from YELLOW pressure on — before the tiers are full (user decision 2026-09-29, "Start at YELLOW earlier") — and also whenever a block would be dropped from the lowest enabled tier or that tier is above 0.95 used and the controller is not GREEN, the oldest, least-reusable blocks of the lowest enabled tier move one rung down (`l0` → `fp8_e4m3` → `tq4` → `tq2` → evict), then the next tier up once the lowest tier sits on one rung; at YELLOW, when no block must leave and the tier is not above `kv.ladder.high_water`, the lowest tier compresses only until it is back to GREEN headroom — while `fill + demand > kv.ladder.low_water`, `demand` being the bytes the YELLOW reclaim wants to demote into it this tick as a fraction of its capacity — and then stops, so a steady YELLOW does not drift the tier to `tq2` (user decision 2026-09-29, "YELLOW depth": compress only until GREEN); ORANGE and above compress as described without that stop; new demotions into a tier take its current rung while the tier has a free slot of the rung's size (a slab tier whose slabs hold another slot size stores them at its own format instead, `rung_no_slot`, so demotions keep flowing; user decision "6b: ladder-on regression — demotions into a tier whose rung changed", A); at most 32 rewrites per reclaim tick with ticks ≥ 50 ms apart; a tier's rung for new demotions steps back up only once the controller is GREEN and the tier has stayed below 0.85 used for `reliability.pressure.deescalate_dwell` (user decision 2026-09-30, option A: no step-up while not GREEN); compressed blocks never go back up. L1 and L2 first; L0 joins as the final sub-step (S-7), after the mixed-format attention of S-5 has passed its gates. The lossless rung is the L0 format's bytes unchanged. Switch: `kv.ladder.enabled` (default `false`); `kv.ladder.max_format` bounds the lossiest rung (default `tq4`: `tq2` failed its own lower-tier GSM8K gate in Task 9, user decision 2026-10-02, "6b Task 16: ladder enablement on the server — four points", 2 A). Every rung change emits a reason code and metrics; tests pin the pressure state.
- [S-7] The ladder's L0 step, the phase's final sub-step, started only after S-5 has passed its correctness and performance gates and S-6 its L1/L2 gates. L0 becomes the ladder's top tier: the same rung order (`bf16` → `fp8_e4m3` → `tq4` → `tq2` → demote or evict, starting at the L0 base format), the same trigger (L0 fill above `kv.ladder.high_water` and the pressure controller not GREEN), bounds (≤ 32 rewrites per tick, ticks ≥ 50 ms apart) and hysteresis; compression runs on the GPU from a base-class page into a page of the smaller class and frees the base page; only unreferenced cached blocks are rewritten (never a block of a running request, a block being promoted or demoted), the last `kv.lossless_tail_blocks` full blocks of a sequence stay at the base format, and so do the newest `kv.recent_window_blocks` full blocks of each live sequence (the recent window, S-5), and a compressed block takes a lineage key (S-3) like a lossy lower-tier copy. `kv.ladder.l0` (default `true`; the whole ladder stays behind `kv.ladder.enabled`, default `false`) keeps the ladder in L1/L2 when false.

### Gates, observability, lab

- [S-8] Quality gates (user decision 2026-09-28, Q9): every KV format (`fp8_e4m3` or `tq4` / `tq2` in a lower tier, `tq4` / `tq2` in L0, the ladder) is compared with the same weights at BF16 KV within `quality.max_accuracy_drop` on `tests/eval/gsm8k-200-shared-prefix.jsonl`, and judged by golden against the model's BF16 reference with the golden token rule and the slug's batched logprob bounds (lossy KV perturbs like batch composition). The shared-prefix variant (user decision 2026-10-01, "6b Task 6" point 1 A) is the same 200 GSM8K items behind one identical ~2000-word system message (generated by `scripts/eval/make-gsm8k-200-shared-prefix.sh`, validated by `eval_task_set_shared_prefix_valid`), because plain GSM8K-200 prompts are short and independent and reuse no KV block, so a lossy-KV gate on it never reads a lossy block. A lossy-KV gate is a pair of `turbine-golden eval` runs on that variant, the BF16-KV baseline and the candidate, at the same concurrency, the same server settings apart from the format under test, and the same `--filler-requests` / `--filler-words` (the runner sends the first two items one after the other — the second hit gives the prefix the reuse evidence a demotion needs — then the fillers, then the rest, so the prefix is pushed out of L0 into the lower tier before the other 198 items arrive); the candidate run states `--min-lossy-cached-ratio` and exits 1 when fewer than that share of the prompt tokens were served from lossy blocks (`usage.prompt_tokens_details.lossy_cached_tokens`), so a gate that reused nothing lossy cannot pass. The L0 TurboQuant formats (`kv.dtype`) hold every block lossy, so their gate needs no lossy-ratio guard (it still sends the same fillers as its BF16 baseline, which `eval-compare` requires); the plain gsm8k-200 reports remain the BF16 / FP8-KV-pool baselines of Phase 6a. Copy ahead (user decision 2026-10-01, "6b: shared-prefix eval never demotes the prefix to L1", A): while the pressure controller is GREEN or YELLOW (from ORANGE on freeing L0 comes first), when capacity demotion or the controller's reclaim would demote, unreferenced blocks of a shared prefix (two or more children, or an ancestor of such a block) that the leaf-first rule holds in L0 (reuse evidence, a child resident in L0, no lower copy yet; a linear re-used chain such as a session's history is left to leaf-first demotion) are copied into the L0 demotion target while their L0 copy stays, lowest value first, within the 32 L0 copies in flight and only into that tier's free room up to half its capacity; the L0 copy then leaves by the Phase 4 rules (once its children have left, or under higher pressure) without another copy, so a prefix shared by one-off requests reaches the lower tier as soon as they are reclaimed. Queued-prefix demotion (user decisions 2026-10-01, "6b: after the held-prefix ledger fix", 1 B, and "6b: queued-prefix demotion — granularity and scope", 1 A, 2 A): at YELLOW and ORANGE, when the controller's reclaim wants more L0 blocks than are unreferenced, requests waiting in the admission queue release their whole attached prefixes, the last to be admitted first (the queue head keeps its own), until the blocks only they hold cover the shortfall, at most 32 blocks per controller tick; the released blocks leave the ledger's held KV at once and the next reclaim demotes them (or frees them when copy ahead already copied them); once admitted, such a request attaches again through the planner (its reservation stays whole, in case the planner recomputes). No new config key. The P4 S-7 leaf-first rule is unchanged; into a lossy tier the copy is one more location of the exact entry (S-3). Ladder variant (user decision 2026-10-02, "6b Task 16: ladder proof results — four open points", 1 A, 4 A): the ladder never compresses at GREEN, so its gate makes the fillers raise pressure. Both sides serve `scripts/lab/phase6-novanas-ladder.yaml` with `kv.gpu.max_bytes=4GiB`, `kv.cpu.max_bytes=4GiB` and `kv.nvme.enabled=false` (L1 is the only lower tier, so the prefix is rewritten there), the baseline adding `kv.ladder.enabled=false` (L1 keeps the exact `l0` copy); the eval sends its 32 fillers 16 at a time (`--filler-concurrency 16`), resends a filler the server answers 503 or 429 (`filler_retries`; scored items still abort), and with `--fillers-settle` polls `/turbine/v1/pressure` until GREEN after the fillers, then sends the next item alone before the rest at `--concurrency` (so the burst of the other items finds the prefix already promoted). The gate is three candidate and three baseline runs, each on a fresh server that is checked to have served only its eval (the sum of `turbine_requests_total` over every endpoint and outcome equals 200 items + 32 fillers + `filler_retries`; `turbine_kv_prompt_tokens_total` is no check here, since resends and SURVIVAL requeues count again), judged by `scripts/eval/paired_compare.py --max-drop 0.01` over the nine candidate × baseline pairs: the median drop is at most 0.01, no pair has McNemar p < 0.05, and every candidate passes `--min-lossy-cached-ratio 0.5`. The recipe is in `.procoder/handoff/p6b-eval-prefix.md`.

## Out of scope

- NVFP4 in every container, NVIDIA execution and the NVIDIA rows (deferred `phase-2b-nvidia`); MXFP6 / MXFP8, INT8 weights or activations, INT4 in other packings, GGUF (umbrella out of scope).
- Attention over KV formats other than `bf16`, `fp8_e4m3`, `tq4` and `tq2`; TurboQuant-compressed K/V in prefill GEMMs other than attention.
- Per-layer KV bit widths; `tq3` (user decision 2026-09-28, Q12); lossless general-purpose compression (LZ4/zstd) of tier slots (user decision 2026-09-28, Q18).
- Producing quantized checkpoints; quantization-aware anything; Python anywhere but fixture generation.
- Weight formats, FP8 KV in L0 itself, YaRN and the quality-gate tooling (`phase-6a-quantization`, closed before this phase starts).

## Constraints

- Test tiers (AGENTS.md "Test tiers", decision 2026-09-27): per landing step `scripts/gate.sh`, plus `scripts/lab-test.sh novanas --tier quick` when GPU-facing code changes (`turbine-kernels`, `turbine-model`, `turbine-device`, the ABI, `kernels/rocm`), plus `scripts/lab-bench.sh --quick` when throughput or numerics can change; phase exit: `scripts/gate.sh --full`, `scripts/lab-test.sh novanas --tier full` and its two-GPU leg, `scripts/lab-bench.sh --golden16` for Llama and OLMoE BF16 with every KV format on, and `scripts/overload-soak.sh novanas --duration 10m` (asked first).
- Reuse first (AGENTS.md rule, decision "Kernel reuse policy"): every kernel of S-1 (transcode), S-4 and S-5 is preceded by a recorded evaluation in `.procoder/ask/decisions.md` of CK (`ck_tile` `gemm_quant`, microscale, FMHA FP8), hipBLASLt (FP8, scaled), llama.cpp HIP (q4/q8 and MXFP4 mat-vec and mmq, flash attention with quantized KV), vLLM / SGLang / aiter ROCm kernels and the compressed-tensors / Quark unpack paths; an own kernel only when none builds, none is correct on `gfx1201` or all are measurably slower. No Python in the build or runtime path; third-party kernel sources are pinned (CK by its existing `FetchContent` commit; llama.cpp by commit if used) and their licenses land in `kernels/rocm/third_party/LICENSES/`.
- Correctness bar: every GPU implementation has a lab test against the CPU reference (codecs and `cpu::tq_attention`); the BF16 and FP8 golden tolerances, the OLMoE calibration and the Phase 4 `kv_gpu` bit-exact checks at the `l0` tier format do not change; lossy blocks are never served to an opted-out request.
- Nothing lossy by default: `kv.cpu.format`, `kv.nvme.format`, `kv.dtype` and `kv.ladder.enabled` default to the exact behaviour.
- Pluggability: every KV codec and kernel implementation is one file (or directory) plus a registry entry; a new `docs/extending/kv-format.md` describes codecs and `docs/extending/eviction-policy.md` the compress action; `cargo test -p turbine-model --test docs_extending` keeps them true.
- Vendor neutrality (umbrella S-5): no HIP type in a public signature of `turbine-kernels`, `turbine-tensor`, `turbine-scheduler`, `turbine-kv` or `turbine-reliability`; every ABI addition is an optional minor group specified so a CUDA library can implement it when `phase-2b-nvidia` is re-specced.
- Unsafe Rust and FFI stay in `turbine-kernels` (and the existing allowlist); `turbine-kv` stays GPU-free (codecs' GPU side is a kernel op the server's orchestrator calls).
- Host copies go through pinned memory (L1 slots, the per-shard pinned bounce buffer); no pageable async copy is added (ROCm pageable-copy bug).
- Bounded everything (TS §21 rule 8): transcode batches (≤ 32 blocks, the Phase 4 `DEMOTION_INFLIGHT`), ladder rewrites per tick (32), lineage keys (one per lossy copy, reclaimed with it), the `lossy_penalty` map (one entry per registered codec).

## Edge cases

- Lossy lineage: a request that opted out arrives while only a lossy copy of its prefix exists: it recomputes from the first lossy block and publishes an exact chain alongside the lossy one; a later exact lookup takes the exact chain.
- Promotion of a lossy block into L0 for a request that allows lossy reuse: the L0 copy keeps the lossy key; blocks that request prefills on top are chained from it (lossy lineage) and are never matched by an opted-out request.
- `kv.lossless_tail_blocks` larger than a sequence's full blocks: every block of it is demoted at the L0 format.
- Ladder: a tier already at `kv.ladder.max_format` and still above high water: the oldest least-reusable blocks are evicted (`ladder_floor`); pressure returns to GREEN mid-rewrite: in-flight rewrites complete, no new ones start; a block referenced by a running request is never rewritten; a block being promoted is never rewritten. A new demotion into a tier whose rung just changed (the slabs still hold the old slot size) is stored at the tier's own format until a slot of the rung's size frees (`rung_no_slot`); demotions keep flowing, the L0 block still leaves.
- Transcode failure on the device: the demotion is abandoned (the source copy stays), the tier is marked degraded as for a copy error (Phase 4 S-12), the request never fails.
- NVMe slab written by an older `TKVSLAB1` version: impossible (wiped at startup).
- A sequence whose L0 blocks have different formats (base-format tail, ladder-compressed older blocks): one attention call reads every block by its tag; a request that opted out of lossy reuse never gets a compressed block attached (lineage keys), and its own blocks are never compressed while it runs.
- A TurboQuant page class that cannot grow (the KV budget is exhausted): the ladder rewrite is skipped for that tick (`reason = "no_room"`), never a request failure. In L1/L2 the same holds for a tier with no free slot of the new format's size (a slab still holding blocks of an old size): the rewrite fails its store and `turbine_kv_ladder_actions_total{reason="no_room"}` counts it; the copy keeps its format: L1 and L2 find the new slot before they free the old one (L2 freed it first until user decision 2026-10-02, "6b Task 16: ladder proof results — four open points", 2 A). After a `no_room` the ladder submits no rewrite into that tier until the tier's `room_epoch` changes (a slab emptied or was released, or host pressure left RED), counts the back-off once as `reason = "no_room_backoff"` and each rewrite it skips in `HierarchyStats::ladder_backoff_skips`; floor evictions of the tier still run (same decision, 3 A).
- `kv.dtype: tq2` with a request that opts out of lossy reuse: the request still runs (its own KV is lossy by configuration, reported in `quantization.kv_dtype`); the opt-out governs reuse of other requests' cached blocks only.
- A kernel library without v2.11 and a non-`l0` tier format, `kv.dtype: tq4|tq2` or the L0 ladder: exit 1 before bind with `kv_transcode_unavailable` or `kv_tq_unavailable`.

## Failure modes

- **Golden or accuracy gate fails for a format:** its row stays `experimental` (degraded) or `unsupported` (wrong), the finding is recorded, and the phase continues with the next format; the phase closes only with the user's decision on each non-passing format.
- **TurboQuant decode mismatch between GPU and CPU:** the lab test fails; the codec's row stays `experimental`.
- **Lossy block served to an opted-out request:** a correctness bug; prevented by lineage keys, covered by a simulator test that asserts it can never happen.
- **Ladder oscillation:** bounded by hysteresis and the per-tick rewrite cap; a simulator test with a pinned pressure trace asserts the rung sequence.
- **Kernel library lacks the v2.11 group:** exit 1 before bind with `kv_transcode_unavailable` or `kv_tq_unavailable`.
