# phase-2b-nvidia

Status: complete

Source: `turbine-spec.md` §19 Phase 1 and Phase 2 feature set carried to NVIDIA, with §3, §5, §6, §9, §16, §17, §18 and §21. Sections of that document are cited as "TS §N". Builds on `.procoder/specs/phase-0-skeleton.md` (NVML discovery with unified-memory reporting, `scripts/lab-test.sh dgx-spark|dgx-spark2`), `.procoder/specs/phase-1-single-request.md` (vendor-neutral kernel C ABI `kernels/include/turbine_kernels.h`, kernel registry and capability traits, _libturbine_hip.so_, Llama executor, HF transformers golden fixtures, `turbine-golden`) and `.procoder/specs/phase-2-serving-runtime.md` (scheduler, paged KV, OLMoE, llguidance structured output, tool calling, baseline bench). Decisions are recorded in `.procoder/ask/decisions.md` ("Answers log for phase 1–8 spec questions (2026-09-25)"): AMD first for Phases 1–2, NVIDIA/GB10 "right after Phase 2 behind the same vendor-neutral kernel traits", kernels as prebuilt shared libraries built with CMake and loaded at runtime, BF16 only, ask the user before any run that needs production workloads moved or memory freed. The six provider, build and memory questions of this spec were answered by the user on 2026-09-25 (all as recommended): FlashInfer for attention; third-party CUDA sources via CMake `FetchContent` at pinned commits; cuBLASLt for dense GEMM; `cublasGemmGroupedBatchedEx` for MoE grouped GEMM with per-expert cuBLASLt as registry fallback; a CUDA 13.0 lab image from `nvidia/cuda:13.0.x-devel-ubuntu24.04` (arm64) pinned by digest; `cudaMalloc` with a pinned `cudaHostAlloc` staging buffer on GB10. The user also confirmed that correctness runs on the Sparks may proceed without asking when the `MemAvailable` pre-check passes, while benchmark, soak and overload runs always ask first.

Amendments made by this spec:

- Amends TS §19 (Phase 1 "CUDA/kernel bridge" on NVIDIA first): NVIDIA execution arrives here, after the AMD Phases 1–2, as a second implementation of the Phase 1 C ABI.
- Amends phase-0 S-7 for the Sparks only: `scripts/lab-test.sh dgx-spark|dgx-spark2` runs in the CUDA 13.0 Spark lab image (`scripts/lab/spark.Dockerfile`, based on `nvidia/cuda:13.0.x-devel-ubuntu24.04` arm64 pinned by digest) instead of plain `rust:1.97-trixie`, because the CUDA shim must be compiled there. novanas is unchanged.
- Amends phase-1 Interfaces: _execution.backend_ `cuda` is accepted (Phase 1 rejected it with exit 2 naming this spec).

## Problem

After Phase 2, Turbine is a serving runtime — continuous batching, chunked prefill, paged BF16 KV, preemption, bounded queues, OpenAI core fields, llguidance structured output and Llama-3 tool calling — for `meta-llama/Llama-3.2-3B-Instruct` and `allenai/OLMoE-1B-7B-0125-Instruct`, but only on the AMD R9700 in novanas through _libturbine_hip.so_. Half of the lab — the two DGX Sparks (NVIDIA GB10, `sm_121`, arm64, ~121 GB of CPU/GPU unified memory each, linked by 200 Gb/s RoCE) — cannot run a single token, and every later phase assumes it can: Phase 3 budgets and pressure-tests unified memory on GB10, Phase 4 disables L1 on unified devices, Phase 5 needs `DeviceBuffer`/`StreamRef` over _libturbine_cuda.so_ for NCCL, Phase 6 is built entirely on the Sparks, and Phase 7 moves KV between HIP and CUDA pools. The Phase 1 C ABI and kernel traits were written vendor-neutral precisely so this port is a second shim, not a second engine: this phase implements _libturbine_cuda.so_ against the same header with NVIDIA kernel providers (TS §6 candidates FlashInfer, CUTLASS, cuBLASLt), proves it against the same committed golden fixtures and tolerance, and shows that everything above the kernel layer (scheduler, KV accounting, sampling, llguidance, tool parsing, API) runs unchanged on arm64 + CUDA + unified memory. It must do so without disturbing the production vLLM that both Sparks serve.

## Users

- **Turbine developers (humans and AI agents):** need `libturbine_cuda.so` built by one CMake command inside the Spark lab container, per-op correctness tests against the CPU reference on a real GB10, the same golden test binary selecting its backend from the environment, and a guarantee that no CUDA code leaks above `turbine-kernels`.
- **Operators evaluating Turbine:** need `turbine-server` with _execution.backend_ `cuda` to load either model on a GB10, compute its memory budget from unified memory correctly, refuse to start (before reading weights) when the library, architecture or memory is wrong, and serve exactly the Phase 2 API.
- **Benchmark runners:** need a recorded Turbine-on-GB10 baseline next to the production vLLM build serving the same BF16 weights on the same Spark (TS §18), with no numeric bar in this phase.
- **Later phases (3, 4, 5, 6, 7):** need the CUDA backend's device buffers, streams, error codes and unified-memory reporting to behave exactly like the HIP backend's through the shared ABI.

## In scope

- [S-1] CUDA shim project `kernels/cuda/` (C++/CUDA, CMake ≥ 3.28 with the CUDA language, `nvcc`), producing _libturbine_cuda.so_ that implements every function of `kernels/include/turbine_kernels.h` at the ABI version current at the end of Phase 2, with no change to the header: `turbine_abi_version`, `turbine_backend_name` (returns `"cuda"`), `turbine_build_archs` (returns `"sm_121"`), context, stream, allocation, copy, memory-info and error functions, and every op with its `_supported` and `_impl` companions. Built for `CMAKE_CUDA_ARCHITECTURES=121a` (the arch-specific target the Blackwell `sm_12x` kernel paths of CUTLASS and FlashInfer require); the CUDA runtime is linked statically (`CUDA_RUNTIME_LIBRARY Static`) so the only CUDA libraries resolved at load time are the driver (`libcuda.so.1`, injected by the NVIDIA container runtime) and the math libraries of the chosen providers.
- [S-2] Rust `cuda` provider in `crates/turbine-kernels`: loads _libturbine_cuda.so_ with `libloading` through the same binding code as the `hip` provider (one `ShimLibrary` type parameterised by the expected backend name), so the kernel registry, `DeviceBuffer`, streams and error mapping are shared. No CUDA type, header or crate (`cudarc` included) enters the Rust workspace; `cargo build --workspace` on macOS is unaffected.
- [S-3] Phase 1 op set on CUDA: `gemm`, `attention_prefill`, `attention_decode`, `rmsnorm`, `rope` (Llama-3 scaled and standard), `silu_mul`, `embedding`, `add` for BF16 with FP32 accumulation, head_dim 128, GQA (24/8 for Llama, 16/16 for OLMoE). Attention (`attention_prefill`, `attention_decode`) comes from FlashInfer (Apache-2.0; its single-request prefill and decode templates, FA2-style path for `sm_12x`, instantiated in `kernels/cuda/src/` and fetched by `kernels/cuda/CMakeLists.txt`); `gemm` (projections and LM head, BF16 in, FP32 accumulate) from cuBLASLt of the pinned CUDA 13.0 toolkit, with heuristic algorithm selection and `turbine_gemm_supported` returning 0 when the heuristic finds no algorithm; `rmsnorm` from FlashInfer's norm kernels. Ops no NVIDIA library ships standalone (embedding gather, Llama-3 rotary embedding when FlashInfer's rope variant does not match the llama3 scaling formula exactly, SiLU-and-multiply, residual add) are minimal Turbine CUDA kernels in `kernels/cuda/src/`. Performance-motivated custom kernels replacing a library kernel come only after profiling (TS §21 rule 3).
- [S-4] Phase 2 op set on CUDA: `attention_prefill_paged` and `attention_decode_paged` through FlashInfer's batch prefill and batch decode with paged KV (ragged batch with page table over the Phase 2 block layout `[num_blocks, 2, block_tokens, kv_heads, head_dim]` BF16 per layer, which is FlashInfer's NHD paged layout `[num_pages, 2, page_size, kv_heads, head_dim]`, passed as pointers and strides — the pool layout is not changed for this backend), `copy_blocks` (a Turbine kernel), `moe_route` (softmax, top-k, token permutation; a Turbine kernel ported from the HIP one) and `moe_experts` (gate/up and down projections for all selected experts as grouped GEMMs through cuBLAS `cublasGemmGroupedBatchedEx` — BF16 inputs, FP32 compute, one group per non-empty expert — with a second registered implementation, one cuBLASLt GEMM per non-empty expert over the permuted token segments, as the registry fallback for any configuration the grouped call rejects; SiLU-and-multiply between, weighted un-permute into the residual).
- [S-5] Context, stream and thread rules in the shim: `turbine_ctx_create(ordinal)` selects the device, creates one non-blocking stream, the GEMM library handle and a preallocated workspace (size fixed at creation, logged), and records the device's compute capability, refusing a device that is not 12.1 with code `-2` and a message naming both. Every entry point re-selects the context's device (`cudaSetDevice`) before work, so any engine thread may call it. Every launch is on the context stream; `turbine_stream_sync` is the only blocking call. CUDA errors map to the Phase 1 codes (`cudaErrorMemoryAllocation` → `-3`, other runtime errors → `-4`, cuBLASLt/provider status → `-5`), and the message from `turbine_last_error` starts with the CUDA error name (e.g. `cudaErrorIllegalAddress: …`) so Phase 3 can classify context-corrupting errors without a new ABI function.
- [S-6] Unified-memory handling on GB10: `turbine_malloc` uses `cudaMalloc` (device allocations carved from the shared LPDDR5X, not pageable or migratable, visible in `cudaMemGetInfo`) for weights, the KV pool and workspace, all preallocated at startup; weights are uploaded through the Phase 1 bounded staging buffer (≤ 256 MiB) allocated with `cudaHostAlloc` (pinned) and copied with `cudaMemcpyAsync` on the context stream. `cudaMallocManaged` and stream-ordered pools are not used. `turbine_mem_info` reports `cudaMemGetInfo`. The startup budget uses the Phase 1 S-5 rule for `unified` devices — available = min(`turbine_mem_info` free, host `MemAvailable`) — for the first time on real hardware; weights + `kv.gpu.max_bytes` + workspace + _reliability.emergency_vram_reserve_ must fit before any weight is read. The Phase 0 inventory entry (kind `unified`, `shared_with_host: true`, arch `sm_121`) is the source of the device kind.
- [S-7] Backend selection: _execution.backend_ accepts `cuda`; with `cuda`, _execution.device_ must be an NVIDIA device of the Phase 0 inventory and the default _execution.kernel_library_ search is `TURBINE_KERNEL_LIBRARY`, then _libturbine_cuda.so_ beside the executable, then the loader search path. The default backend stays `hip` (Phase 1); Spark configs set `cuda` explicitly.
- [S-8] Backend-selected GPU tests: every `#[ignore]` GPU test calls `require_backend("hip"|"cuda")`, which reads `TURBINE_TEST_BACKEND` — equal: the test runs; a different backend: the test prints `SKIP backend=<value>` and returns; unset: the test fails naming the variable. New test binary `crates/turbine-kernels/tests/cuda_ops.rs` mirrors `hip_ops` (Phase 1 and Phase 2 ops against the CPU reference); `tiny_model` gains `cuda_matches_cpu`; the golden in-process test `logits_match_reference` and the Phase 2 `lab_openai` test run on whichever backend `TURBINE_TEST_BACKEND` names.
- [S-9] Lab scripts for the Sparks: `scripts/lab-test.sh dgx-spark|dgx-spark2` builds `kernels/cuda` and runs the workspace tests with `--include-ignored` in the Spark lab container (`docker run --rm --gpus all`) with the weights mounted read-only; `scripts/lab-serve.sh dgx-spark|dgx-spark2 <config>` runs `turbine-server` in a container named `turbine-lab-serve` on port 18000; `scripts/lab-serve.sh <spark> --vllm <slug>` runs the vLLM baseline container `turbine-lab-vllm` on port 18100; `--stop` removes only `turbine-lab-*` containers. Every Spark script first runs a memory precondition (Interfaces) and exits 1 with `precondition` rather than competing with production.
- [S-10] Weights on both Sparks: `/home/piwi/turbine-models/llama-3.2-3b-instruct` and `/home/piwi/turbine-models/olmoe-1b-7b-0125-instruct`, downloaded once over SSH by Claude with a Hugging Face token the user supplies at that time (never written to the repository, scripts, container environment or a file on the host), at the same revisions as on novanas; `scripts/lab/weights-manifest.sh <host> <slug>` prints `sha256  <file>` for every file of a model directory so hosts can be compared.
- [S-11] Golden parity on GB10: both models meet the Phase 1 tolerance file of their fixture directory (`tests/golden/llama-3.2-3b-instruct/`, `tests/golden/olmoe-1b-7b-0125-instruct/`; ≥ 14/16 prompts first 32 greedy tokens identical, top-5 |Δ logprob| ≤ 0.15 nats) in-process on the `cuda` provider and over HTTP with `turbine-golden compare --concurrency 16`. The fixtures and tolerance are the committed HF transformers BF16 references — nothing is re-captured for NVIDIA.
- [S-12] Above-kernel feature parity: the Phase 2 scheduler, paged KV, preemption, `n` > 1, penalties, llguidance `response_format`, `llama3_json` tool calling and graceful shutdown run unchanged on the CUDA backend; the Phase 2 `lab_openai tools_and_json_schema` test passes on a Spark.
- [S-13] Baseline benchmark on dgx-spark (asked first, see Constraints): `turbine-bench` at the Phase 2 profile against Turbine serving each model on the `cuda` backend, then against the production vLLM build (image `ghcr.io/spark-arena/dgx-vllm-eugr-nightly-tf5`, pinned by the digest production runs, `sha256:b94ac8ac…37c3` on 2026-09-25) serving the same BF16 weights in `turbine-lab-vllm`; plus the Phase 2 overload run against Turbine. Baseline only: no numeric bar.
- [S-14] Observability: the Phase 1/2 metrics unchanged in name, with `turbine_kernel_provider_selected{op,provider="cuda",impl}` naming each chosen implementation (`"cublaslt"`, `"flashinfer_prefill"`, `"flashinfer_decode"`, `"flashinfer_batch_prefill_paged"`, `"flashinfer_batch_decode_paged"`, `"flashinfer_rmsnorm"`, `"cublas_grouped_batched"`, `"cublaslt_per_expert"`, `"turbine_cuda"`); a startup log record `kernel_library_loaded` with path, backend, ABI version, build archs, CUDA driver version and the device's compute capability; the CMake build log prints the `nvcc` version, the GEMM library version and the pinned commit of every fetched provider.

## Out of scope

- New model families, quantized weights or KV (NVFP4, FP8, MXFP4), speculative decoding (Phase 8 tracks). BF16 only, as on AMD.
- Memory pools, pressure states, telemetry, circuit breaker and GB10-specific budgeting (`reliability.memory.host_reserve_bytes`, `device_budget_bytes`) — Phase 3; this phase uses the Phase 1 startup budget only.
- KV tiers (L1 disabled on unified memory, L2 NVMe) — Phase 4. NCCL, multi-GPU and multi-node, RoCE — Phases 5–7.
- CUDA graphs, device-side sampling, kernel fusion, autotuning, custom kernels replacing library kernels, FP8/FP4 tensor-core paths (TS §21 rule 3).
- Loading weights by reading directly into device-visible unified memory without the staging buffer (an optimisation, only if a benchmark shows load time matters; it would need managed or host-registered memory, which this phase does not use).
- Mixed-vendor serving in one process or cluster (Phase 7).
- Any change to the production vLLM containers, their ports, their configuration or their images; any change to host packages, drivers or the NVIDIA container runtime on the Sparks.
- A Turbine container image for deployment (the lab image is a test harness, not a product artifact).
- Other NVIDIA GPUs (Hopper, Ada, datacenter Blackwell `sm_100`): _libturbine_cuda.so_ is built and validated for `sm_121` only; other archs are refused by the arch check.

## Constraints

- Same C ABI: _libturbine_cuda.so_ implements `kernels/include/turbine_kernels.h` exactly as _libturbine_hip.so_ does; the header stays free of vendor identifiers (phase-1 `abi_header_neutral` test). If an NVIDIA provider needs information the descriptors do not carry, the ABI version is bumped and both shims implement the change in the same commit — never a CUDA-only side channel.
- Rust only in the workspace build and runtime path; the shim is C++/CUDA compiled by `nvcc` through CMake and exposes only the C ABI (TS §6). No Python in the build or serving path (TS §21 rule 4): no FlashInfer JIT, no Python code generation during `cmake --build`; Python appears only in the unchanged `scripts/golden/hf_reference.py`.
- The Rust workspace builds and every non-ignored test passes on macOS arm64 with no GPU, no CUDA and no ROCm (Phase 0/1 constraint, unchanged). Nothing links CUDA at build time.
- `unsafe` and FFI only in `turbine-device` and `turbine-kernels`, every block with a `// SAFETY:` comment; the Phase 1 ownership rules (TS §21 rule 10) apply unchanged to CUDA device pointers, streams and handles.
- External kernel libraries: each fetched provider pinned by exact commit or release in `kernels/cuda/CMakeLists.txt`, only the template instantiations Turbine uses compiled (BF16, head_dim 128, the GQA ratios of the two models, the Phase 2 page layout); licenses retained under `kernels/cuda/third_party/LICENSES/` (TS §6). Toolkit libraries (cuBLASLt, cuBLAS, the static CUDA runtime) come from the CUDA 13.0 toolkit of the lab image, which matches the host driver 580.173.02's native CUDA version; the toolkit is never taken from the host's `/usr/local/cuda`.
- Target hardware: `dgx-spark` (192.168.10.246) and `dgx-spark2` (192.168.10.245) — NVIDIA GB10, compute capability 12.1 (`sm_121`), arm64 (aarch64) Ubuntu 24.04, driver 580.173.02 (CUDA 13.0 driver API), host CUDA toolkit 13.0 (`nvcc` 13.0.88, cuBLAS/cuBLASLt 13.1.1.3, no NCCL, no cuDNN), CMake 3.28.3 on the host, ~121 GB unified memory, Docker 29 with the `nvidia` runtime. Lab execution is always `docker run --gpus all` (Phase 0), user `piwi`, containers named `turbine-lab-*`, HTTP ports 18000–18099 (Turbine 18000, vLLM baseline 18100).
- Production co-tenancy: both Sparks serve production vLLM (image `ghcr.io/spark-arena/dgx-vllm-eugr-nightly-tf5`, host networking, 55–75 GB of the unified pool; `MemAvailable` was 42 GiB on dgx-spark and 29 GiB on dgx-spark2 on 2026-09-25). Turbine scripts never stop, restart, move or reconfigure those containers. Any run that needs production workloads moved or memory freed on any host is preceded by asking the user, and the user moves workloads. Correctness runs (`lab-test.sh`, golden compare) proceed without asking only when the memory precondition passes. Benchmark, soak and overload runs always ask the user first, because GB10 compute is shared with production vLLM: an unannounced benchmark degrades production and measures co-tenant noise.
- Bounded resources (TS §21 rule 8): the Phase 1 staging buffer (≤ 256 MiB) and the Phase 2 bounds apply unchanged; the shim's GEMM workspace is fixed at context creation; the lab containers get `--memory` caps (Interfaces) so host-side runaway cannot squeeze production.

## Interfaces

### `kernels/cuda/` build

```
cmake -S kernels/cuda -B <build> -DCMAKE_CUDA_ARCHITECTURES=121a [-DTURBINE_CUDA_ROOT=<toolkit>]
cmake --build <build> --parallel
```

- Produces _libturbine_cuda.so_ (SONAME _libturbine_cuda.so_), exporting only `turbine_*` symbols (`-fvisibility=hidden` plus an export list generated from the header). `TURBINE_CUDA_ROOT` defaults to `/usr/local/cuda`. FlashInfer is fetched with CMake `FetchContent` at an exact pinned commit (header-only templates; no FlashInfer Python, JIT or AOT wheel is used), and only the instantiations Turbine uses are compiled by `nvcc` inside the Spark lab image: BF16, head_dim 128, GQA group sizes 3 (Llama 24/8) and 1 (OLMoE 16/16), page size 16. cuBLASLt and cuBLAS (`libcublasLt.so.13`, `libcublas.so.13`) come from the toolkit in the lab image and are linked dynamically. A configure run on a machine without `nvcc` fails with `CUDA compiler not found` — the Rust build never invokes it.
- `kernels/cuda/src/` holds the shim (context, memory and one source file per op family) and the minimal Turbine kernels; `kernels/cuda/third_party/LICENSES/` the provider licenses.

### `scripts/lab-serve.sh` on the Sparks

```
scripts/lab-serve.sh <dgx-spark|dgx-spark2> <config.yaml>
scripts/lab-serve.sh <dgx-spark|dgx-spark2> --vllm <slug>
scripts/lab-serve.sh <dgx-spark|dgx-spark2> --stop
```

- `--dry-run` (before the other arguments) prints the precondition arithmetic and every `docker` command without running any of them, and exits 0.

- Turbine: precondition needed = on-disk weight bytes of the configured model + `kv.gpu.max_bytes` + 4 GiB (workspace, emergency reserve, runtime); requires `MemAvailable` ≥ needed + 8 GiB, else exit 1 `precondition` with the numbers. Builds release `turbine-server` and the kernel library in the lab image, then `docker run -d --gpus all --name turbine-lab-serve --memory 16g -p 18000:18000` with the model mounted read-only and the config at `/config.yaml`; waits up to 10 min for `/ready` 200 on `http://<host>:18000`, streaming the container log; exit 1 with the log tail on failure (and removes the container).
- vLLM baseline: precondition `MemAvailable` ≥ 0.20 × `MemTotal` + 8 GiB; `docker run -d --gpus all --name turbine-lab-vllm -p 18100:8000 --ipc host` of `ghcr.io/spark-arena/dgx-vllm-eugr-nightly-tf5@<digest>` with `serve /models/<slug> --served-model-name <HF id> --dtype bfloat16 --kv-cache-dtype auto --gpu-memory-utilization 0.20 --max-model-len 8192`; waits for `/v1/models` or exits 1 with the log tail. The digest is a variable at the top of the script, set to the digest production runs when the baseline is taken and recorded in the evidence.
- `--stop`: `docker rm -f` of `turbine-lab-serve` and `turbine-lab-vllm` only.

### Metrics and logs

- No new metric names. `turbine_kernel_provider_selected{op,provider,impl}` gains `provider="cuda"` values; `turbine_model_weight_bytes{format="bf16"}` unchanged.

## Data

- Nothing new is persisted by `turbine-server`. Weights, KV blocks and workspace live in allocations of the unified pool for the process lifetime.
- KV block layout and sizes are the Phase 2 ones (`[num_blocks, 2, block_tokens, kv_heads, head_dim]` BF16 per layer; 1,835,008 bytes per 16-token block for Llama-3.2-3B, 2,097,152 for OLMoE). The Spark lab configs use a 4 GiB pool: 2,340 blocks (Llama), 2,048 blocks (OLMoE).
- Expected claims on a Spark (logged by the budget check): Llama-3.2-3B ≈ 6.4 GB weights + 4 GiB KV + workspace + 2 GiB emergency reserve ≈ 13 GiB; OLMoE-1B-7B ≈ 13.8 GB weights + 4 GiB KV + workspace + 2 GiB ≈ 20 GiB.
- Golden fixtures: unchanged committed files under `tests/golden/` (Phase 1 and 2); `turbine-golden compare` outputs for the Spark runs are pasted into task evidence, not committed.
- Lab image: `scripts/lab/spark.Dockerfile` (committed), tagged `turbine-lab-cuda:<sha256 of the Dockerfile, first 12 hex>`, built on each Spark on first use; build outputs under `/home/piwi/turbine-ci/target` (kernel library in `kernels-cuda/`).
- Weights manifests: output of `scripts/lab/weights-manifest.sh` per host, pasted into task evidence.
- Baseline evidence: the `turbine-bench` JSON reports, the vLLM image digest, the lab image tag, the toolkit and driver versions, and a `nvidia-smi --query-compute-apps=pid,used_memory --format=csv` snapshot taken just before each run (records whether production was active).

## Edge cases

- The Phase 0 inventory reports GB10 memory as `unified` with total = host `MemTotal`, while `cudaMemGetInfo` reports its own free/total view of the same pool; the budget must take the minimum of free and `MemAvailable`, never add them or use total.
- `MemAvailable` drops between the precondition and weight upload because production vLLM grows its footprint: the Phase 1 budget check inside `turbine-server` still refuses before reading weights; an allocation failure after it (race) fails startup with exit 1 naming the allocation, never an OOM kill of another process.
- The container `--memory` cap versus GPU allocations: device allocations made by the driver may not be charged to the container's cgroup, so the cap bounds host-side memory only; the precondition and the in-process budget, not the cap, protect production.
- `turbine_build_archs` reports `sm_121` while the library is built for `121a`; a GB10 reports compute capability 12.1 → `sm_121` in the inventory. A library built for another arch (e.g. `sm_90`) is refused at context creation naming both archs.
- A host where the NVIDIA container runtime is missing or `--gpus all` yields no device: Phase 0 inventory has 0 NVIDIA devices; `turbine-server` with backend `cuda` exits 1 naming _execution.device_.
- The cuBLASLt heuristic returns no algorithm for a GEMM shape (e.g. very small `m` in decode, OLMoE expert width 1024 with a handful of tokens): `turbine_gemm_supported` reports `0` for that descriptor and the registry falls through to the next provider in order (the CPU reference is never used for a GPU model: a missing GPU provider is a startup error per Phase 1 S-6).
- Paged attention with a ragged batch mixing a 1-token decode and a 2,048-token prefill chunk; a page table whose last block is partially filled; `block_tokens` other than 16 (the instantiated page sizes are 16 only; other values are refused by `_supported` and hence at startup, naming the value).
- OLMoE: every token selecting the same 8 experts; an expert with zero tokens (grouped GEMM with an empty group); router ties broken by lower expert id exactly as on HIP and in the CPU reference.
- Two engines on one GB10 (Turbine and production vLLM): no exclusive-process compute mode is assumed; both contexts time-slice. Correctness tests must not depend on timing.
- `lab-test.sh` running both on dgx-spark and dgx-spark2 concurrently: they are independent hosts; the scripts share nothing but the source tree.
- `TURBINE_TEST_BACKEND` unset inside a lab container: every GPU test fails loudly (no silent skip).
- Denormals/NaN: BF16 inputs containing NaN in the CPU-reference comparison tests are excluded by construction (seeded unit-variance inputs); a NaN in real logits fails the golden test at that position.

## Failure modes

- **CUDA toolkit or compiler missing in the build environment:** CMake configure fails with `CUDA compiler not found`; `lab-test.sh` exits non-zero naming the CMake step.
- **_libturbine_cuda.so_ missing, unloadable (e.g. missing `libcublasLt.so.13`), wrong ABI version, wrong backend name or wrong arch:** exit 1 naming the path, the loader error, both ABI numbers, both backend names or both archs; the search order is logged.
- **Driver too old for the toolkit the library was built with:** `turbine_ctx_create` returns `-4` with `cudaErrorInsufficientDriver: …`; exit 1 with that message.
- **Memory precondition fails:** the script exits 1 with `precondition` and both numbers before starting any container; the implementer asks the user to free memory and never evicts production.
- **Budget exceeded in-process:** exit 1 before reading weights, naming each term and `available_bytes` with its two sources.
- **CUDA error during an iteration:** handled exactly as the Phase 2 device-error path (requests in the iteration fail with `internal_error`, 3 consecutive failed iterations → `/ready` 503 `device_error`, exit 1); the log record carries the CUDA error name. Sticky-error circuit breaking is Phase 3.
- **Provider does not support a required configuration on `sm_121`:** `_supported` returns 0; if no provider in the configured order supports the op, startup fails naming op and configuration (Phase 1 S-6); the minimal Turbine CUDA kernel is then written for it, recorded in the selection log as `impl="turbine_cuda"`.
- **vLLM baseline fails to start on the chosen digest:** the baseline records "vLLM did not run" with the log tail; this phase's exit is not blocked.
- **Weights differ between hosts:** the manifest comparison fails; the model is re-downloaded (asking the user for the token again) before any golden run on that host.
- **A production container stops or restarts during a lab run:** the lab script does not react to it; the implementer reports it to the user and pauses lab runs until the user confirms.
