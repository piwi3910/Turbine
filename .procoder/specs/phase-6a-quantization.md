## Problem

After Phase 5 Turbine serves `Llama-3.2-3B-Instruct` and `OLMoE-1B-7B-0125-Instruct` in BF16 only, with BF16 KV only, on one or both R9700 cards (`gfx1201`, 32 GB each) of `novanas`. The checkpoints people run at useful sizes ship quantized — FP8 per-channel and block-scaled, MXFP4, INT4 AWQ and GPTQ — and today any `quantization_config` is refused at config load (`weights::tests::bf16_refusals_match_main`). RDNA4 has FP8 WMMA but no FP4 matrix path: hipBLASLt on the installed ROCm 7.14.1 offers FP8 × FP8 → BF16 with scalar and per-row/column scales but no mixed BF16 × FP8 and no block-scaled or microscaled GEMM, so FP4 and INT4 run weight-only and every format needs a kernel decision under the reuse-first rule. An FP8 e4m3 KV cache halves the L0 page and doubles the pool, but no attention path reads FP8 pages today. The families of Phase 7 (Qwen3 at 32K → 128K, gpt-oss at 4K → 128K) extend context with static YaRN RoPE scaling, which the config parser refuses today. The support matrix still names the old Phase 8 tracks, and the quality-gate tooling the umbrella requires exists only on a run-ahead branch.

## Users

- **Operators:** load a quantized checkpoint by pointing `model.path` at it, see its resolved format in the support-matrix row and `/turbine/v1/status`, get a startup refusal with a reason for anything not proven, and choose FP8 KV explicitly.
- **API clients:** get the same OpenAI API from quantized models and from FP8-KV and YaRN-extended configurations.
- **Turbine developers:** add a weight format or a checkpoint packaging as one file plus a registry entry, with a CPU reference and a conformance suite that run on the macOS workstation, and the kernel evaluations recorded before any own kernel.
- **Phase 7:** needs FP8 dense layers under TP 2 (Mixtral), the MXFP4 OpenAI-native loader (gpt-oss) and YaRN for every family.
- **Phase 6b:** needs `DType::F8E4M3`, the FP8 KV path and the quality-gate tooling.

## In scope

The sub-steps land in this order (user decision 2026-09-28, Q1): foundations (S-1, S-2) → weights (S-3 … S-12) → FP8 KV in L0 (S-13, S-14) → YaRN (S-15, S-16); S-17 … S-20 (gates, configuration, observability, lab) accompany every step.

### Foundations

- [S-1] Umbrella port and support-matrix cleanup. The umbrella tasks that exist only on `runahead/p8-umbrella` are ported first: `quality.max_accuracy_drop` and `speculative.method` configuration keys (umbrella plan Task 1), `turbine-golden eval` / `eval-compare` (Task 5), the committed `tests/eval/gsm8k-200.jsonl` with its generator and NOTICE (Task 6) and `scripts/track-gate.sh` (Task 8, with the amended gate and the track names `phase-6a-quantization` and `phase-6b-kv-compression`). Then, in `turbine_core::support`: the refusal reasons name `phase-6-quantization`, `phase-7-model-families` and `phase-8-speculative-decoding` instead of `phase-8a/8b/8c`, and the tests asserting them follow; the four `nvidia`/`sm_121` × Llama / OLMoE BF16 rows become `unsupported` with a reason naming the deferred `phase-2b-nvidia`; `WeightFormatColumn` gains `fp8`, `fp8_block`, `mxfp4`, `mxfp4_a4` (user decision 2026-09-28, Q6), `awq_int4`, `gptq_int4`, each with an `unsupported` refusal row naming `phase-6a-quantization` until its proof passes; `KvFormatColumn` keeps `bf16` and `fp8_e4m3` (`tq4` and `tq2` arrive with `phase-6b-kv-compression`). `SupportKey::bf16` and `SupportKey::before_discovery` are replaced by keys built from the detected weight format and the configured L0 KV dtype, so the resolved row names the real combination.
- [S-2] Engine vocabulary. `turbine_core::types::DType` gains `F8E4M3` (ABI code 16) and `U8` (code 17, raw packed bytes; the element type of INT4 / FP4 / E8M0 buffers), within the header's reserved 16..63 range. `KvDtype` already has `Fp8E4m3PerTensorScale` (wire code 2); `KvLayout` sizes it at one byte per element. No `DType` value is used as a format by itself: packed formats are described by S-3's `QuantScheme`.

### Weights

- [S-3] `WeightFormat` becomes a quantized-linear description. The trait (`turbine_model::weights`) keeps `check_config` / `check_tensor` and replaces the three dtypes with: `column()` (the support-matrix value), `scheme(&self, layer: &LinearSlot) -> QuantScheme` (per linear layer; layers the checkpoint leaves unquantized, e.g. `lm_head`, embeddings, norms, report `QuantScheme::Bf16`), `slots(&self, base: &WeightSlot) -> Vec<WeightSlot>` (the tensors one quantized linear layer needs: packed data, scales, zero points, E8M0 exponents, activation scales) and `activation(&self) -> ActivationQuant` (`None` | `Fp8PerTensorStatic` | `Fp8PerTokenDynamic` | `Fp8PerGroupDynamic { group }` | `Mxfp4Emulated`). One registry entry per checkpoint packaging, one file each under `crates/turbine-model/src/weights/`: `bf16`, `ct_fp8` (compressed-tensors FP8 tensor/channel/block), `hf_fp8` (`quant_method: fp8`, with or without `weight_block_size`), `awq` (AutoAWQ GEMM), `gptq` (AutoGPTQ), `ct_pack_int4` (compressed-tensors `pack-quantized` W4A16), `ct_mxfp4` (`mxfp4-pack-quantized`), `quark_mxfp4` (Quark `fp4` group 32, E8M0 scales, weight-only or W4A4) and `openai_mxfp4` (`quant_method: mxfp4`, `*_blocks` / `*_scales` tensors); `detect` keeps `bf16` first. Container → column mapping (user decision 2026-09-28, Q5): `fp8` ← compressed-tensors `float-quantized` 8-bit with weight strategy `tensor` or `channel`, and `quant_method: fp8` without `weight_block_size`; `fp8_block` ← compressed-tensors weight strategy `block` [128, 128] and `quant_method: fp8` with `weight_block_size` [128, 128]; `awq_int4` ← `quant_method: awq`, `version: gemm`, 4 bits, zero points; `gptq_int4` ← `quant_method: gptq`, 4 bits, `desc_act: false`, and compressed-tensors `pack-quantized` 4-bit int, group strategy, no non-trivial `g_idx`; `mxfp4` ← compressed-tensors `mxfp4-pack-quantized` without input activations, Quark `fp4` weight-only, OpenAI `mxfp4`; `mxfp4_a4` ← Quark `fp4` weights with `fp4` dynamic input tensors. Refused with a reason: act-order GPTQ (`desc_act: true` or a non-identity `g_idx`, reason `gptq_act_order`), any bit width, group size, block shape or scale dtype outside these (reason `quant_scheme_unsupported` naming the field), `kv_cache_scheme` other than null or static FP8 per-tensor, and every container mapping to one of the four `weight_format` columns the umbrella reserves for the deferred `phase-2b-nvidia` (listed under Out of scope).
- [S-4] Loading. `WeightLoader` loads through the detected format (no hard-wired `Bf16`); each quantized linear layer becomes a `QuantLinear { scheme, data: DeviceTensor, scales: Option<DeviceTensor>, zeros: Option<DeviceTensor>, act_scale: Option<f32> }` whose layout is the one the kernel provider needs (S-6): the loader repacks at load time where a packaging's layout differs (AWQ's interleaved nibble order, GPTQ's row-packed `qweight`, OpenAI's `*_blocks`), on the host, through the existing 256 MiB staging buffer and pinned bounce buffer. The fused Q/K/V and gate/up stacks of Phase 1 stay: stacking concatenates packed rows and their scales; a stack whose parts have different per-tensor scales is rescaled to a per-channel scale vector at load (exact). Memory accounting (`ModelShape.weight_bytes`) counts the packed bytes and the scale tensors.
- [S-5] CPU reference. `turbine-kernels` `cpu` provider gains `dequantize(scheme, data, scales, zeros) -> Vec<f32>` for every scheme and a quantized GEMM that dequantizes the weight to F32 and, for `ActivationQuant` other than `None`, quantize-dequantizes the activations first (FP8 e4m3 round-to-nearest-even with saturation; MXFP4 E2M1 with E8M0 shared exponent per 32, OCP rules). It is the reference every GPU implementation is tested against. Every family's `write_tiny` gains a quantized variant per packaging (`testing::tiny::write_tiny_quantized(dir, family, packaging, seed)`, written in Rust, no Python), so the macOS test suite covers detection, loading, repacking and CPU execution of every packaging.
- [S-6] Kernel ABI. An optional minor group v2.9 (`TURBINE_ABI_MINOR` 9; `TURBINE_ABI_VERSION` stays 2, per the umbrella constraint) adds: `turbine_qgemm_desc` (A, B, C pointers and strides as `turbine_gemm_desc`, plus `int32_t scheme`, `b_scales`, `b_zeros`, `a_scales`, `group_size`, `block_n`, `block_k`, `act_quant`) with the trio `turbine_qgemm` / `turbine_qgemm_supported` / `turbine_qgemm_impl` and op code `TURBINE_OP_QGEMM` = 17; `turbine_quantize_act_desc` with the trio `turbine_quantize_act*` (op 18: per-tensor static, per-token dynamic and per-group-of-128 dynamic FP8 e4m3, and MXFP4 quantize-dequantize) ; scheme codes `TURBINE_QSCHEME_FP8_TENSOR` 1, `_FP8_CHANNEL` 2, `_FP8_BLOCK` 3, `_INT4_GROUP_ZP` 4, `_INT4_GROUP_SYM` 5, `_MXFP4` 6; dtype codes `TURBINE_DTYPE_F8E4M3` 16 and `TURBINE_DTYPE_U8` 17. A library with minor < 9 simply has no quantized GEMM, and a quantized checkpoint on it is refused at startup (exit 1, `event="kernel_capability"`, reason `qgemm_unavailable`). Rust: `OpKind::QGemm`, `OpKind::QuantizeAct`, `QGemmConfig { n, k, scheme, act_quant, c_dtype, group_size }`, `trait QGemmKernel { supports, implementation, execute }`, `KernelProvider::qgemm()` / `quantize_act()` defaulting to `None`, and `KernelRegistry::qgemm(&cfg)`.
- [S-7] `fp8` on HIP (user decision 2026-09-28, Q2): W8A8 following the checkpoint's activation scheme — per-token dynamic or per-tensor static activation quantization (`turbine_quantize_act`), then hipBLASLt FP8 × FP8 → BF16 with the weight's scale as scalar or per-column vector (`HIPBLASLT_MATMUL_DESC_*_SCALE_POINTER` / the vector-scale mode the gfx1201 `SABV` kernels implement) and the activation scale per row; a checkpoint with no activation scheme runs W8A16 through the dequantize path of S-8. The quantize step is fused into the preceding RMSNorm where the evaluation shows a provider for it, else it is its own op. Registered implementation `hipblaslt_fp8` in `impl_table.cpp`; the `gemm_table` tuning covers FP8 shapes.
- [S-8] `fp8_block` on HIP: first CK `ck_tile` `ABQuantGrouped` (FP8 A per-token-group-of-128 scales × FP8 B per-128 × 128-block scales) instantiated for `gfx1201` from the pinned CK; if it does not build or does not match the CPU reference, W8A16 through a dequantize-to-BF16 path (user decision 2026-09-28, Q3), with the evaluation recorded before any own kernel.
- [S-9] `awq_int4` / `gptq_int4` on HIP, weight-only (W4A16, BF16 activations): decode (M ≤ 16) through a dequantize-GEMV and prefill through dequantize-to-BF16 tiles feeding a BF16 WMMA GEMM or CK `BQuantGrouped` with packed INT4 B; candidates evaluated in order: CK `ck_tile` `gemm_quant` `BQuantGrouped` (pk_int4 B), llama.cpp's HIP `mul_mat_vec_q` / `mmq` for 4-bit groups (as a registered implementation built from pinned sources), vLLM/aiter ROCm AWQ/GPTQ kernels (their `gfx12` support), then own. Zero points (AWQ) and symmetric groups (GPTQ, 8 as implicit zero) share one kernel family with a scheme flag.
- [S-10] `mxfp4` and `mxfp4_a4` on HIP, weight-only on RDNA4: FP4 E2M1 values times 2^(E8M0 − 127) per 32 elements dequantized to BF16 in the kernel (exact in BF16), candidates in order: CK `ck_tile` microscale pipeline (`gemm_microscale_*`), llama.cpp's HIP MXFP4 (`GGML_TYPE_MXFP4`) mat-vec and mmq kernels, then own. `mxfp4_a4` (Quark W4A4) runs the same kernel after `turbine_quantize_act` quantize-dequantizes each 32-element activation group to MXFP4 (the checkpoint's `round_method: half_even`, `scale_calculation_mode: even`); its row is `supported` only if it passes the S-3 gate against the checkpoint's reference, else `experimental` (decision "Phase 6 MXFP4"). The OpenAI native packaging (`openai_mxfp4`) is loaded and repacked into the same layout and tested on a tiny fixture; its row stays `unsupported` (reason naming `phase-7-model-families`) until Phase 7 closes gpt-oss-20b.
- [S-11] Proofs per weight format. Each format is proven on a real checkpoint downloaded on `novanas` into `/home/piwi/turbine-models/<slug>` with `hf download <repo> --revision <sha> --local-dir …` (free disk checked first, ≥ 60 GB kept free): `fp8` on `RedHatAI/Llama-3.2-3B-Instruct-FP8-dynamic` @ `c308a86de78778c5f904a1d82401ac85e18ca205` (gate) and `RedHatAI/Llama-3.2-3B-Instruct-FP8` @ `377571d314b30f1d58448499e4100e2deafe7d7d` (per-tensor path); `fp8_block` on `unsloth/Llama-3.2-3B-Instruct-FP8-Block` @ `08cf804398b23fab4a1df02fbe8d4d5a11a800cc`; `awq_int4` on `casperhansen/llama-3.2-3b-instruct-awq` @ `272b3bde867b606760447deb9a4d2719fbdfd3ae`; `gptq_int4` on `shuyuej/Llama-3.2-3B-Instruct-GPTQ` @ `dd5a311f040728fbc612eb03c8dadfae0a90552f` (all user decision 2026-09-28, Q4); `mxfp4` on `FabioTrindade/Llama-3.1-8B-Instruct-W4A16KV16-MXFP4A16` @ `14c3aca849a72df8fcc8b3a30ab8d9eed86ee646` and `mxfp4_a4` on `matmelis/Llama_3.2_3B_w_mxfp4_a_mxfp4_gptq` @ `91925ffda6977d097354a99718a20e035f8af80a` (decided); the 8B BF16 quality baseline is `unsloth/Llama-3.1-8B-Instruct` @ `4699cc75b550f9c6f3173fb80f4703b62d946aa5`. Golden references per checkpoint (user decision 2026-09-28, Q8): `scripts/golden/quant_reference.py` (fixture time only) decodes the checkpoint's weights exactly into a temporary BF16 checkpoint and runs the transformers reference on it, with activation fake-quantization for W8A8 and W4A4; each slug's `tolerance.json` is calibrated from transformers' own spread with `self_spread.py` (the OLMoE method, documented in the slug's `README.md`). - [S-12] Quantized layers under parallelism (user decision 2026-09-28, Q7): dense linear layers only; `fp8` and `fp8_block` under Phase 5 TP (per-channel scales sharded with column-parallel outputs, per-tensor scales replicated, 128 × 128 blocks aligned to the shard), `awq_int4` / `gptq_int4` / `mxfp4` under TP where each shard's input dimension is a multiple of the group size (row-parallel) — otherwise refused at startup with `quant_shard_misaligned` naming the layer; proven at tp 2 by the lab golden for `fp8` and `awq_int4`. ### FP8 KV in L0

- [S-13] `kv.dtype` (umbrella-reserved key) with values `bf16` (default) and `fp8_e4m3`. With `fp8_e4m3`, `KvLayout.dtype` is `F8E4M3`, pages halve and the pool holds twice the blocks; the paged-append step quantizes new K and V rows with per-layer K and V scales (user decision 2026-09-28, Q10: from the checkpoint's `kv_cache_scheme` / `k_scale` / `v_scale` tensors when present, else 1.0; the scales enter the namespace key); attention reads FP8 pages through the provider the evaluation picks — the pinned CK FMHA pagedkv / split-KV FP8 instances for `gfx1201` first, then an FP8-reading variant of the Turbine paged kernel (dequantize on load), then llama.cpp's HIP flash attention if its quantized-KV path can be adapted to e4m3 pages. The CPU provider stores and reads F8E4M3 through the S-5 rounding rules. Nothing lossy is on by default (umbrella constraint): `fp8_e4m3` is always an explicit setting. FP8 KV works under Phase 5 TP, EP and DP (per-rank pools, same scales on every rank). Support rows `amd/gfx1201/{Llama,Olmoe}ForCausalLM/bf16/fp8_e4m3/none` turn `supported` after the S-17 gate; FP8 KV combined with a quantized weight format is `supported` only for combinations that passed their own gate.
- [S-14] KV tier accounting under FP8: the lower tiers store the L0 page bytes as they are (the `l0` format), the Phase 4 `kv_gpu` round trips stay bit-exact at `fp8_e4m3`, and `/turbine/v1/kv` and `turbine_kv_bytes` report the real bytes.

### YaRN

- [S-15] `rope_scaling` type `yarn` parsed for every registered family (`factor`, `original_max_position_embeddings`, `beta_fast` (default 32), `beta_slow` (default 1), `mscale` / `mscale_all_dim` / `attention_factor` as transformers resolves them, `truncate` (default true)); `inv_freq` computes transformers' `_compute_yarn_parameters` blend in FP64 on the host; the attention factor folds into the attention softmax scale (`scale × attention_factor²`, user decision 2026-09-28, Q19), so the RoPE ABI is unchanged. `dynamic`, `linear`, `longrope` and a YaRN entry with a `dynamic` flag stay refused (dynamic scaling would change cached keys mid-sequence). `model.max_seq_len` may extend to `factor × original_max_position_embeddings` when `max_position_embeddings` is smaller. A configuration key `model.rope_scaling` (a mapping with HF's field names) overrides `config.json`'s entry (user decision 2026-09-28, Q19).
- [S-16] RoPE configuration in identity: the resolved RoPE parameters (type, theta, every scaling field) enter the namespace key, so blocks cached under one RoPE configuration are never reused under another. Proof (user decision 2026-09-28, Q19): Llama-3.2-3B-Instruct with `model.rope_scaling: {rope_type: yarn, factor: 16.0, original_max_position_embeddings: 8192, beta_fast: 32, beta_slow: 1}` against transformers' native YaRN on a copy of the checkpoint carrying that `config.json` (fixture time), over the 16 golden prompts plus one ≈ 12,000-token prompt, committed as `tests/golden/llama-3.2-3b-instruct-yarn16/`; the row stays the BF16 Llama row (YaRN is not a support-matrix column), gated by that golden at c1 and c16.

## Out of scope

- NVFP4 in every container, NVIDIA execution and the NVIDIA rows (deferred `phase-2b-nvidia`); MXFP6 / MXFP8, INT8 weights or activations, INT4 in other packings, GGUF (umbrella out of scope).
- Act-order GPTQ (`desc_act: true`, non-trivial `g_idx`) (user decision 2026-09-28, Q5).
- Quantized MoE expert weights (Phase 7, user decision 2026-09-28, Q7); pipeline-parallel quantized serving (pipeline stages are refused by the server in Phase 5).
- Dynamic RoPE scaling, `linear`, `longrope`; partial rotary dimensions.
- Producing quantized checkpoints; quantization-aware anything; Python anywhere but fixture generation.
- Automatic selection of `kv.dtype` from a checkpoint's `kv_cache_scheme` (an explicit setting is required).
- Per-tier KV formats, lower-tier transcoding, lossy lineage and the per-request lossy opt-out, TurboQuant (lower tiers and L0), mixed-format attention and the compression ladder: `phase-6b-kv-compression`, which starts after this phase closes.

## Constraints

- Test tiers (AGENTS.md "Test tiers", decision 2026-09-27): per landing step `scripts/gate.sh`, plus `scripts/lab-test.sh novanas --tier quick` when GPU-facing code changes (`turbine-kernels`, `turbine-model`, `turbine-device`, the ABI, `kernels/rocm`), plus `scripts/lab-bench.sh --quick` when throughput or numerics can change; phase exit: `scripts/gate.sh --full`, `scripts/lab-test.sh novanas --tier full` and its two-GPU leg, `scripts/lab-bench.sh --golden16` for Llama and OLMoE BF16 plus every proof checkpoint, and `scripts/overload-soak.sh novanas --duration 10m` (asked first).
- Reuse first (AGENTS.md rule, decision "Kernel reuse policy"): every kernel of S-7 … S-10 and S-13 is preceded by a recorded evaluation in `.procoder/ask/decisions.md` of CK (`ck_tile` `gemm_quant`, microscale, FMHA FP8), hipBLASLt (FP8, scaled), llama.cpp HIP (q4/q8 and MXFP4 mat-vec and mmq, flash attention with quantized KV), vLLM / SGLang / aiter ROCm kernels and the compressed-tensors / Quark unpack paths; an own kernel only when none builds, none is correct on `gfx1201` or all are measurably slower. No Python in the build or runtime path; third-party kernel sources are pinned (CK by its existing `FetchContent` commit; llama.cpp by commit if used) and their licenses land in `kernels/rocm/third_party/LICENSES/`.
- Correctness bar: every GPU implementation has a lab test against the S-5 CPU reference; every quantized checkpoint has a golden reference; the BF16 golden tolerances, the OLMoE calibration and the Phase 4 `kv_gpu` bit-exact checks at `kv.dtype: bf16` and at the `l0` tier format do not change; lossy blocks are never served to an opted-out request.
- Nothing lossy by default: `kv.dtype` defaults to the exact behaviour; a quantized checkpoint is lossy only relative to BF16, and it is served as stored.
- Pluggability: every packaging, weight format and kernel implementation is one file (or directory) plus a registry entry; `docs/extending/weight-format.md` is rewritten for S-3; `cargo test -p turbine-model --test docs_extending` keeps them true.

## Edge cases

- A checkpoint whose `config.json` says `torch_dtype: float16` with quantized linears (AWQ, GPTQ): activations run in BF16 (`model.dtype`), F16 scales are converted at load; embeddings and norms stored in F16 are converted to BF16 at load (logged once).
- `lm_head` or embeddings unquantized (`ignore: ["lm_head"]`) or tied: `QuantScheme::Bf16` for those, the BF16 GEMM path.
- A fused stack (qkv, gate_up) whose parts carry different per-tensor FP8 scales: rescaled to a per-channel vector at load (exact); parts with different schemes (one quantized, one not): refused `quant_scheme_unsupported`.
- `n` or `k` not a multiple of the group or block size: refused `quant_scheme_unsupported` naming the layer (the proof checkpoints are aligned).
- A kernel library without v2.9 and a quantized checkpoint: exit 1 before bind with `qgemm_unavailable`; `kv.dtype: fp8_e4m3` without FP8 paged attention: exit 1 `kv_fp8_unavailable`.
- CPU backend: every format runs through the S-5 reference (slow, `experimental` like every CPU row).
- FP8 KV with a checkpoint that stores `k_scale`/`v_scale` and a TP split: every rank uses the same per-layer scale.
- YaRN with `original_max_position_embeddings` ≥ `max_position_embeddings` (nothing to extend): accepted, `max_seq_len` capped by `max_position_embeddings`; YaRN on a model whose config already has `llama3` scaling: the override replaces it wholesale.
- Two requests with different RoPE overrides cannot exist (one model per process); a server restarted with a different override never sees the old blocks (L2 wiped; namespace differs).

## Failure modes

- **Unsupported quantized checkpoint:** config load refuses it (exit 1 before weights are read, `quant_refused` with reason); an `unsupported` support row exits 2 under `--check-config` and 1 at startup (umbrella).
- **Kernel library lacks a group:** exit 1 before bind with `qgemm_unavailable` or `kv_fp8_unavailable`.
- **A quantized kernel produces NaN/Inf at warm-up:** the Phase 1 warm-up check fails startup (exit 1) naming the op and implementation.
- **Golden or accuracy gate fails for a format:** its row stays `experimental` (degraded) or `unsupported` (wrong), the finding is recorded, and the phase continues with the next format; the phase closes only with the user's decision on each non-passing format.
- **A download fails or disk falls below 60 GB free:** the download stops and the coordinator is asked; nothing else is deleted.
