## How each number was measured

1. **Served kernel timeline (primary source).** A bench-only `turbine-server` (the `lab-bench.sh` command line plus `ROCP_TOOL_ATTACH=1`) ran the fixed bench. 25 s in, `rocprofv3 --attach <pid> --attach-duration-msec 3000 --kernel-trace --memory-copy-trace --hip-runtime-trace -f csv` recorded about 130 steps. The script split the kernel trace into engine steps at each `logits_reduce_kernel`. A step containing `rope_token_kernel` counts as mixed (it has prefill rows); the others count as decode-only (graph-replayed). For each step it reports the span from the first to the last kernel, the busy time (sum of kernel durations), the per-kernel time, and the idle time between kernels, attributed to each kernel pair. The HIP API trace gives the host side of the step boundary: `hipEventSynchronize`, `hipMemcpyAsync` and `hipGraphLaunch`.
2. **Op profile (`turbine-model --test perf forward_profile`, release, native on GPU 0).** Each op is followed by a stream sync. That is good for large ops. For small ones it adds about 15–20 µs of launch and sync time per op (e.g. `add_rmsnorm` reads 23 µs against a 2 µs kernel). The synthetic decode cases also copy full logits rows (`reduce: None`), which serving does not do. At Llama b16 that adds 4.3 ms of `logits_read`.
3. **Kernel microbenchmarks (`turbine-kernels --test hip_ops decode_op_timings prefill_op_timings`).** Every op alone at the served shapes, with weights cycled out of the caches.
4. **hipBLASLt algorithm sweep (scratch program, not committed).** For every GEMM shape Turbine runs, it reproduces the exact layouts of `kernels/rocm/src/gemm.cpp` (weight `OP_T`, activation `OP_N`, F32 compute). It times hipBLASLt's first heuristic answer (what the library runs today) against all 256 algorithms the heuristic returns, on random BF16 data, with more than 512 MB of weight copies cycled. (A first run on constant data inflated the compute-bound results by up to 25 %, so only the random-data run is used.)
5. **Memory footprint.** `mem_info_vram_used` / `mem_info_gtt_used` of card0 (GPU 0) were sampled every 2 s while serving.
6. **A/B runs with existing switches only** (no code): `HIP_FORCE_DEV_KERNARG=1` (Llama, traced) and `execution.overlap_scheduling=true` (Llama, traced).

`serving_mix` (Llama fusion combinations, superseded by the served trace) and `host_step_costs` (host sampler cost, which the served `sample` stage already puts at 7 µs per iteration) were not rerun.

- GEMMs are 72.7 % of busy time, and 87 % of the weight bytes stream at 570–604 GB/s. The weak spots are o_proj and down, the two N=3072 shapes, which reach only 48 workgroups with the heuristic's 64×64 tile.
- The roofline for one step is weights 6.43 GB + KV ~1.72 GB ≈ 8.15 GB, i.e. 13.4 ms at the ~610 GB/s the LM head and OLMoE's attention actually reach. The step runs at 73 % of that roofline.
- **Gaps between kernels:** 287 boundaries × ~3.5 µs = 1.0 ms (5.5 % of the step), even though the step is one graph replay. `HIP_FORCE_DEV_KERNARG=1` changes nothing (gaps 1,360 vs 1,373 µs, 767.1 tok/s), so kernarg placement is not the cause. Only fewer kernels shorten this.
- **Host round trip:** 0.35–0.39 ms of GPU idle per step. It breaks down as: host wake-up from the logits wait (15 µs), host work (sampling, detokenize, emit, complete, schedule, pack; ~125–130 µs), `hipGraphLaunch` (~140 µs, blocking; the graph's first kernel starts ~1 µs after it returns), and the two small upload copies (blit kernels of ~3 µs).

## Host syncs and round trips (both models)

Per step, graph-replayed or eager, the HIP API trace shows:

- 3 × `hipMemcpyAsync`: the H2D batch metadata through pinned staging, the H2D logits-reduce inputs, and the D2H reduce results. Each runs as a ~3 µs `__amd_rocclr_copyBuffer` blit kernel.
- 3 × `hipEventSynchronize`, of which exactly **one** blocks: the logits wait. The other two are staging-reuse checks that return in ~1 µs.
- 1 × `hipGraphLaunch` (136–140 µs of host time) for a decode step, or ~290 kernel launches of ~2 µs each for a mixed step.

No step issues a device→host read inside the layer loop.

## Item 3: the OLMoE decode host round trip per layer. Refuted for this tree.

- **Code.** `hooks/moe.rs` reads the expert offsets back only when `MoeKernel::needs_host_offsets` is true for the batch's routed rows. On gfx1201 the card profile picks `turbine_hip_moe_small_m` up to 512 routed rows (every decode batch of up to 64 sequences) and `turbine_hip_moe_wmma` above that. Both read the group sizes on the device and carry no `IMPL_NEEDS_HOST_OFFSETS` flag. So no per-layer copy is made, and decode batches stay graph-capturable (`FfnHook::graph_capturable`). Only the `hipblaslt_*` fallbacks need host offsets.
- **Trace.** OLMoE's step boundary is identical in shape to Llama's (same copies, one blocking wait). 3,710 of about 3,730 decode forwards were graph replays (`turbine_decode_graph_total{outcome="replayed"}`).
- **Cost at Gen5.** The per-step round trip costs 0.38 ms of GPU idle, 1.6 % of the 24.3 ms step. The bytes moved are a few KB (the D2H blit is 2.7 µs). The time is host work (~125 µs) and `hipGraphLaunch` (~136 µs), not the link. If a host-offset provider were ever selected again, `decode_op_timings` puts `moe_offsets_read` at 34–38 µs per layer (0.55–0.6 ms per step at Gen5), plus the loss of decode graphs.
- **What the Gen1 collapse needs instead.** 149 ms vs 17 ms is ~130 ms of extra time per step, which at Gen1's measured ~1.6 GB/s is ~210 MB of PCIe traffic per step. The per-step transfers cannot account for that. The most likely cause is **VRAM oversubscription on GPU 1**:
  - The OLMoE server occupies **25.4 GB** of the card's 34.2 GB; the Llama server occupies **17.9 GB**. GTT grows by only 6–10 MB in both, so nothing spills on GPU 0.
  - When sampled today, GPU 1 already had **14.0 GB** in use by another tenant, at 88 % busy.
  - OLMoE plus that tenant (39.4 GB) cannot be resident together; Llama plus that tenant (31.9 GB) can. Evicted buffers (weights or KV moved to GTT by the driver) would then be read over PCIe every step, which hurts badly at Gen1 and only OLMoE.
  - Unverified; it needs a functional run on GPU 1 with the other tenant present. Suggested check: sample card1 `mem_info_vram_used` / `mem_info_gtt_used`, and run `rocprofv3 --kfd-trace` for queue-eviction and page-migration events.

## Other findings

1. **`execution.gemm_autotune: true` is a no-op.** Nothing outside the config reads the key. `libturbine_hip.so` does not export the ABI v2.1 `turbine_ctx_set_option`. `gemm.cpp` asks hipBLASLt for one heuristic algorithm (`requestedAlgoCount = 1`) and caches it. The sweep shows that answer is 15–41 % slower than the best algorithm for four of the nine decode shapes.
2. **The perf log's "decode fwd ms" is diluted.** `lab-bench.sh` scrapes `/metrics` after the golden c1 run (batch-1 steps) in the same server. The clean c16 decode forward is 17.48 ms for Llama (the log says 16.9) and 23.48 ms for OLMoE (the log says 21.2). Rows remain comparable to each other, but they understate c16 by 3–10 %.
3. **`logits_reduce` runs one workgroup per row.** It takes 330 µs for 16 rows of 128,256 logits (8.2 MB, ~25 GB/s), 2 % of every Llama step.
4. **Overlap scheduling does hide the host round trip:** traced decode span 17.96 vs 18.25 ms, 769.3 tok/s. But TTFT p50 rises to 254 ms (+29 %): 118 mixed steps instead of 107, because new arrivals join one iteration later. The throughput gain is spent on TTFT, which is why it measured flat when it landed.
5. **Wave-shaped arrivals.** Under this workload new requests arrive about two per step (requests prefilled together finish together). Mixed steps therefore hold two prompts (~1,630 tokens) well under the 2,048-token budget. The pressure state stayed GREEN (`batch_growth_limit` unlimited), so this is arrival-limited, not a scheduler cap. TTFT p50 ≈ two mixed steps, and it scales with the mixed-step time.

## Recommended landing order (one change, then measure)

Every step is measured the same way, and each row is appended to `.procoder/perf-log.md`:
