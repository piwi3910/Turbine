## Findings so far (no lab measurement yet; from source and headers)

- **llama.cpp** (fresh clone `bd4eeaa0`, 2026-10-07): no FP8 e4m3 tensor type → no candidate for
  Qwen3 FP8-block or Mixtral FP8 per-tensor. MXFP4 `mul_mat_id` is W4A8 only on HIP:
  `mmq.cu` `ggml_cuda_mmq_get_prec_src1` always quantizes src1 to Q8_1 off Blackwell, and
  `GGML_PREC_F32` on src1 makes the CUDA/HIP backend refuse the op. So its arithmetic is not the
  gpt-oss checkpoint's W4A16 (as in 6a's MXFP4 evaluation); still time it as a speed reference.
- **hipBLASLt 1.4.1** (ROCm 7.14): `VEC128_32F` and `BLK128x128_32F` scale modes are "Not supported
  yet" in `hipblaslt.h` → no block-scaled FP8 (Qwen3) path at all. BF16 grouped GEMM had no gfx1201
  solution in Phase 2c (`moe.cpp` `probe_grouped_gemm`). FP8×FP8 and FP8×BF16 grouped heuristics
  still need probing (the harness's `hipblaslt_grouped` candidate does it).
- **CK** (pinned `cd957402` and latest rocm-libraries `fc6b9d63`, 2026-10-07):
  - `example/ck_tile/18_flatmm` lists **gfx1201** in `SUPPORTED_GPUS` and has a WMMA config
    (`FlatmmConfig16_Wmma`): `moe_flatmm` (FP8×FP8 with per-token × per-channel F32 scales — Mixtral's
    static per-tensor W8A8 is expressible as constant row/col scales, same arithmetic) and
    `mixed_prec/a16w4_moe_flatmm` (`bf16xfp4`: BF16 activations × MXFP4 weights = gpt-oss's W4A16
    arithmetic; gfx12 under `CK_TILE_USE_WMMA && !CK_USE_GFX1250`). **These are the prime reused
    candidates.** gemm1 `gate_up` fuses SiLU (check whether gpt-oss's clamped SwiGLU / biases /
    interleaved gate_up can be expressed — likely not, would need the epilogue extended).

    real routing. `patch_flatmm.py` replaces it with seeded uniform top-k routing packed into
    `MPerBlock` tiles per expert (as `moe_sorting` would emit); the CK GPU reference
