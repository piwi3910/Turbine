## Why the ladder was refused, and what enables it

- `support_startup::kv_format_availability` refused `kv.ladder.enabled` (`kv_transcode_unavailable`, "rewrites not wired to the
  device transcode"). The `Compress` rewrites were host-codec `IoOp::Move` jobs on the I/O pool.
- The host codec cannot carry the ladder. Measured on novanas (release, one core, Llama-3.2-3B block of 14.7 MB): `fp8_e4m3`
  encode 121 ms / decode 422 ms, `tq4` 916 / 225 ms, `tq2` 577 / 240 ms. An fp8 → tq4 rewrite costs about 1.3 s of an I/O
  thread, and 32 rewrites per tick would stall L2 promotions behind them. Plan Task 15's file line already says "rewrites: L1/L2
  slot → device staging → transcode → back", so the device path is the settled design, not a new choice.
- Built (`kv_orchestrator.rs`): with the ladder on, the device transcode allocates `LADDER_LANES` (2) rewrite lanes, each an
  L0-layout block plus a slot (counted in `transcode_staging_bytes`, so in the memory budget). A rewrite takes a lane, or waits
  for one (`Job::Lane`; it never falls back to the host codec while lanes exist). The source goes to the lane: an L1 slot straight
  on the copy stream, an L2 copy through an I/O-pool read and a staging buffer. The lane is decoded (unless the source is `l0`)
  and encoded into the new format on the compute stream, D2H'd into a staging buffer, then the I/O pool `put_as`es it in the
  same tier. `tier_formats(cfg)` now includes the ladder rungs down to `max_format`, so demotions at a tier's current rung use the
  device too and the TurboQuant tables are uploaded when a rung needs them.
- Startup: the ladder's L1/L2 refusal is gone. `kv.ladder.max_format` is checked like a tier format: a library without the
  v2.11 transcode refuses it, TurboQuant L0 pages refuse it, and tensor or pipeline parallelism refuses it in
  `check_tier_formats` (the static-rank `TierDriver` has no `Compress`). `kv.ladder.l0` stays refused (Task 17).
- `scripts/overload-soak.sh` takes `--set <k>=<v>` (forwarded to `lab-serve.sh`) and saves `/metrics` to `metrics.txt` after the
  cool-down, so the soak can run the ladder config and show `turbine_kv_ladder_actions_total`.
- New lab config `scripts/lab/phase6-novanas-ladder.yaml`: L0 8 GiB, L1 2 GiB `l0`, L2 4 GiB `l0` under
  `/home/piwi/turbine-kv-ladder`, ladder on, `l0: false`, **`max_format: tq4`** (tq2 failed its own lower-tier GSM8K gate in
  Task 9; this is a choice for the lead to confirm, see Open 2).

## The turbine-kv changes (need the owner's OK)

1. `hierarchy.rs`: a directory entry's `ref_count` is the L0 pool refcount, refreshed by `sync_l0_refs` only for blocks still in
   `l0_keys`. When the L0 copy leaves (`remove_copy` at L0, `after_plan` reclaim), the entry kept the last synced value. A block
   that was referenced at its last sync and then demoted keeps `ref_count = 1` forever, and `ladder_sweep` (`ref_count == 0`)
   never rewrites it. On the server that is nearly every demoted block: the cpu-backend engine test saw 0 rewrites at ORANGE
   (both L2 blocks had `ref=1`). Fix: set `ref_count = 0` at both removal sites (6 lines). kv_sim never hit it.
2. `tier/l1.rs`: L1 allocates 1 GiB pinned slabs per slot size and released an empty slab only at host RED. The ladder writes
   new slot sizes (fp8, tq4), so an L1 of 2 slabs could never hold a third format and every later rewrite failed `Full`. Fix:
   at the size limit an empty slab of another size takes the new size (L2 already reformats empty slabs). Test
   `tier::tests::l1_reuses_an_empty_slab_for_another_slot_size`.
   This does not solve fragmentation: a slab still holding one block of an old size keeps that size. Small L1s can still stall
   (Open 3).

3. Because of (1), kv_sim `ladder_under_pinned_pressure` changed and its fixture is re-pinned in the same commit: ladder on
   122,384 recomputed tokens (610 rewrites) against 147,328 off, so the S-6 AC still holds; 9 rung changes, step-ups only at
   GREEN (steps 5127, 5756, 6313). The L1 `l0 → fp8_e4m3` change moved from step 1600 to 1113.
