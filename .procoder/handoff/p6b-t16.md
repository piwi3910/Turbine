adds `--set kv.ladder.enabled=false`. Eval: shared-prefix variant, c16, 32 fillers of 2000 words.

- FC 16 and 12: admission admits fillers until reservations fill the pool, the controller goes GREEN → SURVIVAL (0.995), a filler gets 503
  and the run aborts (fixed by the retries). FC 10: peak 0.745, YELLOW only, no ladder action.
- FC 16 with retries: the ladder acts as designed — L1 (lowest tier) rewrites the 23 prefix blocks `l0 → fp8_e4m3 → tq4`
  (`fill_high_water` 23 + 23), but lossy cached 0: the items reuse an exact L0 copy (`all_l0` 183, `l0_pressure` 16).
- With `--fillers-settle`: the first item after GREEN still plans `l0_pressure` and recomputes the prefix into a fresh exact L0 copy;
  every later item hits it (accuracy 0.770, lossy 0, guard exit 1). Without the single-item step the c16 burst of cold plans drove
  SURVIVAL again (item 503).
- **Cause (server defect, not fixed): the planner's pressure state is stale on an idle engine.** `EngineLoop::receive_commands` blocks
  when quiet and `submit` → `attach` → `attach_prefix` runs before `read_snapshot` / `kv_before_plan` refresh `KvHierarchy::l0_state`, so
  a request arriving after an idle stretch is planned with the state of the last busy turn. Here the last turn was at RED (09:54:10),
  the controller reached GREEN at 09:54:31, the item came after and got `PlanReason::L0Pressure` (planner.rs: `l0_state >= Red && best >
l0_prefix`). Proposed fix: in `EngineLoop::attach` (or `submit`) refresh the state first, e.g. a light
  `KvOrchestrator::set_l0_state(self.rel.handle.snapshot().state)` (not `before_plan`, which also does housekeeping). Test idea: cpu
  engine with L2 (pattern `yellow_releases_queued_prefixes_and_they_reattach`): get a prefix into L2 under YELLOW/RED while another
  request keeps the engine turning, let it go quiet at RED, tick the controller to GREEN, submit the prefix: `plans_total{reason=
"l0_pressure"}` stays 0 and the plan retrieves.
- Prompt-token check: filler retries and SURVIVAL requeues inflate `turbine_kv_prompt_tokens_total` (970,363 against 726,723), so "served
  only its eval" must be checked another way (e.g. HTTP request count = 232 + `filler_retries`, or the item tokens 629,014 plus the
