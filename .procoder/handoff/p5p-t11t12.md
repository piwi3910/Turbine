## What landed

- **Task 11** (`TokenMatcher::forced_tokens`, default empty): llguidance 1.8.0's
  `compute_ff_tokens`, cut at EOS and capped by `max`, never advancing the matcher. Pinned by
  `structured::tests::forced_tokens_follow_llguidance` (tiny byte tokenizer). Mutation-checked.
- **Task 12**: the engine asks after every constrained choice-0 sample
  (`EngineLoop::request_forced`, `structured_output.jump_forward` gates it) and plans the
  extension via `Scheduler::extend`. Key design points, in the order they bit:
  1. **The run travels with the plan item** (`BatchItem::draft`, scheduler-owned): the first cut
     kept the draft on the `Choice` and the `NeedsHost` rebuild re-read it after an interleaved
     sample had replaced it — the batch then fed a run that no longer matched the plan's length
     (the `jf seq=1 i=3 len=4 draft=2` panic). The plan's draft is the single source of truth;
     `build_batch` sets an engine-side `jump_drafts` map entry for `sample_forced` to verify
     against, removed at the sample or when a decode/re-prefill item retires the extension.
  2. **Extension detection** is structural, not a flag: a prefill-kind item whose start is the
     sampled token's position (`prompt_len + generated − 1`) with a non-empty draft. A prefill
     item anywhere else in a decoding choice is a re-prefill after preemption — preemption also
     clears `extend_pending` scheduler-side, and the re-prefill feeds from history.
  3. **`plan_extensions` reserves a logits row per remaining decode candidate** (the old check
     counted only the extension's own rows, so `rows + len ≤ max_running_requests` could pass
     with the decodes pushing the batch to `max_running_requests + k` rows — the executor's
     `max_seqs` refusal). The scheduler's `extend` now takes the run (`Vec<u32>`); its tests and
     the simulator were updated.
  4. **A jump-forward step is never launched ahead**: `Build::NeedsHost` while an iteration is in
     flight, and the forced iteration completes serially (`finish_forced`) — its outcome carries
     the real appended/rolled-back counts, and **it must carry `iteration`** (the first cut used
     `IterationOutcome::default()`, whose `iteration: 0` never matched `busy`, so the request
     stayed busy forever and the engine spun empty plans — the 123k-iteration hang).
  5. `kv_commits` caps at prompt + choice-0 generated: kept tokens only.
- **Metrics**: `turbine_jump_forward_tokens_total{outcome="accepted"|"rolled_back"}`,
  `turbine_jump_forward_steps_total` (`ServerMetrics::jump_forward`).
