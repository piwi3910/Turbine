## Pricing model (decision "6b Task 4: planner copy bytes", A)

The planner prices a copy at its encoded bytes (`PlanInputs.copy_bytes`). `TransferEngine`
observes every completed non-`Compress` copy at `req.bytes`, the bytes it moved (t15's
`max(bytes, from_bytes, to_bytes)` is gone). The bandwidth sample is now bytes over
(duration − latency estimate), and it's taken only when that is at least half the copy. The
old whole-duration sample made small, latency-bound compressed copies drag the per-byte rate
down (a full block priced 51 % slow), and full-size L2 blocks then priced above recompute.
The simulator's copy time is latency + `req.bytes`/bandwidth, so estimates seeded at its
costs stay there. Tests `transfer::tests::{estimates_are_per_encoded_byte,
mixed_copy_sizes_keep_latency_out_of_the_rate}` (both red before the fix).

### The ladder finding (why on 140752 lost to off 138336)

The cause is the transfer pricing, not the ladder. The engine timed each copy from its start to
the poll that saw it complete, so kv_sim observed copy times rounded up to the next 1 ms step:

| L2 → L0 copy         | modelled | observed |
| -------------------- | -------- | -------- |
| L0 format, 1835008 B | 1.935 ms | 2.000 ms |
| fp8, 917728 B        | 1.018 ms | 2.000 ms |
| tq4, 286720 B        | 0.387 ms | 1.000 ms |

With the ladder off, every L2 copy is a full block, and the estimate settled at exactly
0.129 ms + 0.98 GB/s = 2.000 ms per block. That is the break-even with recomputing 16 tokens at
8000 tok/s. With the ladder on, the over-timed compressed copies pulled the L2 → L0 estimate down
to 0.55–0.9 GB/s with 0.3–0.5 ms latency. Every full-size L2 block then priced above recompute,
so the planner recomputed it: 218 `recompute_cheaper` plans with the ladder on against 26 with it
off, and fewer cached tokens even though the ladder run had more L1/L2 lookup hits (YELLOW:
1593 L1+L2 hits vs 1301, 48176 cached tokens vs 54784). The planner lossy penalty (fp8 0.1) was
not the cause. With exact copy times the ladder wins, both at 6341cfa + the timing fix
(137440 < 145312) and with B + make_room (123456 < 128768).

## Open

0. **Production copy timing.** `IoPoolBackend` and `CopyStreamBackend`
   (`crates/turbine-server/src/kv_orchestrator.rs`, owned by the other builder) don't implement
   `took`, so on the server a copy is timed to the iteration boundary that polls it. That is the
   same bias at decode-step granularity (ms to tens of ms), and it is worse for small compressed
   copies, so it would price lossy tiers too slow in production. Options:
   A) the backends time their own copies (the I/O thread records get/put end; copy streams use a
   completion event or host timestamp), like `tp_tiers.rs` already does (recommended);
   B) the estimator discounts the poll interval (fragile);
   C) leave it: the planner errs toward recompute.

1. (Landed in 117fc51, see above.) Eviction score at encoded size: user decision 2026-09-30 **B** (58979cc). This was
   **blocked, not landed**. The candidate is `.procoder/handoff/p6b-t4t15-optionB-wip.patch`
   (apply with `git apply`). It has `score_one` pricing retrieval at `copy_codec(..).to_bytes`,
   memory at the copy's format bytes in its tier, the test
   `hierarchy::tests::score_prices_a_copy_at_its_encoded_size` (red before), and a
   `make_room` fix. Findings:
   - B alone: `per_tier_formats` fails (L1 ends with 7 copies, it needs more than 8);
     `ladder_under_pinned_pressure` needs a re-pin (on 145056 / off 147840).
   - Root cause is pre-existing (Phase 4 / Task 3): `make_room` doesn't count L1→L2 spills
     already in flight, so repeated calls spill further. L1 goes from full to empty in 3
     steps under RED, on the pre-B tree as well. The `> 8` final-state check passed there only
     by timing. B moves the victim order to fp8 copies (cheap to fetch back from L2 as tq4,
     one unit each), which exposes it.
   - B + the `make_room` fix (count in-flight departures as pending room): `per_tier_formats`,
     `cost_aware_beats_lru` and everything else pass, but ladder-off improves to 138336 and
     ladder-on (140752) no longer beats it, which violates the S-6 AC.
   - Needs a decision: land the `make_room` fix (Phase 4 behaviour change) and then look at
     why the ladder loses; or land B without it and change `per_tier_formats` to check L1's
     peak occupancy (it reaches 12 copies > 8), which weakens that assertion.
   - `demote_min_value` (absolute, default 0.0, so inert unless set): under B an L0 block's
     value falls roughly with the L1 codec's compression, because retrieval shrinks while
     memory stays at the L0 size. A configured threshold therefore drops more blocks exactly
     when the lower tier is cheaper, the opposite of the intent. Keep its meaning, but
     document it or later make it relative (not changed).
