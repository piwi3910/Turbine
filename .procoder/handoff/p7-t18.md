## The blocker: `slot_bytes` counts every weight slot as BF16

Evidence (three deterministic startups, 2026-10-09 06:02–06:11 UTC):

- run `1009055713-3623d739` (`scripts/lab-cluster.sh --bench-lock qwen3moe-spread-novanas`,
  my new calibration scenario): the tp2 server exits —
  `model startup failed: memory budget cannot hold the model: device 0 dedicated: budget=33904656384 (31.58 GiB); weights=30544916480 (28.45 GiB); workspace=1073741824; runtime=1073741824; reserve=2147483648; kv=0 (minimum 1.5 GiB for one 32768-token sequence)`
- run `20261009T060242Z` (`scripts/lab-perf.sh novanas qwen3moe --placement tp2 --eval`):
  the same error from the serve Job `1009060421-1601cba7` (lab-perf exits 1, no vLLM leg ran).
- run `20261009T061059Z` (`--placement ep2 --eval`): the same with
  `weights=32073216000 (29.87 GiB)` (serve Job `1009061102-11219681`).

Root cause: `slot_bytes` (`crates/turbine-server/src/model.rs:641`) computes every
[`WeightSlot`] as `shape product × 2` — 2 bytes/element, a BF16 assumption from before the
quantized formats. The tp2/ep2 budget branches use it over `tp::weight_slots` /
`ep::weight_slots`; the numbers match exactly: tp2's 30 544 916 480 B = 15.27e9 elements/rank
× 2, ep2's 32 073 216 000 B = 16.04e9 × 2. The true stored bytes per rank are half that
(fp8 = 1 B/element + tiny BF16 block scales): ~14.2 GiB (tp2) / ~14.9 GiB (ep2) of the 31.58
GiB budget — the model fits with ~12 GiB of KV headroom, which is what the configs expect.
The one-device branch is already dtype-aware (`arch.shape().weight_bytes` →
`weight_format.0.weight_bytes(self)`, `crates/turbine-model/src/config.rs:161`), so only the
sharded branches diverge. The Job logs show the parallel plan is correct (`tp=2` /
`ep=2`, hostmem/rccl) and the kernels resolve (fp8_block experts `turbine_hip_moe_quant`,
`local=0..128` under tp) — nothing else is wrong.

Why Task 17 did not catch it: its two-GPU leg (`hip_trace_vs_cpu_qwen3moe`) runs through the
`turbine-model` test harness, which never builds the server's memory budget; the tiny host
tests bypass it too. Mixtral (Task 21, `phase7-novanas-mixtral-{tp2,ep2}.yaml`, ~44 GB FP8)
has the same latent bug and will hit it in Task 22.

## What the fix needs (builder's suggestion, not a decision)

Make the sharded budget branches format-aware like the one-device branch: per-slot stored
bytes (fp8 1 B, mxfp4 0.5 B + scale tensors) instead of the flat ×2, or per-rank bytes derived
from `arch.shape().weight_bytes` sharded the way `tp::weight_slots`/`ep::weight_slots` shard.
Test first with a quantized tiny checkpoint: the tp2/ep2 budget's `weights=` term equals the
sum of the rank's stored bytes. Watch the interaction with Task 21's
`/turbine/v1/kv ranks[].headroom_bytes` (same accounting) and with the
`mixtral_placement_refusal` test. This is shared budget code outside Task 18's file list, which
is why I stopped instead of improvising.
