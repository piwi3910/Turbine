# AGENTS.md

Guidance for AI coding agents working in this repository.

## Project state

Turbine is a Rust LLM inference engine (reliability-first, hierarchical KV cache, no Python/PyTorch in the serving path). The repository holds the spec, the Phase 0 skeleton (`crates/turbine-{core,observability,device,api,server}`, `benches/turbine-bench`) and the Phase 1 single-request path under construction: `crates/turbine-{tensor,kernels,model}`, the vendor-neutral kernel C ABI `kernels/include/turbine_kernels.h` and the HIP shim `kernels/rocm/` (_libturbine_hip.so_), serving Llama-3.2-3B-Instruct (BF16) on one R9700 in `novanas`, and the Phase 2 serving runtime under construction: `crates/turbine-kv` (paged KV block pool and block tables) and `crates/turbine-scheduler` (continuous batching with chunked prefill, bounded queues, deterministic simulator), kernel ABI v2, OLMoE-1B-7B, tool calls and JSON-schema output. `turbine-spec.md` is the original product vision; the work is driven by procoder's chain in `.procoder/`:

- `.procoder/specs/phase-*.md` — one spec per phase. Order (decision 2026-09-28): 0, 1, 2, 2c, 2m, 3, 4, 5 done; then 6a quantization (weight formats, FP8 KV, YaRN; `phase-6a-quantization`), then 6b KV compression (per-tier KV formats, TurboQuant, the compression ladder; `phase-6b-kv-compression`) — Phase 6 split in two, decision 2026-09-28 — then 5p serving efficiency (moved after Phase 6, decision 2026-09-28: token-granular prefix reuse, cache-aware scheduling, jump-forward structured output, overlap scheduling if measured worthwhile; `phase-5p-serving-efficiency`), 7 model families, 8 speculative decoding (AMD only; umbrella `phase-6-8-expansion.md`, each phase's own spec — `phase-6a-quantization`, `phase-6b-kv-compression`, `phase-7-model-families`, `phase-8-speculative-decoding` — written when it starts). Deferred until the user lifts the multi-node / NVIDIA hold: 2b NVIDIA (carries NVFP4), 9 multi-node, 10 advanced distribution (written as 6 and 7; marked `Status: deferred` or a `Deferred:` line). Where a phase spec amends `turbine-spec.md`, the phase spec wins.
- `.procoder/plans/phase-*.md` — one implementation plan per phase; build task by task, test first, gate-clean, one commit per task.
- `.procoder/contract/interfaces.md` — cross-phase names (crates, types, config keys, metrics, C ABI). Its §23 conflict picks are binding.
- `.procoder/ask/decisions.md` — every user decision with its options. Read it before re-opening any design question.

If reality contradicts a spec or plan mid-build, update the spec/plan first and re-run `spec check` / `plan check`.

## Commands

Toolchain: Rust 1.97, edition 2024 (workspace `rust-version`). No GPU, ROCm install or model weights are needed to build or test: GPU libraries (NVML, amd-smi, _libturbine_hip.so_) are loaded at runtime, and GPU- or weights-dependent tests are `#[ignore]`d and run only on the lab hosts.

- Build: `cargo build --workspace`
- Test: `cargo test --workspace`
- One crate: `cargo test -p turbine-core`
- One unit test: `cargo test -p turbine-core config::tests::byte_size_parsing`
- One integration test: `cargo test -p turbine-api --test api route_table_phase0`
- Lint: `cargo clippy --workspace --all-targets -- -D warnings`
- Format: `cargo fmt --all` (check only: `cargo fmt --all --check`)
- Commit gate: `scripts/gate.sh [--full] [--base <rev>]` — `cargo fmt --all --check` locally, then on `novanas` via `scripts/remote-cargo.sh`: `cargo clippy --workspace --all-targets -- -D warnings` (always whole-workspace) and tests for only the crates the diff against `--base` (default: the merge-base of HEAD and `main`) touches, plus their reverse dependencies (from `cargo metadata --no-deps`, dev-dependencies included); a change to a workspace-wide file (root `Cargo.toml`/`Cargo.lock`, `rust-toolchain*`, `.cargo/**`) or `--full` runs the whole workspace instead. Runs with `cargo nextest` when it is on `novanas` (installed there once by this script, via plain `ssh`, if missing; falls back to `cargo test` if that install fails). Prints one line, `gate: ok|FAIL crates=<list> passed=N failed=M`; exit code is the failure. The clippy and test output goes to `target/gate/<timestamp>.log`: a clean gate deletes it, a failing one keeps it and names it on the FAIL line (` log=<path>`).
- No vendor GPU crate in the dependency tree: `! cargo tree --workspace | grep -Ei 'hip|rocm|cuda'`
- Validate a config: `cargo run -p turbine-server -- --config examples/turbine.yaml --check-config` — prints the resolved support-matrix row (`support: <status> (<vendor>/<arch>/<architecture>/bf16/bf16/none)`; the device arch is `*` since nothing is discovered) and then `config ok`.
- Support matrix: `cargo run -p turbine-server -- --support-matrix [--output json]` prints every row of `turbine_core::support::SUPPORT_MATRIX` (vendor, arch, architecture, weight/KV format, speculation → `supported` | `experimental` | `unsupported` with a reason) and exits 0 without reading a config. At startup the row is resolved from the backend's vendor, the model's `config.json` architecture and (after discovery) the device arch; `/turbine/v1/status` reports it as `support`, `turbine_support_matrix_status{status}` as a gauge, and the log as `event="support_matrix"` (WARN when experimental, e.g. the `cpu` backend). The Phase 7 families (Qwen3, Qwen3-MoE, Mistral, Mixtral: CPU backend only today) and the Phase 6a weight formats (`fp8`, `fp8_block`, `mxfp4`, `mxfp4_a4`, `awq_int4`, `gptq_int4`) and `fp8_e4m3` KV are `unsupported` on `amd` until their proof passes, except `experimental` on gfx1201 Llama (and OLMoE for FP8 KV) while each proof runs; every `nvidia` key is `unsupported` naming the deferred `phase-2b-nvidia` (`DEFERRED_VENDORS`, listed as `deferred nvidia …` / `deferred_vendors` in the output), and the NVFP4 columns are reserved for it. The key's weight and KV columns are the checkpoint's detected format and the configured KV dtype (`support_startup::format_columns`).
- Module selection (Phase 2m): `scheduler.policy` (default `default`) names a registered scheduling policy and `execution.card_profile` (default `auto`, the profile of the discovered device arch; a profile name forces it) a registered card profile, next to `execution.backend` and `model.tool_call_parser`; an unregistered name exits 2 before any port is bound, and `/turbine/v1/status` lists the chosen module per extension point under `modules` and every kernel choice under `kernels`.
- Run the server: `cargo run -p turbine-server -- --config examples/turbine.yaml --set server.listen=127.0.0.1:8000` (`--set <dotted.key>=<yaml value>` overrides any key; stop with Ctrl-C or SIGTERM). Exit codes: `0` clean shutdown, `1` runtime failure (port bind, explicitly configured GPU library fails to load, model directory or kernel library unusable, memory budget cannot hold the model), `2` invalid configuration, including an unregistered module name and an `unsupported` support-matrix row (reported before any port is bound), `3` fatal circuit (sticky device error, pressure-controller failure or engine panic; a supervisor restarts the process).
- Run the server with a model (needs a HIP device, the weights and _libturbine_hip.so_, so in practice use `scripts/lab-serve.sh` below): `cargo run --release -p turbine-server -- --config examples/turbine.yaml --set model.path=<model-dir> --set execution.kernel_library=<build>/libturbine_hip.so`. `/ready` answers 503 `loading_model` until warm-up is done, then 200; requests are batched continuously on one engine thread (Phase 2): up to _scheduler.max_running_requests_ run at once, further ones wait in the Phase 3 admission queue (_reliability.admission.max_queue_; full → 429 `queue_full`, waited longer than _reliability.admission.queue_timeout_ → 503 `queue_timeout`; _scheduler.max_queued_requests_ only bounds the HTTP→engine channel). Phase 3 reliability: every admitted request reserves its worst-case KV, `/turbine/v1/pressure` is the pressure document, SURVIVAL rejects 503 `overloaded`, and the circuit breaker answers 503 `circuit_open` (also on `/ready`) after a device error until internal probes pass; a sticky device error exits 3. SIGINT/SIGTERM: `/ready` and new requests answer 503 `shutting_down`, running requests get _server.shutdown_grace_, the rest are cancelled, exit 0. KV pages hold _kv.block_tokens_ tokens, default 128: on HIP a multiple of 128 runs paged attention on Composable Kernel `fmha_fwd_pagedkv` (decode of grouped query heads, e.g. Llama, on CK `fmha_fwd_splitkv`, which shares each K/V page across the query heads of its KV head); any other size falls back to the slower Turbine kernel and the server logs `event="paged_attention_fallback"` at startup.
- Build the HIP kernel library (ROCm host only; the lab Jobs do this for you): `cmake -S kernels/rocm -B <build> -DCMAKE_HIP_COMPILER=/opt/rocm/rocm/bin/hipcc -DGPU_TARGETS=gfx1201 && cmake --build <build>` produces `<build>/libturbine_hip.so`; `TURBINE_ROCM_PATH` overrides `/opt/rocm/rocm`. `execution.kernel_library: null` finds it via `TURBINE_KERNEL_LIBRARY`, then beside the executable, then the loader path.
- GPU/weights tests read `TURBINE_TEST_BACKEND` (`hip`), `TURBINE_KERNEL_LIBRARY`, `TURBINE_TEST_MODEL_DIR` and (Phase 2 MoE tests) `TURBINE_TEST_MOE_MODEL_DIR`; an unset backend variable or a missing model directory fails the test (never skips, never downloads). Run them through `scripts/lab-test.sh`, not locally.
- Reliability (Phase 3): `cargo test -p turbine-reliability` (budget, ledger, pressure state machine, admission, throttle, circuit); `cargo test -p turbine-scheduler --test overload_sim` (deterministic 10× overload, OOM recovery, cancellation; `survival_liveness_seed_6` / `_seed_1` / `_option_b` are the SURVIVAL liveness regressions; `survival_liveness_sweep -- --ignored --nocapture` prints seeds 1–12); `cargo test -p turbine-server --features fault-injection --test fault` (fault-injection build: `reliability.fault_injection` fails every Nth pool reservation, raises device OOM or kernel errors at an iteration; a default build refuses the section with exit 2); `reliability.recovery.survival_liveness` picks how SURVIVAL releases KV (`requeue_unstarted`, provisional default, or `continue_prefills`); lab: `scripts/lab-test.sh novanas --features fault-injection` (adds `sticky_device_error_exits_3` on the GPU) and `turbine-device --test lab live_telemetry`; overload soak `scripts/overload-soak.sh <novanas|dgx-spark|dgx-spark2> [--duration <dur>] [--model <path>]` (refuses a busy GPU with `precondition`, then calibrate → overload → cool-down → `verdict.json` under `target/soak/`; ask the user first, like every lab run).
- KV tiers (Phase 4): the `kv` section sizes L0 (the GPU pool), L1 (`kv.cpu.*`: pinned host memory grown in 1 GiB slabs up to `kv.cpu.max_bytes`, checked against MemTotal minus `reliability.memory.host_reserve_bytes` with exit 2; only on discrete-VRAM devices and with a kernel library exporting the ABI v2.5 copy streams, else a WARN and no L1) and L2 (`kv.nvme.*`: slab files under `kv.nvme.path`, wiped at startup, capped by free disk with exit 1); `kv.policy` names a registered eviction policy (`cost_aware` default, `lru`; `docs/extending/eviction-policy.md`) and `kv.prefix_sharing: false` turns reuse off (A/B). Requests share full-block prefixes globally unless they send `x-turbine-cache-salt`; `prompt_cache_key` plus `x-turbine-session-resume-within` / `x-turbine-session-end` are session hints; responses carry `usage.prompt_tokens_details.cached_tokens`; `GET /turbine/v1/kv` is the KV document and `POST /turbine/v1/kv/prefetch` queues promotions. Host tests: `cargo test -p turbine-kv` (identity, directory, tiers, policy, planner, transfer, session, hierarchy), `cargo test -p turbine-scheduler --test kv_sim`, `cargo test -p turbine-server --bin turbine-server engine::r#loop` (prefix reuse and an L2 round trip on the cpu backend). Multi-turn load: `turbine-bench ... --profile multi-turn --sessions <n> --turns <n> --shared-prefix-words <n> [--think-time <min>..<max>] [--session-hints]` (report adds `cached_tokens_ratio`, `ttft_ms_first_turn`, `ttft_ms_later_turns`). Concurrency 1 is the strict gate; above 1 the same token rule (≥ `min_prompts_passing` identical prefixes, margin excuse unchanged) is judged with the looser batched logprob bounds `max_abs_logprob_diff_likely_batched` / `_tail_batched` of `tolerance.json` (0.25 / 0.75; batch composition changes GEMM rounding — user decision 2026-09-26), each falling back to its strict bound when absent; the verdict line says `strict bounds (concurrency n)` or `batched bounds (concurrency n)`, the JSON report `concurrency` and `logprob_bounds`. A golden gate is both runs: `--concurrency 1` and `--concurrency 16`. `--batched-bounds` judges every concurrency by the batched bounds (the Phase 5 tensor-parallel gate against a one-GPU capture: multi-GPU modes are gated against a `capture` of the one-GPU server taken in the same run — strict for EP and PP, `--batched-bounds` for every mode with TP, which also judges TP against the committed reference with `--batched-bounds`; OLMoE under TP is gated against the committed reference only, its capture leg informational — while one GPU stays gated against the committed reference; `turbine-golden positions --url|--candidate … --prompt-id <id>` prints one prompt's per-position |Δ|). Exit `0` tolerance holds, `1` violated or the endpoint fails, `2` usage or I/O error.

## Architecture (planned — spec §4–§11)

Request path: `OpenAI API → Request Manager → Admission/Pressure Controller → Scheduler ↔ KV Orchestrator → Batch Builder → Execution Planner → Model Executor → Kernel Registry → external kernels (hipBLASLt/Composable Kernel on AMD; FlashInfer/cuBLASLt on NVIDIA) → GPU`.

Workspace layout: `crates/turbine-*` (each crate is created in the phase that gives it content — see the contract §1) plus `kernels/{rocm,cuda}` for the vendor-neutral kernel C ABI shims (`libturbine_hip.so`, `libturbine_cuda.so`, loaded at runtime). Key cross-cutting ideas that span several crates:

- **Turbine owns orchestration, not kernels.** Kernels come from external providers behind capability-based traits (`supports(cfg)` + `execute(ctx)`); FFI goes `Rust → Turbine HIP/CUDA shim → kernel library`. Scheduler/KV/reliability logic must never depend on a specific kernel provider.
- **KV is a tiered, managed resource** (L0 GPU → L1 pinned CPU → L2 NVMe → L3 cluster → L4 external), with recompute treated as a virtual tier. Eviction is cost-aware and pluggable, never LRU alone. Keep directory, placement, tiers, policy, transport and metrics as separate boundaries — no monolithic KV module.
- **Pressure controller** drives behavior via states `GREEN → YELLOW → ORANGE → RED → SURVIVAL` with hysteresis, plus a circuit breaker (`HEALTHY → DEGRADED → CIRCUIT_OPEN → DRAINING → PROBING`). Admission is predictive (`Admit | Queue{reason} | Reject{reason}`) and an emergency VRAM reserve is excluded from normal scheduling.
- **Registries and `docs/extending/`** (Phase 2m): every extension point — model family, tool-call format, weight format, kernel implementation, card family, execution backend, logits processor, scheduling policy, eviction policy (Phase 4) — is a trait plus a compiled-in `static` registry (`turbine_core::registry`) with a conformance suite run over the registry by its crate's `registry_conformance` tests. To add a module, follow its page under `docs/extending/` (index `docs/extending/README.md`): the files to add, the registry entry, the suite and command, the lab checks and the pitfalls; `cargo test -p turbine-model --test docs_extending` keeps the pages true to the tree.
- **Distributed-aware from day one**: V1 is single-GPU, but APIs stay multi-device aware; topology is a graph (node/NUMA/PCIe/GPU/NIC with edge bandwidth/latency), never a flat GPU list.

Target order (user decisions): AMD first — Phases 1–2 run Llama-3.2-3B-Instruct (BF16) and then OLMoE-1B-7B on the Radeon R9700s in `novanas` (ROCm/HIP); NVIDIA GB10 (`dgx-spark`, `dgx-spark2`, Phase 2b) is on hold until everything works well on `novanas` (decision 2026-09-26), so Phase 3 follows Phase 2 / 2c. After Phase 5 (decision 2026-09-28), AMD only: Phase 6 quantization (FP8 weights and FP8 KV, MXFP4, INT4 AWQ / GPTQ), then Phase 5p serving efficiency, Phase 7 model families (Qwen3 dense and MoE, gpt-oss-20b, Qwen3.5/3.6 hybrids, Mistral / Mixtral), Phase 8 speculative decoding; multi-node (Phase 9), advanced distribution (Phase 10) and NVIDIA (Phase 2b, with NVFP4) are deferred. OpenAI-compatible API with SSE, tools and JSON-schema output (llguidance), continuous batching with chunked prefill, paged KV, Prometheus metrics. Diagnostics live under `/turbine/v1/*`, separate from the OpenAI routes.

## Engineering rules (spec §21 — binding)

- Every optimized path needs a correctness/reference test; never trade stability for throughput by default; benchmark before specializing hot paths.
- No Python/PyTorch fallback — mark a feature unsupported until a native path exists.
- Every automatic control decision exposes reason codes, metrics, and structured traces.
- Bound all queues and caches; backpressure is mandatory. Cancellation must release resources promptly, with a test.
- Unsafe Rust and FFI stay isolated, with documented ownership/lifetime rules for GPU pointers and streams.
- Scheduler logic must be testable as a deterministic simulation without GPUs (spec §17).
- Build the smallest correct vertical slice first; avoid micro-crates without a real ownership/API boundary.
- Reuse kernels first, write our own last (user decision 2026-09-27): before adding a kernel, evaluate existing providers on the target card (Composable Kernel, hipBLASLt/cuBLASLt, FlashInfer, vLLM/SGLang kernels, llama.cpp's HIP/CUDA kernels) as registered implementations, and write one only when none works or all are measurably slower; record the evaluation in `.procoder/ask/decisions.md`. No Python (e.g. Triton) in the build or runtime path.
- Pluggability is the architecture (user decision 2026-09-26): model families, prompt/tool-call formats, quantization formats (weights and KV), speculative-decoding proposers, logits processors, scheduling and eviction policies, backends, card families, kernel providers, collectives and transports each sit behind a trait with one file (or directory) per implementation and a static registry — adding one is additive, never conditionals spread across crates; only kernels load as runtime libraries. Unsupported combinations are refused at startup with a reason code. Tracking issues: #1–#6.
